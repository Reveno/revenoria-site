# Доступність вебсторінок: семантика, клавіатура та контраст

> [!abstract] Пов'язана лекція
> [[courses/web-programming/lectures/01-iak-pratsiuie-veb-html-ta-css|Лекція 1. Як працює веб, HTML та CSS]]. Ви знайдете й виправите типові проблеми доступності на навмисно «поганій» сторінці.

## Навіщо ця робота

Доступність (accessibility, a11y) означає, що сторінкою можуть користуватися всі: люди з вадами зору (скрінрідери, збільшення), моторики (лише клавіатура), слуху (субтитри), а також ті, хто просто сидить на сонці з тьмяним екраном. У багатьох країнах доступність державних сайтів вимагається законом, а ще вона поліпшує SEO та зручність для всіх.

Ви візьмете сторінку з типовими помилками, перевірите її автоматичними інструментами та вручну, виправите та переконаєтесь, що кількість проблем зменшилась. Головна навичка тут бачити сторінку «очима» допоміжних технологій.

## Мета

Навчитися знаходити й виправляти типові проблеми доступності: семантичну розмітку, альтернативні тексти, підписи форм, фокус клавіатури та достатній контраст.

Після заняття ви повинні вміти:

- використовувати семантичні елементи замість `div`;
- додавати `alt`, підписи `label` і `aria-label`;
- перевіряти навігацію клавіатурою;
- розраховувати контраст за WCAG;
- користуватися Lighthouse або axe;

## Обладнання та програмне забезпечення

Visual Studio Code, Node.js 20 LTS і новіший (перевірка: `node -v`), npm, сучасний браузер (Chrome або Firefox), Git. Усі приклади працюють локально, без реєстрації в зовнішніх сервісах.

## Теоретична частина

**Семантика.** Елементи `header`, `nav`, `main`, `footer`, `button`, `h1-h6` несуть зміст, який розуміють скрінрідери; `div` та `span` його не мають. **Альтернативний текст** описує інформативне зображення (для декоративного `alt=""`). **Форми**: кожне поле має підпис `label for`. **Клавіатура**: усе інтерактивне має досягатися Tab, мати видимий фокус, а порядок має відповідати візуальному. **Контраст**: звичайний текст потребує співвідношення не менше 4.5:1 (рівень WCAG AA), великий 3:1.

## Хід роботи

### Крок 1. Підготуйте «погану» сторінку

Збережіть як `bad.html` розмітку нижче. Вона містить кілька типових помилок: немає мови, заголовків і підписів, кнопка зроблена з `div`, зображення без опису, світло-сірий текст на білому.

```html
<html>
<head><title>Курси</title></head>
<body>
  <div style="font-size:28px">Курси коледжу</div>
  <div onclick="alert('меню')" style="cursor:pointer">Меню</div>
  <img src="logo.png">
  <p style="color:#aaa">Запишіться на курс уже сьогодні.</p>
  <input type="text" placeholder="Email">
  <div onclick="send()" style="background:#ddd;padding:8px;width:90px">Надіслати</div>
</body>
</html>
```

### Крок 2. Запустіть автоматичну перевірку

Відкрийте сторінку в Chrome, DevTools → Lighthouse → категорія Accessibility → Analyze. Запишіть оцінку й список проблем (відсутній `lang`, контраст, відсутність `alt`, поле без підпису, невідповідні кнопки).

![[attachments/web-pr07-step2.svg|820]]
*Крок 2. Результат Lighthouse до виправлень (приклад). Вигляд терміналу (приклад очікуваного виводу; ваші значення можуть відрізнятися). Джерело: власна ілюстрація автора курсу, для цього конспекту.*

### Крок 3. Перевірте вручну клавіатурою

Натискайте Tab. «Меню» та «Надіслати» зроблені з `div`, тому в порядок фокуса не потрапляють: клавіатурний користувач їх не досягне. Спробуйте також Enter на кнопці. Запишіть, що не вдалося.

> [!tip] Ручна перевірка клавіатурою знаходить проблеми, яких автоматичні інструменти не бачать. Лише приблизно третину проблем можна знайти автоматично.

### Крок 4. Виправте семантику

Додайте `lang="uk"`, структурні елементи, заголовок `h1`, справжні кнопки та посилання, `alt` для логотипа, підпис для поля.

```html
<!doctype html>
<html lang="uk">
<head><meta charset="utf-8"><title>Курси коледжу</title></head>
<body>
  <header>
    <img src="logo.png" alt="Логотип коледжу">
    <nav><button type="button" aria-expanded="false">Меню</button></nav>
  </header>
  <main>
    <h1>Курси коледжу</h1>
    <p>Запишіться на курс уже сьогодні.</p>
    <form>
      <label for="email">Електронна пошта</label>
      <input id="email" type="email" required>
      <button type="submit">Надіслати</button>
    </form>
  </main>
</body>
</html>
```

### Крок 5. Виправте контраст і фокус

Колір `#aaa` на білому дає контраст близько 2.3:1, а потрібно не менше 4.5:1. Замініть на `#595959` (близько 7:1) і не прибирайте контур фокуса. Додайте стилі.

```css
p { color: #595959; }
button { padding: 8px 16px; font-size: 1rem; }
:focus-visible { outline: 3px solid #1a73e8; outline-offset: 2px; }
```

### Крок 6. Повторіть перевірку й порівняйте

Запустіть Lighthouse ще раз. Оцінка має зрости до 95-100. Складіть таблицю «було/стало» для кожної проблеми. Перевірте також збільшення тексту до 200 % і роботу вкладками.

## Завдання для самостійного виконання

Додайте на сторінку модальне вікно: після натискання на кнопку фокус переходить у вікно, клавіша Esc його закриває, а фокус повертається на кнопку. Поясніть, чому без цього скрінрідер-користувач «губиться».

## Індивідуальні завдання (варіанти)

Варіант обирається за порядковим номером у списку групи (якщо номер більший за 5, від нього віднімають 5 до отримання числа від 1 до 5).

| № | Зміни до базового завдання |
|---|---|
| 1 | сторінка запису на курс |
| 2 | сторінка розкладу (таблиця з `th` та `caption`) |
| 3 | форма реєстрації з повідомленнями про помилки (`aria-live`) |
| 4 | навігаційне меню з випадним списком |
| 5 | галерея зображень з описами |

## Типові помилки

- Робити кнопки з `div` без ролі й клавіатурної підтримки.
- Прибирати контур фокуса (`outline: none`) без заміни.
- Покладатися лише на колір (червоний = помилка) без тексту.
- Писати `alt="картинка"` замість змістовного опису.
- Перевіряти лише автоматичним інструментом.

## Контрольні питання

1. Чому семантичні елементи кращі за `div`?
2. Яким має бути мінімальний контраст тексту за WCAG AA?
3. Коли `alt` має бути порожнім?
4. Які проблеми не знаходить автоматична перевірка?

## Вимоги до звіту

Звіт подається без титульного листа й містить: тему й мету; повний перелік виконаних команд або код; скриншоти ключових кроків (із видимим запрошенням терміналу або вікном редактора); відповіді на контрольні питання; висновки.

## Критерії оцінювання

| Оцінка | Що враховується |
|---|---|
| 5 | усі кроки виконано, результати пояснено, самостійне завдання виконано, звіт повний |
| 4 | кроки виконано, є незначні неточності в поясненнях |
| 3 | виконано основну частину, самостійне завдання не виконано |
