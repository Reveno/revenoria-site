# Продуктивність вебсторінок: Lighthouse та Core Web Vitals

> [!abstract] Пов'язана лекція
> [[courses/web-programming/lectures/01-iak-pratsiuie-veb-html-ta-css|Лекція 1. Як працює веб, HTML та CSS]], [[courses/web-programming/lectures/14-git-ci-cd-deploi-ta-ekonomika-vebrozrobky|Лекція 14. Git, CI-CD, деплой та економіка веброзробки]]. Ви виміряєте швидкість завантаження сторінки, знайдете вузькі місця й підтвердите покращення цифрами.

## Навіщо ця робота

Користувачі залишають повільні сайти: кожна додаткова секунда завантаження помітно знижує кількість тих, хто доходить до кінця дії (покупки, реєстрації). Тому швидкість це не «приємний бонус», а частина якості продукту. Щоб покращувати швидкість, її треба виміряти, а не вгадувати: нерідко найбільші втрати дає не те, що здається.

Ви виміряєте «важку» сторінку, застосуєте чотири типові оптимізації (стиснення зображень, відкладене завантаження, `defer` для скриптів, кешування) і перевірите, наскільки покращились показники LCP, CLS та загальний бал.

## Мета

Навчитися вимірювати продуктивність сторінки за допомогою Lighthouse, розуміти метрики Core Web Vitals і застосовувати базові оптимізації.

Після заняття ви повинні вміти:

- запускати Lighthouse і читати звіт;
- пояснювати LCP, CLS, INP;
- оптимізувати зображення;
- відкладати завантаження скриптів і зображень;
- налаштовувати заголовки кешування;

## Обладнання та програмне забезпечення

Visual Studio Code, Node.js 20 LTS і новіший (перевірка: `node -v`), npm, сучасний браузер (Chrome або Firefox), Git. Усі приклади працюють локально, без реєстрації в зовнішніх сервісах.

## Теоретична частина

**Core Web Vitals.** **LCP** (Largest Contentful Paint) час появи найбільшого елемента, добре до 2.5 с. **CLS** (Cumulative Layout Shift) сума «стрибків» розмітки, добре менше 0.1. **INP** (Interaction to Next Paint) затримка реакції на дії користувача, добре до 200 мс. **Типові причини повільності**: великі нестиснені зображення, скрипти, що блокують відображення, відсутність кешу, зайві шрифти. Вимірювати слід кілька разів і в режимі інкогніто, щоб розширення не спотворювали результат.

## Хід роботи

### Крок 1. Підготуйте тестову сторінку

Створіть `index.html` з трьома великими фотографіями (візьміть будь-які знімки 3000×2000 пікселів) і скриптом аналітики без `defer`. Запустіть локальний сервер: `npx serve .`.

```html
<!doctype html>
<html lang="uk">
<head>
  <meta charset="utf-8"><title>Фотогалерея</title>
  <script src="analytics.js"></script>
</head>
<body>
  <h1>Фотогалерея</h1>
  <img src="photo1.jpg"><img src="photo2.jpg"><img src="photo3.jpg">
</body>
</html>
```

### Крок 2. Виміряйте вихідний стан

DevTools → Lighthouse → Performance (режим Desktop або Mobile, однаковий протягом усієї роботи) → Analyze. Запишіть: Performance, LCP, CLS, Total Blocking Time, розмір завантажених даних (вкладка Network). Виконайте вимірювання тричі й візьміть середнє.

![[attachments/web-pr08-step2.svg|820]]
*Крок 2. Вихідні показники (приклад). Вигляд терміналу (приклад очікуваного виводу; ваші значення можуть відрізнятися). Джерело: власна ілюстрація автора курсу, для цього конспекту.*

### Крок 3. Оптимізуйте зображення

Зменште розмір до реально потрібного (наприклад, 1200 пікселів завширшки) і стисніть. Утиліта `squoosh` у браузері або `npx sharp-cli` дає WebP/AVIF у 5-10 разів менше за JPEG. Вкажіть розміри в HTML, щоб браузер резервував місце й не було «стрибків»: `width` та `height`.

```html
<img src="photo1.webp" width="1200" height="800" alt="Берег моря" loading="lazy">
```

### Крок 4. Відкладіть скрипти

Скрипт у `<head>` без атрибутів блокує побудову сторінки. Додайте `defer`: він завантажується паралельно й виконується після розбору документа.

```html
<script src="analytics.js" defer></script>
```

### Крок 5. Налаштуйте кешування

Для статичних файлів із версією в імені (`photo1.v2.webp`) задайте довгий термін кешування. Для `npx serve` використайте `serve.json`; для nginx директиву `expires 1y;`.

```json
{
  "headers": [
    { "source": "**/*.{webp,js,css}",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] }
  ]
}
```

### Крок 6. Виміряйте результат і порівняйте

Повторіть Lighthouse тричі та складіть таблицю «до/після». Поясніть, яка оптимізація дала найбільший внесок.

![[attachments/web-pr08-step6.svg|820]]
*Крок 6. Показники після оптимізації (приклад). Вигляд терміналу (приклад очікуваного виводу; ваші значення можуть відрізнятися). Джерело: власна ілюстрація автора курсу, для цього конспекту.*

## Завдання для самостійного виконання

Додайте адаптивні зображення `srcset`/`sizes`, щоб мобільні пристрої отримували менші файли, і порівняйте обсяг переданих даних у режимі Mobile до й після. Поясніть, чому для різних екранів потрібні різні файли.

## Індивідуальні завдання (варіанти)

Варіант обирається за порядковим номером у списку групи (якщо номер більший за 5, від нього віднімають 5 до отримання числа від 1 до 5).

| № | Зміни до базового завдання |
|---|---|
| 1 | галерея з трьох фотографій |
| 2 | сторінка з вбудованим відео (`preload="none"`) |
| 3 | сторінка з веб-шрифтами (`font-display: swap`) |
| 4 | сторінка зі сторонніми віджетами: порівняти з відкладеним завантаженням |
| 5 | сторінка новин зі списком із 200 елементів (віртуалізація або пагінація) |

## Типові помилки

- Оптимізувати без вимірювань.
- Порівнювати результати різних режимів (Desktop та Mobile).
- Ставити `loading="lazy"` на головне зображення верхньої частини сторінки: це погіршує LCP.
- Не вказувати `width` та `height` у зображень.
- Використовувати довгий кеш для файлів без версії в імені.

## Контрольні питання

1. Що вимірюють LCP, CLS та INP?
2. Чому `defer` пришвидшує показ сторінки?
3. Для яких зображень не слід ставити `loading="lazy"`?
4. Чому вимірювання слід повторювати кілька разів?

## Вимоги до звіту

Звіт подається без титульного листа й містить: тему й мету; повний перелік виконаних команд або код; скриншоти ключових кроків (із видимим запрошенням терміналу або вікном редактора); відповіді на контрольні питання; висновки.

## Критерії оцінювання

| Оцінка | Що враховується |
|---|---|
| 5 | усі кроки виконано, результати пояснено, самостійне завдання виконано, звіт повний |
| 4 | кроки виконано, є незначні неточності в поясненнях |
| 3 | виконано основну частину, самостійне завдання не виконано |
| 2 | результат не отримано, звіт неповний |
