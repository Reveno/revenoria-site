# Git, CI-CD, деплой та економіка веброзробки

> [!abstract] Коротко
> Завершальна лекція курсу: як код, написаний протягом попередніх тринадцяти занять, потрапляє від вашого редактора до реального, працюючого в інтернеті застосунку – через гілки git, pull request, автоматизовані перевірки CI/CD, контейнери Docker і сучасні платформи деплою. А насамкінець – практична економіка веброзробки: скільки коштує хостинг, як оцінювати трудомісткість задач і як влаштоване ціноутворення й монетизація в реальній роботі, включно з фрилансом.

## Навчальні цілі

1. Пояснити, навіщо потрібні гілки git і як побудований типовий процес pull request.
2. Пояснити принцип CI/CD і написати простий workflow для GitHub Actions.
3. Пояснити, яку проблему вирішує Docker, і прочитати простий Dockerfile.
4. Розгорнути застосунок на сучасній платформі деплою з коректним налаштуванням змінних оточення.
5. Оцінювати трудомісткість задач і розуміти базові моделі ціноутворення у фрилансі.

## План лекції

1. Git: гілки та pull request
2. CI/CD: автоматизовані перевірки та розгортання
3. Docker: контейнеризація
4. Деплой: від репозиторію до робочого застосунку
5. Вартість хостингу
6. Оцінка трудомісткості
7. Ціноутворення, монетизація та фріланс

## Git: гілки та pull request

Уявіть, що над одним і тим самим документом одночасно працюють кілька людей – якщо всі редагують ОДИН спільний файл одночасно, правки неминуче накладаються одна на одну, і хтось обов'язково втратить щойно написане. Git вирішує цю проблему для коду через гілки (branches): кожна людина (чи кожна окрема задача) отримує власну, ІЗОЛЬОВАНУ копію історії проєкту, де можна вільно експериментувати й робити проміжні, ще не завершені зміни, не торкаючись основної, стабільної версії коду (зазвичай гілка `main`), якою в цей самий момент, можливо, користуються реальні користувачі застосунку.

```bash
git checkout -b feature/course-search   # створити нову гілку від поточного стану main
# ... робота, коміти ...
git push origin feature/course-search   # відправити гілку на GitHub
```

Коли робота в окремій гілці завершена, її не зливають (merge) у `main` напряму й без жодної перевірки – натомість відкривають pull request (PR): формальний запит «будь ласка, розгляньте мої зміни й, якщо все гаразд, злийте їх у основну гілку». PR показує повний, наочний diff – точно ЩО саме змінилось рядок за рядком, – дозволяє колегам залишити коментарі до конкретних рядків, і слугує тим самим контрольним пунктом якості, про який ми говорили на девʼятій лекції стосовно middleware: жодна зміна не потрапляє в `main`, минаючи цю станцію перевірки.

Пригадайте минулу лекцію: якщо суттєва частина коду в PR згенерована AI-асистентом, гарна практика – прямо зазначити це в описі PR, щоб рецензент знав, з якою пильністю підійти до перевірки саме цих ділянок.

Коли кілька гілок, що змінювали ОДНІ Й ТІ САМІ рядки коду, намагаються злитись докупи, git не завжди може розібратись самостійно, яку саме версію рядка залишити, – виникає конфлікт злиття (merge conflict), і git прямо позначає в файлі ОБИДВА варіанти змін поруч, залишаючи остаточний вибір людині:

```
<<<<<<< HEAD
const pageSize = 20;
=======
const pageSize = 25;
>>>>>>> feature/pagination
```

Це не помилка й не привід панікувати – це git чесно кажучи «я не знаю, яка з двох версій правильна, вирішіть самі», – потрібно вручну обрати правильний варіант (чи скомбінувати обидва), видалити службові маркери `<<<<<<<`/`=======`/`>>>>>>>` і завершити злиття. Що менша й частіша окрема гілка, то менший шанс на серйозний конфлікт, – ще один практичний аргумент на користь декомпозиції великих задач на дрібніші, яку ми детально обговоримо в розділі про оцінку трудомісткості.

## CI/CD: автоматизовані перевірки та розгортання

CI (Continuous Integration, безперервна інтеграція) – практика автоматичного запуску перевірок (тести, лінтер, компіляція TypeScript із четвертої лекції) при КОЖНІЙ зміні, що потрапляє в pull request, – ще до того, як людина-рецензент взагалі гляне на код. CD (Continuous Deployment/Delivery) – продовження того самого принципу: якщо всі автоматичні перевірки пройшли успішно й код злитий у `main`, застосунок автоматично розгортається на реальному сервері, без ручного втручання.

GitHub Actions – поширений інструмент для налаштування саме такого автоматизованого конвеєра,описаного в YAML-файлі:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm install
      - run: npm run lint
      - run: npm test
```

Цей workflow запускається автоматично при кожному pull request у гілку `main`: встановлює Node.js (пригадайте восьму лекцію), встановлює залежності через `npm install`, і послідовно запускає лінтер і тести. Якщо будь-який із цих кроків завершується помилкою, GitHub одразу позначає весь PR червоним хрестиком – прямий, видимий сигнал і автору, і рецензенту, що щось не так, ще до того, як людина витратить час на ручну перевірку коду, який навіть не компілюється.

> [!info] Для допитливих – чому це особливо важливо саме з AI-асистентами
> Пригадайте попередню лекцію про галюцинації: AI-асистент може згенерувати синтаксично бездоганний, але логічно неправильний код. CI не ловить логічні помилки САМІ ПО СОБІ – але якщо в проєкті є тести (написані заздалегідь чи згенеровані разом із кодом і перевірені вручну), CI автоматично й негайно перевіряє, що новий код НЕ ПОРУШИВ очікувану поведінку, – додатковий, автоматизований рівень захисту саме там, де людська пильність могла ослабнути.

## Docker: контейнеризація

Класична проблема командної розробки: «на моєму компʼютері працює» – код, що бездоганно запускається на машині одного розробника, раптом ламається на машині іншого через дрібну відмінність версії Node.js, відсутню системну бібліотеку чи інше значення змінної оточення. Docker вирішує цю проблему буквально тим самим способом, звідки й запозичив свою назву та логотип, – стандартизованим морським контейнером для вантажоперевезень. До появи таких уніфікованих контейнерів кожен вид вантажу вимагав окремого, спеціально пристосованого корабля чи вантажівки; стандартний контейнер, натомість, має однакові розміри й кріплення незалежно від того, ЩО саме всередині, – тому будь-який кран, корабель чи вантажівка, розрахована на стандартний контейнер, може обробити АБСОЛЮТНО будь-який вантаж, не переймаючись його внутрішнім вмістом.

Docker-контейнер запаковує ВЕСЬ застосунок разом із конкретною версією Node.js, усіма системними залежностями й точним набором бібліотек із `package-lock.json` (восьма лекція) в один переносний, самодостатній «ящик», який поводиться АБСОЛЮТНО ІДЕНТИЧНО незалежно від того, на якій фізичній машині його запускають, – на компʼютері розробника, на сервері колеги чи на реальному продакшн-сервері.

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

`FROM node:20-alpine` – базовий «шаблон контейнера» з уже встановленим Node.js конкретної версії; `COPY` й `RUN npm install` копіюють код і встановлюють залежності ВСЕРЕДИНІ цього ізольованого середовища; `CMD` вказує команду, яка запускається при старті контейнера. Готовий, зібраний файл-«креслення» називають образом (image) – так само, як ми говорили про схему як «креслення» на десятій лекції, – а РЕАЛЬНИЙ, ЗАПУЩЕНИЙ на основі цього креслення екземпляр застосунку – контейнером (container). З одного образу можна одночасно запустити скільки завгодно однакових, незалежних контейнерів.

Реальний застосунок рідко складається з ОДНОГО контейнера – пригадайте десяту лекцію: серверу потрібна ще й окрема база даних PostgreSQL. `docker-compose` дозволяє одним файлом описати одразу ДЕКІЛЬКА повʼязаних контейнерів і те, як вони спілкуються між собою:

```yaml
services:
  app:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgresql://user:pass@db:5432/mydb
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: pass
```

Командою `docker compose up` обидва контейнери – застосунок і база даних – запускаються одночасно, уже налаштовані на звʼязок один з одним, і будь-хто в команді відтворює на власній машині ІДЕНТИЧНЕ середовище розробки за один рядок команди, замість того щоб вручну встановлювати PostgreSQL і Node.js потрібних версій самостійно.

## Деплой: від репозиторію до робочого застосунку

Сучасні платформи деплою – Vercel, Railway та подібні – значно спростили процес, що раніше вимагав ручного налаштування сервера. Типовий сценарій: підключаєте свій GitHub-репозиторій до платформи один раз, і надалі кожен `git push` у гілку `main` автоматично запускає збірку й розгортання нової версії застосунку – по суті, той самий принцип CD, про який ми щойно говорили, тільки реалізований самою платформою хостингу, без потреби писати власний YAML-файл.

Vercel історично спеціалізується на фронтенд-застосунках (React, який ми детально вивчали на пʼятій-сьомій лекціях) – статичні файли роздаються через глобальну мережу серверів, розташованих географічно близько до кожного конкретного відвідувача, для максимальної швидкості завантаження. Railway (та подібні платформи) орієнтовані на повноцінні бекенд-застосунки з базою даних – Node.js/Express-сервер із десятої-дванадцятої лекцій разом із PostgreSQL, керовані як окремі, звʼязані між собою сервіси на одній платформі.

Незалежно від конкретної платформи, змінні оточення з девʼятої лекції – `DATABASE_URL`, `JWT_SECRET` – НІКОЛИ не потрапляють у код чи в сам git-репозиторій навіть при деплої: їх налаштовують окремо, безпосередньо в панелі керування платформи хостингу, звідки вони підставляються в `process.env` реального, запущеного сервера, – той самий принцип розділення коду й секретів, лише застосований тепер до реального продакшн-середовища, а не лише до локальної розробки.

## Вартість хостингу

Більшість сучасних платформ пропонують безкоштовний рівень (free tier) із обмеженнями – фіксованою кількістю годин роботи на місяць, обмеженим обсягом бази даних, – достатнім для навчальних і невеликих пет-проєктів, але непридатним для застосунку з реальним, зростаючим навантаженням користувачів. Після вичерпання безкоштовних лімітів платформи переходять на модель pay-as-you-go – оплата за фактично використані ресурси: час роботи сервера, обсяг переданого трафіку, розмір бази даних. Практична порада для невеликого стартового проєкту – почати з безкоштовного рівня чи найдешевшого платного плану, і масштабувати витрати ЛИШЕ разом із реальним зростанням кількості користувачів, а не закладати заздалегідь дорогу інфраструктуру «про запас» під навантаження, якого ще, можливо, ніколи не буде.

## Оцінка трудомісткості

Одна з найважчих практичних навичок для будь-якого розробника-початківця – реалістично оцінити, скільки ЧАСУ забере конкретна задача, перш ніж її ще навіть почали виконувати. Найпоширеніша й найпередбачуваніша помилка тут – систематична недооцінка, і причина цього добре пояснюється аналогією з айсбергом: над водою видно лише саме написання коду – ту частину роботи, яку легко уявити наперед і яку найчастіше й рахують, оцінюючи задачу. Але значно більша частина реальних трудовитрат ховається ПІД водою, поза увагою під час первинної оцінки: тестування, налагодження неочікуваних граничних випадків, читання чужого коду й документації незнайомої бібліотеки, узгодження вимог із замовником, який сам ще не до кінця сформулював, чого хоче.

Практичний прийом, що частково компенсує цю схильність, – той самий принцип декомпозиції, який ми застосовували протягом усього курсу: розбити велику, нечітку задачу («зроби сторінку профілю») на дрібніші, конкретніші підзадачі («форма редагування даних», «завантаження аватарки», «валідація полів»), кожну з яких значно легше й точніше оцінити окремо, ніж спробувати одразу оцінити задачу цілком одним числом. Сума точніших дрібних оцінок майже завжди виявляється надійнішою за одну загальну, інтуїтивну оцінку всієї задачі одразу.

Багато команд замість точних годин на кожну дрібну підзадачу використовують відносне оцінювання за категоріями розміру («T-shirt sizing»: S/M/L/XL) чи умовними «сторі-поінтами» – це свідомо визнає, що людина зазвичай значно ТОЧНІШЕ порівнює дві задачі одна з одною («ця складніша за ту приблизно вдвічі»), ніж називає абсолютну кількість годин наперед. І навіть після ретельної декомпозиції та відносного оцінювання досвідчені розробники все одно закладають буфер на непередбачені обставини – типово 20-30% зверху від суми оцінок – саме через «підводну частину айсберга», яку неможливо повністю передбачити наперед, хоч би як ретельно не декомпозувати задачу.

## Ціноутворення, монетизація та фріланс

Розберемо, як усе вивчене протягом курсу конвертується в реальну оплачувану роботу. Фрилансери й агенції найчастіше обирають між кількома моделями оплати. Погодинна оплата (hourly rate) – простий, передбачуваний спосіб для обох сторін, але створює дивний, часто небажаний стимул: розробник, що працює швидше й ефективніше, формально заробляє МЕНШЕ за той самий обсяг реально виконаної роботи. Фіксована ціна за проєкт (fixed price) усуває цей перекос, але перекладає весь ризик недооцінки трудомісткості (яку ми щойно детально розглянули) на самого виконавця – якщо задача виявиться складнішою за первинну оцінку, різницю доведеться покрити власним, неоплаченим часом. Ціноутворення на основі цінності (value-based pricing) – найскладніший, але часто найвигідніший підхід: ціна визначається не витраченим часом, а тим, СКІЛЬКИ реальної цінності (заощаджені гроші, новий потік доходу) застосунок принесе замовнику.

Для власних продуктів (SaaS – Software as a Service) типові моделі монетизації включають підписку (фіксована щомісячна плата за доступ), freemium (базова функціональність безкоштовна, розширені можливості – платні) та одноразову покупку. Вибір моделі напряму впливає на технічні рішення, які ми детально розглядали раніше в курсі, – наприклад, підпискова модель вимагає надійної системи ролей і перевірки прав доступу, дуже схожої на RBAC, детально розглянутий на дванадцятій лекції, тільки тепер роль визначає не адміністративні права, а рівень платного тарифу конкретного користувача.

> [!info] Для допитливих – практичні поради для старту у фрилансі
> Завжди фіксуйте обсяг роботи (scope) письмово, до початку виконання, – усна домовленість «зроби мені сайт» майже гарантовано призводить до «розповзання обсягу» (scope creep), коли замовник поступово додає нові вимоги, вважаючи їх «дрібницею», що «і так малась на увазі». Простий письмовий договір чи бодай детальний лист-погодження зі списком конкретних робіт, ціною й термінами захищає обидві сторони й дає підставу ввічливо, але твердо сказати «це вже поза початковим обсягом, обговорімо додаткову оплату», коли вимоги справді розповзаються. Портфоліо з кількох реальних, завершених проєктів – навіть невеликих навчальних, подібних до тих, що ви створювали протягом цього курсу, – важливіше для перших замовлень, ніж формальний диплом чи сертифікат. І, нарешті, чесна комунікація про реалістичні терміни (з урахуванням «підводної частини айсберга» з попереднього розділу) будує довшу й довірливішу репутацію, ніж обіцянки нереалістично швидких термінів заради першого враження.

Тут, по суті, замикається коло всього курсу: щоб реалістично оцінити задачу «форма реєстрації з валідацією» чи «сторінка каталогу з пагінацією», потрібно вже впевнено орієнтуватись у HTML/CSS з першої лекції, JavaScript із другої-третьої, React із пʼятої-сьомої, Express і базах даних із восьмої-десятої – саме тому цей курс і був побудований послідовно, від фундаменту до практичної економіки роботи над реальними застосунками.

## Завдання на занятті (20-25 хв)

1. Створіть нову гілку в навчальному репозиторії курсу, внесіть невелику зміну, відкрийте pull request із описом змін.
2. Напишіть простий workflow GitHub Actions, що запускає `npm test` при кожному pull request у `main`.
3. Розбийте задачу «додати сторінку каталогу курсів із фільтрацією та пагінацією» (пригадайте одинадцяту лекцію) на пʼять-сім дрібніших підзадач і оцініть кожну окремо в годинах.

> [!question] Перевірте себе
> - Чому пряма робота в спільній гілці `main` без окремих гілок і pull request небезпечна для командного проєкту?
> - Яку роль відіграє pull request як «контрольний пункт», подібний до middleware з девʼятої лекції?
> - Що означають маркери `<<<<<<<`/`=======`/`>>>>>>>` при конфлікті злиття, і чому це не помилка git?
> - Чим Continuous Integration відрізняється від Continuous Deployment?
> - Яку саме проблему («на моєму компʼютері працює») вирішує Docker, і чим образ (image) відрізняється від контейнера (container)?
> - Навіщо `docker-compose` описує одразу кілька контейнерів (застосунок і базу даних) в одному файлі?
> - Чому змінні оточення на платформі деплою налаштовують ОКРЕМО від коду навіть під час автоматичного розгортання?
> - Чому оцінка трудомісткості за принципом «айсберга» зазвичай точніша за декомпозицією задачі, ніж одним загальним числом?
> - У чому недолік погодинної оплати з погляду стимулів розробника, і як фіксована ціна за проєкт перекладає ризик на іншу сторону?
> - Чим модель монетизації SaaS-продукту (підписка/freemium) технічно повʼязана з RBAC із дванадцятої лекції?
