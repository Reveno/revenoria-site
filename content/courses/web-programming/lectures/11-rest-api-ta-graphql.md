# REST API та GraphQL

> [!abstract] Коротко
> Формалізуємо принципи REST, за якими ми фактично вже проєктували маршрути на восьмій-девʼятій лекціях, і додаємо практичні деталі повноцінного API: версіонування, пагінацію великих списків даних та документування через OpenAPI. Насамкінець — коротке знайомство з GraphQL як альтернативним підходом, що вирішує проблему над- і недозавантаження даних, характерну для REST.

## Принципи REST

Пригадайте найпершу лекцію курсу: HTTP-методи, статус-коди, клієнт-серверна модель без збереження стану. REST (Representational State Transfer) — це не окрема технологія чи бібліотека, а НАБІР архітектурних принципів, які кажуть, ЯК саме правильно використовувати ці вже знайомі можливості HTTP для побудови узгодженого, передбачуваного API. Фактично на восьмій і девʼятій лекціях ми вже писали REST-подібні маршрути, здебільшого інтуїтивно, — тепер розберемо, чому це працює саме так, формальніше.

Перший принцип — ресурси ідентифікуються через URL. «Ресурс» у REST — це будь-яка сутність, з якою працює застосунок: конкретний курс, список усіх курсів, конкретний користувач. Кожен такий ресурс має свою УНІКАЛЬНУ адресу — `/courses`, `/courses/42` — і ця адреса описує ЩО це за дані, а не ЩО з ними зробити: сама дія (отримати, створити, видалити) визначається не URL, а HTTP-МЕТОДОМ із таблиці першої лекції.

> [!warning] Типова помилка
> Проєктувати URL-адреси як дієслова замість іменників — `/getCourses`, `/deleteCourse?id=5` — це поширена помилка тих, хто щойно переходить від звичайних функцій до REST-мислення. Правильний REST-стиль: `GET /courses` (отримати список), `DELETE /courses/5` (видалити конкретний курс) — сама дія вже закодована в HTTP-методі, тому дублювати її ще й у назві URL зайве й суперечить принципу REST.

Другий принцип — той самий stateless, про який ми детально говорили на найпершій лекції: сервер не памʼятає нічого про попередні запити того самого клієнта між окремими зверненнями. Кожен запит до REST API повинен містити АБСОЛЮТНО ВСЮ інформацію, потрібну для його обробки, — включно з токеном авторизації (детально розберемо на наступній лекції), а не покладатися на те, що сервер «памʼятає» вас із попереднього запиту.

Третій принцип — уніфікований інтерфейс: однакові HTTP-методи означають однакові дії для БУДЬ-ЯКОГО ресурсу в усьому API, без винятків. `GET` завжди читає, ніколи нічого не змінюючи на сервері; `POST` завжди створює; `DELETE` завжди видаляє — і ця узгодженість напряму повʼязана з CRUD-операціями, які ми детально розбирали на попередній лекції для Prisma: `GET` відповідає `findMany`/`findUnique`, `POST` — `create`, `PUT`/`PATCH` — `update`, `DELETE` — `delete`. REST-маршрут — це, по суті, тонкий HTTP-«фасад» над тими самими операціями з базою даних.

> [!info] Для допитливих — рівні зрілості REST (модель Річардсона)
> Не всі API, що називають себе «REST», однаково послідовно застосовують ці принципи. Модель зрілості Річардсона виділяє кілька рівнів: рівень 0 — один-єдиний URL для всього, дія передається в тілі запиту (по суті, це вже не REST, а RPC поверх HTTP); рівень 1 — окремі URL для різних ресурсів, але без урахування HTTP-методів; рівень 2 — те, що ми детально розглядаємо в цій лекції: ресурси через URL, дії через методи, коректні статус-коди; рівень 3 додає HATEOAS (Hypermedia as the Engine of Application State) — відповідь API сама містить посилання на повʼязані дії, доступні для цього ресурсу (наприклад, посилання на скасування щойно створеного замовлення прямо у відповіді на його створення), так що клієнту не потрібно наперед «знати» всю структуру API. Рівень 3 на практиці зустрічається рідко через додану складність — переважна більшість реальних API, включно з тими, що ми будемо писати, зупиняються на рівні 2.

## Проєктування URL-адрес і статус-кодів

Практичні конвенції REST, вироблені спільнотою за роки використання, варто засвоїти як типовий стандарт, навіть попри те, що формально REST їх жорстко не диктує:

| Дія | Метод і шлях |
|---|---|
| Список усіх курсів | `GET /courses` |
| Один конкретний курс | `GET /courses/42` |
| Створити курс | `POST /courses` |
| Оновити курс повністю | `PUT /courses/42` |
| Оновити курс частково | `PATCH /courses/42` |
| Видалити курс | `DELETE /courses/42` |
| Лекції конкретного курсу | `GET /courses/42/lectures` |

Останній рядок демонструє вкладені ресурси (nested resources) — лекції природно «належать» конкретному курсу, тому й адреса відображає цю ієрархію, замінюючи окремий, менш очевидний `GET /lectures?courseId=42`. Обидва варіанти технічно робочі, але вкладена форма читається природніше й одразу видно звʼязок «один-до-багатьох» із попередньої лекції прямо в самій структурі URL.

Статус-коди варто підбирати ТОЧНО під конкретну ситуацію, а не обмежуватись лише `200` та `404`, — пригадайте повну таблицю категорій із першої лекції: `201 Created` для успішного `POST`, `204 No Content` для успішного `DELETE`, коли повертати вже нічого (сам ресурс видалено, тіла відповіді немає), `400 Bad Request` для некоректних вхідних даних (та сама валідація middleware з девʼятої лекції), `401 Unauthorized`/`403 Forbidden` для проблем з авторизацією (детально на наступній лекції). Точний, змістовний статус-код — це частина «контракту» API: клієнт, отримавши `422` замість узагальненого `400`, може одразу програмно розрізнити «дані некоректні за форматом» від «дані коректні за форматом, але суперечать бізнес-правилу» — без потреби парсити текст повідомлення про помилку.

Окрім самого шляху, REST-ендпоінти для СПИСКІВ часто приймають додаткові query-параметри для фільтрації й сортування — той самий `req.query`, який ми детально розглядали на восьмій лекції:

```
GET /courses?module=02-frontend&sort=title&order=asc
```

```js
app.get("/courses", async (req, res) => {
  const { module, sort = "id", order = "asc" } = req.query;

  const courses = await prisma.course.findMany({
    where: module ? { module } : undefined, // фільтр застосовується, лише якщо параметр переданий
    orderBy: { [sort]: order }               // обчислюваний ключ обʼєкта з другої лекції
  });

  res.json(courses);
});
```

Зверніть увагу на `where: module ? { module } : undefined` — якщо клієнт не передав параметр `module` узагалі, фільтр просто не застосовується, і повертаються ВСІ курси; такий підхід дозволяє одному й тому самому маршруту обслуговувати і запит «дай усі курси», і запит «дай лише курси конкретного модуля», без дублювання логіки в окремих ендпоінтах.

## Версіонування API

Уявіть, що ваш API вже використовують кілька різних клієнтів — мобільний застосунок, сайт, застосунок партнера, — і вам потрібно змінити формат відповіді одного з ендпоінтів так, що стара форма даних перестане працювати з новим кодом. Якщо просто змінити наявний ендпоінт «на місці», усі клієнти, які досі очікують СТАРИЙ формат, миттєво зламаються — а оновити одночасно ВСІХ клієнтів, особливо мобільні застосунки, які користувачі оновлюють у власному темпі, часто просто неможливо. Це та сама ситуація з «заселеним будинком», яку ми обговорювали на попередній лекції про міграції бази даних: не можна просто знести й перебудувати те, чим уже активно користуються.

Версіонування API вирішує це, дозволяючи СТАРІЙ і НОВІЙ версії існувати ОДНОЧАСНО, паралельно, доки всі клієнти не перейдуть на нову за власним графіком. Найпоширеніший спосіб — версія прямо в URL:

```
GET /api/v1/courses   — стара форма відповіді, підтримується для наявних клієнтів
GET /api/v2/courses   — нова форма відповіді
```

Обидва маршрути можуть навіть викликати ту саму бізнес-логіку й сервісний шар усередині, лише по-різному форматуючи фінальну відповідь клієнту, — версіонується САМЕ ПУБЛІЧНИЙ контракт API, а не обовʼязково вся внутрішня реалізація.

Коли стару версію нарешті планують повністю прибрати, про це заздалегідь попереджають клієнтів — наприклад, через заголовок відповіді `Deprecation` чи `Sunset`, що вказує орієнтовну дату відключення старої версії, — щоб команди, які досі користуються `/api/v1/`, мали достатньо часу спокійно перейти на нову версію, а не дізналися про поломку вже постфактум, коли стару версію вимкнули без попередження.

## Пагінація великих списків

Пригадайте попередню лекцію: `prisma.course.findMany()` без жодних обмежень поверне АБСОЛЮТНО ВСІ рядки таблиці. Для навчальної таблиці з десятком курсів це непомітно, але уявіть таблицю з мільйоном записів — надсилати клієнту мільйон рядків JSON одним запитом украй непрактично: повільно, витрачає багато памʼяті і на сервері, і в браузері клієнта, і переважна більшість цих даних користувачеві прямо зараз узагалі не потрібна. Уявіть бібліотеку, яка видає читачеві НЕ весь каталог книг одразу стосом до стелі, а невелику, керовану пачку — скажімо, 20 книг за раз, — і окрему позначку-закладку, за якою можна попросити наступну пачку, коли перша буде опрацьована.

```js
const page = Number(req.query.page) || 1;
const pageSize = 20;

const courses = await prisma.course.findMany({
  skip: (page - 1) * pageSize, // пропустити попередні сторінки
  take: pageSize                // взяти лише pageSize записів
});
```

Це offset-пагінація — найпростіший варіант, де клієнт запитує «сторінку номер N», а сервер обчислює, скільки записів пропустити. Вона зрозуміла й проста, але має практичну ваду при ЧАСТІЙ зміні даних: якщо між запитом сторінки 1 і сторінки 2 хтось додав новий запис на початок списку, усі наступні записи «зсуваються», і користувач ризикує побачити один запис двічі або пропустити інший. Альтернатива — курсорна пагінація (cursor-based), де замість номера сторінки клієнт передає ІДЕНТИФІКАТОР останнього побаченого запису («покажи записи ПІСЛЯ цього конкретного `id`»), що лишається стабільним незалежно від того, скільки нових записів додали на початок списку:

```js
const lastId = Number(req.query.after) || 0;

const courses = await prisma.course.findMany({
  where: { id: { gt: lastId } }, // лише записи з id більшим за останній побачений
  take: 20,
  orderBy: { id: "asc" }
});
```

В обох варіантах клієнту зазвичай корисно повернути не лише сам масив даних, а й невеликі метадані про пагінацію — інакше фронтенд (пригадайте списки з ключами на пʼятій лекції) не зможе коректно намалювати кнопки «наступна сторінка» чи зрозуміти, чи є ще дані для довантаження:

```js
const totalCount = await prisma.course.count();

res.json({
  data: courses,
  pagination: { page, pageSize, totalCount, hasNextPage: page * pageSize < totalCount }
});
```

## OpenAPI: документування контракту API

Коли над одним API працює команда — одні пишуть сервер, інші пишуть фронтенд, треті інтегрують сторонній сервіс, — усім їм потрібен ЄДИНИЙ, точний опис того, які ендпоінти існують, які параметри приймають, і яку саме форму відповіді повертають. OpenAPI (раніше відомий як Swagger) — стандартний, машиночитний формат для опису такого контракту API, дуже схожий за духом на TypeScript-інтерфейси з четвертої лекції, тільки описує не окремий обʼєкт усередині коду, а всю ПОВЕРХНЮ API назовні:

```yaml
paths:
  /courses/{id}:
    get:
      summary: Отримати курс за id
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        "200":
          description: Курс знайдено
          content:
            application/json:
              schema:
                type: object
                properties:
                  id: { type: integer }
                  title: { type: string }
        "404":
          description: Курс не знайдено
```

Практична вигода такого формального опису подвійна. По-перше, з нього автоматично генерують інтерактивну документацію (Swagger UI) — сторінку, де будь-який розробник, навіть не знайомий із внутрішньою реалізацією сервера, бачить повний список ендпоінтів і може одразу спробувати надіслати тестовий запит просто з браузера. По-друге, з тієї самої специфікації можна автоматично згенерувати TypeScript-типи для клієнта — фронтенд одразу отримує точні інтерфейси відповіді API, синхронізовані з реальним контрактом сервера, тим самим принципом, яким Prisma на попередній лекції генерувала типи із схеми бази даних.

## GraphQL: інший підхід

Насамкінець розглянемо принципово інший підхід до побудови API, який варто знати, навіть якщо в цьому курсі ми надалі користуватимемось REST. Пригадайте таблицю проєктування URL вище: щоб отримати курс РАЗОМ із його лекціями, довелося окремо продумувати `include`, як на попередній лекції з Prisma, — і REST-ендпоінт зазвичай повертає ФІКСОВАНИЙ, наперед визначений набір полів, однаковий для АБСОЛЮТНО ВСІХ клієнтів, незалежно від того, що конкретному клієнту реально потрібно.

Уявіть комплексний обід у їдальні, де порція завжди фіксована: суп, друга страва, гарнір, компот — усе разом, одним чеком. Якщо вам потрібен ЛИШЕ суп, ви все одно отримуєте (і, можливо, платите за) весь комплекс — це називають надлишковим завантаженням (over-fetching). А якщо вам, навпаки, потрібні ЩЕ й хлібні палички, яких немає в комплексі, доведеться робити ДРУГЕ окреме замовлення — недостатнє завантаження (under-fetching), що змушує клієнта робити кілька окремих REST-запитів поспіль, щоб зібрати всі потрібні дані для однієї сторінки інтерфейсу.

GraphQL вирішує обидві проблеми одразу, дозволяючи КЛІЄНТУ самому точно вказати, ЯКІ САМЕ поля йому потрібні в конкретному запиті, — це схоже на меню «збери свою страву», де клієнт сам обирає рівно ті інгредієнти, які хоче, не більше й не менше:

```graphql
query {
  course(id: 42) {
    title
    lectures {
      title
    }
  }
}
```

Цей запит — не URL і не окремий ендпоінт: замість десятків окремих REST-маршрутів GraphQL здебільшого використовує ОДИН-ЄДИНИЙ ендпоінт (найчастіше `POST /graphql`), а сам ЗАПИТ, подібний до наведеного вище, надсилають у тілі HTTP-запиту, і сервер повертає РІВНО ТІ поля, які були запитані, — жодних зайвих даних, жодних відсутніх полів, що вимагали б другого запиту.

На боці сервера кожному полю відповідає функція-резолвер (resolver), що відповідає за отримання саме цих даних, — і тут природно застосовується все, що ми вже знаємо про Prisma з попередньої лекції:

```js
const resolvers = {
  Query: {
    course: async (parent, args) => {
      return prisma.course.findUnique({
        where: { id: args.id },
        include: { lectures: true }
      });
    }
  }
};
```

Читання даних у GraphQL називають запитом (query), а запис-зміну — мутацією (mutation), окремим типом операції з власним, явно позначеним ключовим словом, щоб одразу було видно, чи операція просто читає дані, чи змінює їх на сервері (той самий поділ на `GET` проти `POST`/`PUT`/`DELETE` з REST, тільки виражений інакше):

```graphql
mutation {
  createCourse(title: "Нова дисципліна", module: "01-osnovy") {
    id
    title
  }
}
```

> [!info] Для допитливих — проблема N+1
> Гнучкість GraphQL має і зворотний бік: якщо резолвер курсу наївно, у циклі, окремо запитує лекції для КОЖНОГО курсу зі списку, замість одного ефективного `include`-запиту, як ми робили в Prisma на попередній лекції, це виллється в N+1 окремих звернень до бази даних — одне для списку курсів і ще по одному на кожен курс окремо, замість одного обʼєднаного запиту. Цю проблему на практиці вирішують спеціальними бібліотеками (наприклад, DataLoader), що автоматично «збирають» окремі запити резолверів за короткий проміжок часу в один пакетний запит до бази.

> [!info] Для допитливих — REST чи GraphQL?
> REST простіший для старту, добре кешується стандартними HTTP-механізмами з першої лекції (`Cache-Control`, `ETag`) і залишається типовим стандартом для більшості API. GraphQL найбільше виправданий, коли клієнтів багато й РІЗНИХ (мобільний застосунок, вебсайт, партнерська інтеграція), кожен потребує різного набору полів, а над- і недозавантаження даних у REST стає відчутною проблемою продуктивності. У цьому курсі ми й надалі користуватимемось REST як основним підходом.
