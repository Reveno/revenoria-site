# React – компоненти, JSX, стан і пропси

> [!abstract] Коротко
> React – бібліотека для декларативної побудови інтерфейсу з окремих, повторно використовуваних компонентів. Розглянемо JSX, компонентний підхід, передачу даних через пропси, умовний рендер, списки з ключами та найпростіший стан через `useState` – фундамент, на якому наступна лекція побудує повноцінну роботу з хуками.

## Навчальні цілі

1. Пояснити, чим декларативний підхід React відрізняється від ручної роботи з DOM із третьої лекції.
2. Писати JSX і розуміти, у що він перетворюється під час компіляції.
3. Створювати компоненти, типізувати й передавати пропси, використовувати `children`.
4. Реалізовувати умовний рендер і рендер списків із правильними ключами.
5. Додавати найпростіший локальний стан через `useState`.

## План лекції

1. Навіщо React: декларативний підхід проти імперативного
2. JSX: синтаксис і компіляція
3. Компоненти та пропси
4. Умовний рендер
5. Списки та ключі
6. Перший стан: `useState`

## Навіщо React: декларативний підхід проти імперативного

Пригадайте третю лекцію, де ми навчились додавати елементи на сторінку вручну: `document.createElement`, `element.textContent = ...`, `parent.appendChild(element)`. Для однієї картки товару це виглядало цілком розумно. Але уявіть тепер повноцінний інтернет-магазин: список із сотні товарів, де кожен потрібно й показати, і оновити ціну після зміни валюти, і підсвітити, якщо товару немає в наявності, і прибрати зі списку, якщо покупець видалив його з обраного, – і все це має відбуватись синхронно, без єдиного пропущеного оновлення, поки користувач клікає, фільтрує й гортає сторінку дедалі швидше. Писати це вручну, через послідовність команд «знайди цей елемент, зміни в нього оцей клас, а тепер онов і той текст», – це схоже на те, як диктувати таксисту КОЖЕН окремий поворот на маршруті: «зараз наліво, тепер прямо два квартали, тепер направо біля аптеки» – стомливо, а головне – крихко: досить один раз забути сказати про якийсь поворот, і водій просто заблукає.

React пропонує зовсім інший спосіб мислення – декларативний. Замість детальних покрокових інструкцій «як саме» змінити DOM, ви просто описуєте, ЯК МАЄ ВИГЛЯДАТИ інтерфейс ЗАРАЗ, для поточних даних, – а вже сам React бере на себе відповідальність порівняти цей опис із тим, що реально є на екрані, і застосувати рівно ті зміни в DOM, які фактично потрібні. Це вже схоже не на покрокову диктовку поворотів, а на те, щоб просто назвати таксисту кінцеву адресу – «мені потрібно опинитись ось тут» – і дозволити водієві (React) самому розібратись, яким маршрутом туди доїхати найефективніше, зважаючи на те, де машина знаходиться зараз.

> [!definition] Декларативний підхід
> Опис БАЖАНОГО РЕЗУЛЬТАТУ («інтерфейс для цих даних має виглядати так») замість послідовності команд, ЯК ЦЬОГО РЕЗУЛЬТАТУ досягти. React-компонент – це, по суті, функція, яка на основі поточних даних ОПИСУЄ, як має виглядати інтерфейс, а не змінює DOM напряму командами на кшталт `appendChild`.

Порівняймо це на конкретному прикладі – лічильник кліків, який ми ще напишемо детально трохи пізніше в цій лекції. Ось як виглядав би імперативний підхід, яким ми користувались на третій лекції:

```js
let count = 0;
const countLabel = document.querySelector(".count-label");
const button = document.querySelector(".increment-button");

button.addEventListener("click", () => {
  count = count + 1;
  countLabel.textContent = `Кліків: ${count}`; // не забути оновити ЦЕЙ конкретний елемент вручну
});
```

Тут програміст особисто відповідає за КОЖЕН крок синхронізації даних із тим, що реально показано на екрані: збільшити число, знайти потрібний DOM-вузол, оновити саме його текст. У маленькому прикладі це виглядає безпечно, але уявіть, що те саме число `count` впливає одразу на пʼять різних місць інтерфейсу – підпис лічильника, бейджик у шапці сайту, стан кнопки (заблокована, якщо ліміт вичерпано), – і про кожне з цих пʼяти місць доведеться памʼятати окремо, вручну, у кожному місці коду, де `count` змінюється. Забути оновити хоча б одне з них – і інтерфейс почне показувати дані, які розійшлися з реальним станом програми. У декларативному варіанті React ви просто один раз описуєте, як компонент має виглядати ЗАЛЕЖНО ВІД `count`, – і REACT, а не ви особисто, гарантує, що всі ці місця завжди синхронізовані з актуальним значенням, скільки б їх не було.

Механізм, завдяки якому React ефективно знаходить, ЩО САМЕ реально змінилось, називають узгодженням (reconciliation). Уявіть, що ви порівнюєте дві версії того самого документа через режим «відстеження змін» у текстовому редакторі: замість того щоб видаляти весь старий документ і друкувати новий з нуля, редактор підсвічує лише конкретні рядки, які реально відрізняються. React робить приблизно те саме: він тримає в памʼяті «знімок» того, як інтерфейс мав виглядати минулого разу, порівнює його з новим описом, який щойно повернула ваша функція-компонент, і вносить у реальний DOM лише ТОЧКОВІ зміни там, де щось справді відрізняється, – замість того щоб щоразу знищувати й перебудовувати весь DOM заново, що було б неприпустимо повільно.

## JSX: синтаксис і компіляція

Тепер про те, ЯК саме описують цей «бажаний вигляд» інтерфейсу на практиці. React використовує розширення синтаксису JavaScript, яке називається JSX – і виглядає воно на перший погляд як HTML, вставлений прямо всередину JavaScript-коду:

```jsx
function Greeting() {
  return <h1>Привіт, студенте!</h1>;
}
```

Але це не HTML у прямому сенсі – браузер, як і у випадку з TypeScript із попередньої лекції, НЕ вміє виконувати JSX напряму. Спеціальний компілятор (найчастіше Babel) «перекладає» JSX у звичайні виклики функцій JavaScript ще до того, як код потрапить у браузер:

```jsx
// те, що ви пишете
const element = <h1 className="title">Привіт</h1>;

// у що це компілюється насправді
const element = React.createElement("h1", { className: "title" }, "Привіт");
```

Це та сама ідея «перекладу перед виконанням», яку ми детально розбирали на попередній лекції про TypeScript, тільки цього разу перекладається не система типів, а сам синтаксис розмітки. І саме тому JSX накладає кілька формальних обмежень, яких немає в звичайному HTML, – вони випливають напряму з того, що під капотом це насправді виклики JavaScript-функцій, а не окрема мова розмітки:

- Атрибути пишуться в camelCase, а не kebab-case: `className` замість `class` (слово `class` зарезервоване в JavaScript як ключове слово для класів), `onClick` замість `onclick`.
- Будь-який JavaScript-вираз вставляється у фігурні дужки `{ ... }` прямо всередині розмітки – змінна, виклик функції, арифметика.
- JSX-розмітка, яку повертає компонент, має мати РІВНО ОДИН кореневий елемент – не можна повернути два сусідні теги на одному рівні без спільного «обгортаючого» елемента, так само як функція не може мати два незалежних `return` одночасно.

```jsx
function UserCard({ name, age }) {
  return (
    <div className="card">
      <h2>{name}</h2>
      <p>Вік: {age}</p>
    </div>
  );
}
```

> [!warning] Типова помилка
> Спроба повернути два елементи поруч без спільного контейнера – `return <h1>...</h1><p>...</p>;` – призведе до помилки компіляції, адже це буквально означало б повернути «два корені» одним `return`. Якщо додавати зайвий `<div>` навколо не хочеться (наприклад, він порушить CSS Grid/Flexbox-розмітку батька з першої лекції), React надає спеціальний тег `<>...</>` (Fragment) – він групує елементи для JSX, але не додає жодного зайвого вузла в реальний DOM.

Кілька практичних дрібниць синтаксису JSX, які стануть у пригоді буквально одразу. По-перше, значення `false`, `null`, `undefined`, вставлені у фігурні дужки `{ ... }`, React просто НЕ рендерить – на екрані не зʼявляється нічого, і жодної помилки це не викликає, – саме на цій властивості й побудований умовний рендер через `&&`, який ми детально розглянемо трохи далі. По-друге, інлайн-стилі в JSX задають не рядком, як у звичайному атрибуті `style="color: red"` у HTML, а обʼєктом JavaScript із властивостями в camelCase:

```jsx
<p style={{ color: "red", fontSize: "16px" }}>Текст</p>
```

Тут насправді ДВІ пари фігурних дужок: зовнішня – це вже знайома вставка JavaScript-виразу в JSX, а внутрішня – сам літерал обʼєкта з другої лекції, той самий синтаксис `{ key: value }`, який ми там детально розбирали. По-третє, коментарі всередині JSX-розмітки (не в звичайному JS-коді навколо, а саме всередині тегів) теж пишуть через фігурні дужки: `{/* це коментар */}` – звичний `//` тут не спрацює, бо синтаксично ви перебуваєте всередині розмітки, а не звичайного JS-виразу.

## Компоненти та пропси

Компонент – це, по суті, іменована, самодостатня «форма» для шматка інтерфейсу, яку можна повторно використовувати скільки завгодно разів, підставляючи щоразу інші дані, – приблизно як модульні меблі, з яких можна зібрати шафу будь-якого розміру з одних і тих самих стандартних секцій, або як формочка для печива: одна формочка, а печива з неї можна витиснути скільки завгодно, і кожне буде мати ту саму форму. У сучасному React компонент найчастіше пишуть як звичайну JavaScript-функцію, що повертає JSX:

```jsx
function ProductCard(props) {
  return (
    <div className="card">
      <h3>{props.name}</h3>
      <p>{props.price} грн</p>
    </div>
  );
}

// використання компонента, немов звичайного HTML-тега
<ProductCard name="Ноутбук" price={25000} />
<ProductCard name="Мишка" price={350} />
```

Дані, які передають у компонент ЗЗОВНІ, при його використанні, називають пропсами (props, скорочено від properties) – вони приходять компоненту єдиним обʼєктом-аргументом (у прикладі вище – `props`), схожим на звичайний параметр функції з другої лекції. Насправді компонент і Є звичайною функцією, тож тут можна одразу застосувати деструктуризацію, яку ми детально розбирали на другій лекції, – замість того щоб щоразу писати `props.name`, `props.price`, можна дістати потрібні поля прямо в параметрах функції:

```jsx
function ProductCard({ name, price }) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{price} грн</p>
    </div>
  );
}
```

Дуже важлива властивість пропсів, яку варто запамʼятати одразу й міцно: вони ЛИШЕ ДЛЯ ЧИТАННЯ (read-only). Компонент отримує пропси й може на їхній основі щось відобразити, але не має права змінювати сам обʼєкт `props` зсередини – це такий самий принцип «одностороннього потоку даних», який ми обговорювали на другій лекції стосовно `const` та spread: дані рухаються ЗВЕРХУ ВНИЗ, від батьківського компонента до дочірнього, і жодна дитина не може «крикнути вгору» й напряму змінити те, що передав їй батько. Якщо дочірньому компоненту потрібно якось «повідомити» батьківський про зміну, це роблять не мутацією пропсів, а через передачу функції-колбека самим пропсом – але детально керування станом і передача подій між компонентами – тема наступної лекції.

Типізувати пропси через TypeScript, яким ми озброїлись на попередній лекції, – стандартна практика в сучасних React-проєктах, і робиться це через уже знайомий інтерфейс:

```tsx
interface ProductCardProps {
  name: string;
  price: number;
  discount?: number; // необовʼязковий проп
}

function ProductCard({ name, price, discount }: ProductCardProps) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{discount ? price * (1 - discount) : price} грн</p>
    </div>
  );
}
```

Компоненти можна вкладати один в одного, будуючи інтерфейс з дедалі більших блоків, зібраних із дрібніших, – так само як зі стандартних модульних секцій меблів збирають цілу шафу, а не одну полицю:

```jsx
function ProductList({ products }) {
  return (
    <div className="cards">
      {products.map(product => (
        <ProductCard key={product.id} name={product.name} price={product.price} />
      ))}
    </div>
  );
}
```

(Про `key` в цьому прикладі – трохи згодом, у розділі про списки; поки що просто зверніть увагу на сам принцип композиції – `ProductList` не малює картки самостійно, а делегує це вже готовому компоненту `ProductCard`, викликаючи його стільки разів, скільки товарів у списку.)

Окремо варто згадати спеціальний проп `children` – він автоматично містить усе, що було вкладено МІЖ відкривальним і закривальним тегом компонента при його використанні, подібно до того, як вкладений вміст HTML-тега (`<div>ось цей текст</div>`) є «вмістом» цього тега:

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

// використання
<Card>
  <h3>Заголовок</h3>
  <p>Довільний вміст усередині</p>
</Card>
```

Це надзвичайно потужний патерн для «обгорткових» компонентів – модальних вікон, карток, панелей – які самі не знають наперед, ЩО САМЕ буде всередині, а лише визначають спільне оформлення-«рамку» навколо довільного вмісту.

Ще одна деталь, яку варто пояснити окремо, бо вона легко спантеличує на початку: чому `<ProductCard />` написано з великої літери, а звичайні HTML-теги на кшталт `<div>` – з малої? Це не просто стиль оформлення, а РЕАЛЬНЕ синтаксичне правило, на якому JSX-компілятор розрізняє два принципово різні випадки. Тег, що починається з малої літери, компілятор сприймає як звичайний, вбудований HTML-елемент і компілює в рядок-назву тега (`React.createElement("div", ...)`). Тег, що починається з ВЕЛИКОЇ літери, компілятор сприймає як посилання на змінну з цим імʼям у коді – вашу функцію-компонент – і компілює у виклик саме цієї функції (`React.createElement(ProductCard, ...)`). Тому назви компонентів у React завжди пишуть у PascalCase (`ProductCard`, а не `productCard`) – це не просто конвенція, а технічна необхідність, щоб компілятор узагалі розпізнав тег як ваш компонент, а не спробував відрендерити його як невідомий HTML-тег `<productcard>`.

Композиція компонентів через вкладеність – зручний спосіб побудувати складний інтерфейс із простих частин, але в неї є практичне обмеження, з яким ви неминуче зіткнетесь, щойно дерево компонентів виросте на кілька рівнів углиб. Уявіть, що дані про залогіненого користувача потрібні глибоко вкладеному компоненту – наприклад, аватарці в шапці профілю, – а сам список користувача отримує лише найвищий, кореневий компонент застосунку. Пропси передаються ЛИШЕ від безпосереднього батька до безпосередньої дитини, тому якщо між ними ще три проміжні рівні компонентів, яким самі дані взагалі не потрібні, доведеться «протягнути» цей проп через КОЖЕН із цих проміжних рівнів, лише щоб він дістався кінцевого адресата:

```jsx
function App({ user }) {
  return <Layout user={user} />;
}
function Layout({ user }) {
  return <Header user={user} />; // Layout сам не використовує user, лише передає далі
}
function Header({ user }) {
  return <Avatar user={user} />; // Header теж лише передає далі
}
function Avatar({ user }) {
  return <img src={user.avatarUrl} alt={user.name} />; // а тут user нарешті реально потрібен
}
```

Це явище має усталену назву – «пробурювання пропсів» (prop drilling), і воно не так болісне при трьох рівнях вкладеності, як у прикладі вище, але стає справжнім тягарем при десяти-пʼятнадцяти. React пропонує окремий механізм для передачі даних напряму до глибоко вкладеного компонента, минаючи всі проміжні рівні, – Context, з яким ми детально попрацюємо на наступній лекції разом з іншими хуками.

Насамкінець – пропси мають значення за замовчуванням так само природно, як звичайні параметри функції з другої лекції, адже компонент і Є звичайною функцією:

```jsx
function ProductCard({ name, price, currency = "грн" }) {
  return <p>{name}: {price} {currency}</p>;
}
```

## Умовний рендер

Дуже часто частину інтерфейсу потрібно показувати лише за певної умови – наприклад, повідомлення «Товару немає в наявності» лише тоді, коли товару справді немає. Оскільки JSX – це, як ми зʼясували, насправді звичайний JavaScript, для умовного відображення використовують ті самі інструменти, що й у звичайному коді, лише вставлені у фігурні дужки `{ ... }`.

Найпоширеніший спосіб для випадку «показати ЩОСЬ АБО НІЧОГО» – оператор `&&`:

```jsx
function StockBadge({ inStock }) {
  return (
    <div>
      {!inStock && <span className="badge">Немає в наявності</span>}
    </div>
  );
}
```

Тут спрацьовує та сама особливість `&&`, яку варто памʼятати: якщо ліва частина (`!inStock`) хибна, вираз одразу повертає це хибне значення й НЕ обчислює праву частину взагалі, – а React просто нічого не рендерить замість хибного значення (`false`, `null`, `undefined`). Якщо ж ліва частина істинна, `&&` повертає праву частину – саме той JSX-елемент, який і буде відображено.

Коли потрібно вибрати одне з ДВОХ альтернативних відображень (а не «щось або нічого»), використовують тернарний оператор:

```jsx
function StockBadge({ inStock }) {
  return inStock
    ? <span className="badge badge-success">В наявності</span>
    : <span className="badge badge-danger">Немає в наявності</span>;
}
```

> [!warning] Типова помилка
> Використання `&&` з числом як лівою частиною – наприклад, `{count && <span>{count} товарів у кошику</span>}`. Якщо `count` дорівнює `0`, React виведе на екран буквально цифру «0» замість того, щоб нічого не показати, – тому що `0` хибне (falsy), і `&&` поверне саме його, а не `false`/`undefined`. React рендерить числа, включно з нулем, на відміну від `false` чи `null`, які він просто пропускає. Виправлення – явно перетворити на булеве значення: `{count > 0 && ...}`, або скористатись тернарним оператором.

Коли варіантів відображення не два, а більше, компонент часто зручніше «розгалужити» ще ДО самого `return`, а не намагатись утиснути всю логіку у вкладені тернарні оператори прямо всередині JSX, – це називають патерном раннього повернення (early return):

```jsx
function OrderStatus({ status }) {
  if (status === "loading") {
    return <p>Завантаження...</p>;
  }
  if (status === "error") {
    return <p className="error">Сталася помилка</p>;
  }
  return <p className="success">Замовлення оформлено</p>;
}
```

Це той самий `RequestState` із дискримінованим обʼєднанням, який ми типізували на попередній лекції через TypeScript, – тепер він визначає, ЯКИЙ САМЕ JSX компонент поверне, і ранній `return` тут читається набагато природніше, ніж один вкладений тернарний оператор на три варіанти поспіль.

## Списки та ключі

Практично будь-який реальний інтерфейс рано чи пізно потребує відобразити СПИСОК даних – картки товарів, коментарі, пункти меню. Пригадайте другу лекцію: метод `map()` перетворює кожен елемент масиву на щось нове – і в React саме `map()` є стандартним способом перетворити масив ДАНИХ на масив JSX-ЕЛЕМЕНТІВ:

```jsx
function ProductList({ products }) {
  return (
    <ul>
      {products.map(product => (
        <li key={product.id}>{product.name} – {product.price} грн</li>
      ))}
    </ul>
  );
}
```

Зверніть увагу на спеціальний проп `key` – його НЕОБХІДНО вказувати на кожному елементі, згенерованому в циклі, і React голосно попереджає в консолі, якщо його забути. Щоб зрозуміти, навіщо він потрібен, повернімось до механізму узгодження (reconciliation), про який ми говорили на початку лекції. Коли список змінюється – наприклад, користувач видаляє один товар із середини списку з десяти, – React має якось зрозуміти, ЯКИЙ САМЕ з елементів масиву видалили, щоб прибрати з DOM рівно один відповідний вузол, а не перемальовувати весь список заново. Уявіть бейджики учасників конференції: якщо на кожному бейджику написано лише порядковий номер у черзі («учасник №3»), а не імʼя, і хтось із середини черги йде геть, усім, хто стояв позаду нього, доведеться переклеїти бейджик на новий номер – фактично «оновити» усіх, хоча реально пішла лише одна людина. Якщо ж на кожному бейджику написано СТАБІЛЬНЕ, унікальне імʼя, а не порядковий номер, видно точно, ХТО саме пішов, а решта учасників залишаються при своїх бейджиках без жодних змін.

`key` – це і є таке «стабільне імʼя» для кожного елемента списку: унікальний і незмінний ідентифікатор (найчастіше – `id` із бази даних), за яким React точно відстежує, який DOM-вузол відповідає якому елементу масиву, навіть якщо порядок елементів змінився, один додався чи видалився.

> [!warning] Типова помилка
> Використовувати як `key` просто індекс елемента в масиві (`products.map((product, index) => <li key={index}>...`) – це та сама пастка «бейджика з номером у черзі», яку ми щойно розібрали. Якщо список статичний і ніколи не змінює порядок чи склад елементів, індекс технічно спрацює без видимих проблем. Але щойно елемент видаляють із середини списку чи список пересортовують, індекси всіх наступних елементів «зсуваються», і React через них плутає, який реальний елемент даних тепер відповідає якому DOM-вузлу, – це може призвести до заплутаних візуальних багів, коли, наприклад, поле введення тексту «залишається» на неправильному рядку після видалення сусіднього.

> [!exam] На іспиті
> Питання «чому не можна використовувати індекс масиву як key» – одне з найпопулярніших практичних питань про React. Правильна відповідь обовʼязково має згадувати механізм узгодження (reconciliation): проблема не в самому React, а в тому, що індекс НЕ є стабільним ідентифікатором конкретного елемента даних – він лише описує поточну ПОЗИЦІЮ, яка змінюється щоразу, коли змінюється сам список.

На практиці список рідко рендерять «як є» – частіше його спершу фільтрують за якоюсь умовою, і лише потім перетворюють на JSX. Оскільки `filter` і `map`, як ми детально розбирали на другій лекції, обидва повертають НОВИЙ масив, їх природно зʼєднувати в ланцюжок, рядок за рядком читаючи як «спочатку залиш потрібне, потім перетвори на розмітку»:

```jsx
function InStockList({ products }) {
  return (
    <ul>
      {products
        .filter(product => product.inStock)
        .map(product => <li key={product.id}>{product.name}</li>)}
    </ul>
  );
}
```

## Перший стан: `useState`

Дотепер усі наші компоненти були «пасивними»: вони показували те, що їм передали ззовні через пропси, і не могли самостійно ЗАПАМʼЯТАТИ жодних власних даних чи відреагувати на дію користувача зміною самих себе. Компонент, який реагує на клік лише виведенням чогось у консоль, не змінюючи власного відображення, – не дуже цікавий приклад інтерактивного інтерфейсу. React дає компоненту можливість мати власну «памʼять» – локальний стан – через спеціальну функцію `useState`, яку ми лише побіжно торкнемось тут, а детально розберемо на наступній лекції разом з іншими хуками.

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Кліків: {count}</p>
      <button onClick={() => setCount(count + 1)}>Клікнути</button>
    </div>
  );
}
```

`useState(0)` повертає масив із двох елементів, які традиційно дістають через деструктуризацію масиву з другої лекції: поточне значення стану (`count`, тут стартує з `0`) і функцію для його ОНОВЛЕННЯ (`setCount`). Ключовий момент, який відрізняє цей підхід від звичайної змінної: виклик `setCount` не просто змінює число десь у памʼяті – він повідомляє React, що дані змінились, і компонент потрібно ПЕРЕРЕНДЕРИТИ, тобто заново викликати функцію `Counter`, щоб отримати новий, актуальний опис інтерфейсу з новим значенням `count`, а далі React уже сам, через знайомий нам механізм узгодження, застосує до реального DOM лише ті зміни, які фактично потрібні.

> [!info] Для допитливих – чому не можна просто `let count = 0`
> Якби `Counter` використовував звичайну змінну `let count = 0` замість `useState`, зміна цієї змінної (`count = count + 1`) НІЯК не повідомила б React про потребу перерендерити компонент – React просто не «підписаний» на звичайні змінні, він реагує лише на виклики спеціальних функцій-оновлювачів на кшталт `setCount`. Крім того, кожен новий виклик функції `Counter` (а компоненти в React викликаються заново при кожному рендері) створював би змінну `count` заново, обнуляючи її, – тоді як `useState` спеціально влаштований так, щоб «памʼятати» значення між рендерами того самого компонента. Механізм, завдяки якому це працює, – той самий, що ми детально розглядали на другій лекції: [[courses/web-programming/lectures/06-react-khuky-ta-keruvannia-stanom|Лекція 6. React-хуки та керування станом]] покаже, що хуки React побудовані на замиканнях (closures).

Той самий принцип працює й для інших типів даних, не лише чисел, – наприклад, для булевого «перемикача» (показати/приховати блок):

```jsx
function Accordion({ title, children }) {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(!isOpen)}>{title}</button>
      {isOpen && <div>{children}</div>}
    </div>
  );
}
```

Тут одразу видно, як зустрічаються дві теми з цієї лекції: `setIsOpen(!isOpen)` перемикає булеве значення на протилежне при кожному кліку, а `{isOpen && <div>{children}</div>}` – той самий умовний рендер через `&&`, який ми розглядали раніше, – тепер керує видимістю вмісту акордеона залежно від значення стану.

Насамкінець варто згадати одну тонкість, з якою ви неминуче зіткнетесь, щойно спробуєте оновити стан на основі його ПОПЕРЕДНЬОГО значення кілька разів поспіль. `setCount(count + 1)`, написаний двічі підряд в одному обробнику, НЕ збільшить лічильник на два, як можна було б інтуїтивно очікувати, – обидва виклики «бачать» те саме, ще не оновлене значення `count`, захоплене з поточного рендера. Безпечніший спосіб – передати в `setCount` не нове значення напряму, а функцію, яка отримує АКТУАЛЬНЕ попереднє значення на момент реального оновлення:

```jsx
setCount(prevCount => prevCount + 1); // безпечно навіть за кілька викликів поспіль
```

Чому це працює саме так і що таке «застаріле замикання» (stale closure), яке спричиняє першу, неправильну поведінку, – детально розберемо на наступній лекції, коли говоритимемо про хуки й замикання глибше.
