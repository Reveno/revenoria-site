# React – маршрутизація, форми та робота з API

> [!abstract] Коротко
> Завершуємо блок React: маршрутизація без перезавантаження сторінки через React Router, керовані форми, валідація введення, відправка даних на сервер через `fetch` із коректною обробкою станів завантаження, і оптимізація повторних рендерів через `React.memo`. Ця лекція збирає докупи практично все, що ми вивчили про React за останні три заняття.

## Навчальні цілі

1. Пояснити, чим маршрутизація в SPA (React Router) відрізняється від переходів між звичайними HTML-сторінками з першої лекції.
2. Будувати керовані форми через `value`+`onChange` і розуміти компроміс із неконтрольованими полями.
3. Реалізовувати клієнтську валідацію форм, комбінуючи HTML5-атрибути з першої лекції та власну JS-логіку.
4. Відправляти дані форми на сервер через `fetch`, коректно відображаючи стани завантаження, успіху й помилки.
5. Оптимізувати зайві рендери компонентів через `React.memo` у поєднанні з `useCallback`.

## React Router: маршрутизація без перезавантаження сторінки

Пригадайте найпершу лекцію: коли браузер переходить за звичайним посиланням `<a href="/courses">`, це запускає весь цикл, який ми детально розбирали на самому початку курсу, – новий DNS-резолвінг (якщо потрібно), новий HTTP-запит, сервер повертає цілком новий HTML-документ, і браузер будує DOM практично з нуля, заново завантажуючи весь CSS і весь JavaScript. Для звичайного багатосторінкового сайту це нормально й очікувано. Але React-застосунок – це, як правило, SPA (Single Page Application, односторінковий застосунок): сервер віддає лише ОДНУ, часто майже порожню HTML-сторінку з підключеним великим JS-файлом, а весь подальший інтерфейс будує вже сам React прямо в браузері. Якби «навігація» між розділами такого застосунку щоразу викликала звичайний перехід за `<a>`, це означало б заново завантажувати весь важкий JS-бандл при кожному переході – украй марнотратно й повільно.

Уявіть різницю між тим, щоб купувати нову фізичну антену щоразу, коли хочете переключити канал телевізора, і тим, щоб просто натиснути кнопку пульта на вже увімкненому телевізорі – саме тіло телевізора, вся його «важка» апаратна частина, лишається на місці, змінюється лише те, що показується на екрані просто зараз. React Router працює саме за принципом пульта: сам React-застосунок («телевізор») завантажується один раз, а «перемикання каналів» – це просто зміна того, ЯКИЙ компонент зараз відображається, без жодного повторного звернення до сервера за новою сторінкою.

```jsx
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">Головна</Link>
        <Link to="/courses">Курси</Link>
      </nav>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/courses" element={<CourseList />} />
        <Route path="/courses/:courseId" element={<CourseDetail />} />
      </Routes>
    </BrowserRouter>
  );
}
```

Ключова відмінність, яку варто відзначити окремо, – компонент `<Link to="/courses">` виглядає майже як звичайний `<a href="/courses">`, і зрештою рендериться саме в тег `<a>` в реальному DOM (щоб посилання лишалось посиланням для скрінрідерів і для можливості відкрити в новій вкладці), але поводиться зовсім інакше при звичайному кліку. Усередині `Link` React Router перехоплює клік через `onClick` і викликає `event.preventDefault()` – той самий метод із третьої лекції, який скасовує типову поведінку браузера, – щоб зупинити звичайний перехід за посиланням із повним перезавантаженням сторінки. Замість цього він програмно змінює адресний рядок браузера через History API (без перезавантаження) і повідомляє React, який саме компонент тепер потрібно відрендерити для нового шляху, – і компонент `CourseList` просто з'являється на місці попереднього, весь процес відбувається миттєво, без жодного нового HTTP-запиту за HTML-сторінкою.

Зверніть увагу на `:courseId` у шляху `/courses/:courseId` – це динамічний сегмент маршруту, значення якого читають усередині цільового компонента через хук `useParams`:

```jsx
import { useParams } from "react-router-dom";

function CourseDetail() {
  const { courseId } = useParams();
  // courseId – це рядок із URL, наприклад "42" для /courses/42

  return <p>Деталі курсу №{courseId}</p>;
}
```

Часто цей параметр одразу використовують для завантаження конкретних даних – той самий `useFetch` із попередньої лекції чудово поєднується з `useParams`:

```jsx
function CourseDetail() {
  const { courseId } = useParams();
  const { data: course, isLoading } = useFetch(`/api/courses/${courseId}`);

  if (isLoading) return <p>Завантаження...</p>;
  return <h2>{course.title}</h2>;
}
```

Останній інструмент навігації, вартий згадки, – `useNavigate`, який дозволяє перейти на інший маршрут ПРОГРАМНО, з коду, а не через клік користувача по `<Link>` – типовий сценарій: перенаправити користувача на сторінку профілю одразу після успішного входу в систему.

```jsx
import { useNavigate } from "react-router-dom";

function LoginForm() {
  const navigate = useNavigate();

  function handleLoginSuccess() {
    navigate("/profile");
  }
  // ...
}
```

Насамкінець варто коротко пояснити, ЯК саме браузер узагалі дозволяє «підмінити» адресний рядок без перезавантаження сторінки, – адже це не якась внутрішня магія React, а стандартний браузерний History API. Метод `history.pushState()` дозволяє JavaScript-коду записати новий URL в адресний рядок і в історію переходів браузера (та сама історія, якою керують кнопки «вперед»/«назад») БЕЗ жодного мережевого запиту чи перезавантаження, – саме цей метод і викликає React Router усередині `<Link>` та `navigate()`. А коли користувач natively тисне кнопку «назад» у браузері, спрацьовує подія `popstate` – той самий формат подій, які ми детально розбирали на третій лекції, – і React Router слухає саме цю подію, щоб зрозуміти, який компонент тепер потрібно показати для URL, куди користувач щойно повернувся.

Ще одна практична деталь – що показати, якщо користувач перейшов за шляхом, якого взагалі немає серед оголошених `<Route>`. Для цього визначають «уловлюючий» маршрут із зірочкою, який спрацьовує, якщо жоден інший `path` не підійшов:

```jsx
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/courses" element={<CourseList />} />
  <Route path="*" element={<NotFound />} />
</Routes>
```

Це прямий фронтендовий аналог статус-коду `404 Not Found` із першої лекції – тільки замість того, щоб сервер повертав окрему HTML-сторінку з таким статусом, сам React-застосунок локально вирішує показати компонент `NotFound`, не звертаючись до сервера взагалі.

Насамкінець – вкладені маршрути (nested routes), які добре моделюють ситуацію, коли частина розмітки (наприклад, спільна бічна панель навігації курсу) має лишатись на екрані НЕЗАЛЕЖНО від того, яка конкретно вкладка курсу зараз відкрита, а змінюється лише внутрішній вміст:

```jsx
<Routes>
  <Route path="/courses/:courseId" element={<CourseLayout />}>
    <Route path="lectures" element={<LectureList />} />
    <Route path="assignments" element={<AssignmentList />} />
  </Route>
</Routes>

function CourseLayout() {
  return (
    <div>
      <CourseSidebar />
      <Outlet /> {/* сюди React Router підставить LectureList або AssignmentList */}
    </div>
  );
}
```

`<Outlet />` тут – це «місце-заглушка», куди React Router вставляє відповідний ДОЧІРНІЙ маршрут залежно від того, яка саме частина URL зараз активна, тимчасом як `CourseSidebar` і загальна структура `CourseLayout` лишаються незмінними на екрані при переході між вкладками – точнісінько так само, як не перемальовується вся сторінка сайту при переході за посиланням у межах одного роздiлу.

## Керовані форми

Пригадайте форми з першої лекції – там ми обмежувались нативною HTML-валідацією через атрибути `required`, `type="email"` тощо, а сам браузер самостійно тримав поточне значення поля десь у собі. У React найпоширеніший підхід зовсім інший: значення КОЖНОГО поля форми свідомо тримають у стані компонента (`useState`), а не дозволяють браузеру керувати ним самостійно, – це називають керованим компонентом (controlled component).

Уявіть секретарку, яка веде протокол зборів: замість того щоб дозволити будь-кому підходити й дописувати щось у протокол самостійно, кожен учасник каже секретарці вголос, ЩО саме додати, а секретарка сама записує це в протокол і, за потреби, зачитує поточний текст назад. React у ролі керованого компонента поводиться так само: значення поля вводу (`value`) завжди береться з ОДНОГО, конкретного джерела істини – стану компонента, – а не з внутрішньої, «схованої» памʼяті самого DOM-елемента поля, як це відбувається у звичайному, некерованому HTML.

```jsx
function LoginForm() {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");

  function handleSubmit(event) {
    event.preventDefault(); // зупиняємо типове перезавантаження сторінки при відправці форми
    console.log({ email, password });
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={(event) => setEmail(event.target.value)}
      />
      <input
        type="password"
        value={password}
        onChange={(event) => setPassword(event.target.value)}
      />
      <button type="submit">Увійти</button>
    </form>
  );
}
```

Пара `value` + `onChange` тут працює нерозривно, і саме тому: `value={email}` каже React «поле завжди повинно показувати те, що зараз лежить у змінній `email`», а `onChange` – це той момент, коли користувач ФІЗИЧНО щось надрукував, і саме через нього ми одразу оновлюємо `email` через `setEmail`, що, своєю чергою, викликає перерендер, і React знову «диктує» полю його ж власне, щойно оновлене значення. Виходить цикл: користувач друкує символ → `onChange` спрацьовує → `setEmail` оновлює стан → компонент перерендериться → `value` знову «диктує» полю актуальне значення. З боку користувача це виглядає як звичайне миттєве введення тексту, але технічно кожна надрукована літера проходить через увесь стан компонента.

> [!warning] Типова помилка
> Вказати `value`, але забути `onChange`, – React відреагує попередженням у консолі «You provided a `value` prop to a form field without an `onChange` handler», а поле фактично стане повністю нередагованим: React щоразу «диктуватиме» полю те саме, незмінне значення з `value`, ігноруючи спроби користувача щось надрукувати, адже нічого насправді не оновлює сам стан.

Іноді повний контроль над кожним натисканням клавіші взагалі не потрібен – наприклад, для простої форми, де значення полів читають лише один раз, у момент відправки. Для таких випадків існують некеровані компоненти (uncontrolled), де значення бере не React-стан, а сам DOM, – і читають його безпосередньо через `useRef` із попередньої лекції:

```jsx
function SimpleForm() {
  const nameRef = useRef(null);

  function handleSubmit(event) {
    event.preventDefault();
    console.log(nameRef.current.value); // читаємо напряму з DOM лише в момент відправки
  }

  return (
    <form onSubmit={handleSubmit}>
      <input ref={nameRef} type="text" />
      <button type="submit">Відправити</button>
    </form>
  );
}
```

Компроміс тут прямий: керовані поля дають повний контроль над кожним натисканням – можна одразу форматувати введення, лічити символи, показувати підказки в реальному часі, – але коштують трохи більше коду й додаткових перерендерів при кожній літері. Некеровані поля простіші й дешевші, але не дозволяють реагувати на зміни «наживо», лише в момент, коли ви явно вирішили прочитати значення. На практиці керовані компоненти – типовий вибір за замовчуванням у React, а некеровані лишають для простих, рідкісних випадків.

Форма з двома полями, як у прикладі вище, ще виглядає зручно, але уявіть форму реєстрації з десятьма полями – писати для КОЖНОГО окремий `useState` і окремий рядок `onChange={(e) => setXxx(e.target.value)}` швидко стає одноманітним і громіздким. Типовий прийом для форм із багатьма полями – тримати всі значення в ОДНОМУ обʼєкті стану й оновлювати конкретне поле через атрибут `name` та обчислюваний ключ обʼєкта, той самий синтаксис `[key]: value`, який ми детально розбирали на другій лекції:

```jsx
function RegistrationForm() {
  const [formData, setFormData] = useState({ email: "", password: "", city: "" });

  function handleChange(event) {
    const { name, value } = event.target; // деструктуризація з другої лекції
    setFormData({ ...formData, [name]: value }); // spread + обчислюваний ключ
  }

  return (
    <form>
      <input name="email" value={formData.email} onChange={handleChange} />
      <input name="password" value={formData.password} onChange={handleChange} />
      <input name="city" value={formData.city} onChange={handleChange} />
    </form>
  );
}
```

Тепер, замість окремого обробника на КОЖНЕ поле, всі поля діляться ОДНІЄЮ функцією `handleChange` – вона зчитує, яке саме поле викликало подію, через `event.target.name`, і оновлює лише відповідний ключ обʼєкта `formData`, залишаючи решту полів незмінними завдяки spread.

## Валідація форм

Тепер про те, як переконатись, що введені користувачем дані коректні, перш ніж відправляти їх далі. Пригадайте атрибути валідації з першої лекції – `required`, `pattern`, `minlength` – вони й досі працюють і чудово підходять для найпростіших, поверхневих перевірок формату просто «з коробки», без жодного JavaScript. Але для складнішої логіки – «пароль і підтвердження пароля мають збігатися», «email не повинен уже бути зареєстрованим» – потрібна власна перевірка на JavaScript, і саме тут стан компонента знову стає в пригоді, цього разу для зберігання ПОВІДОМЛЕНЬ ПРО ПОМИЛКИ:

```jsx
function SignupForm() {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [errors, setErrors] = useState({});

  function validate() {
    const newErrors = {};
    if (!email.includes("@")) {
      newErrors.email = "Некоректна адреса пошти";
    }
    if (password.length < 8) {
      newErrors.password = "Пароль має містити щонайменше 8 символів";
    }
    setErrors(newErrors);
    return Object.keys(newErrors).length === 0; // true, якщо помилок немає
  }

  function handleSubmit(event) {
    event.preventDefault();
    if (validate()) {
      console.log("Форма валідна, можна відправляти");
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      {errors.email && <p className="error">{errors.email}</p>}

      <input type="password" value={password} onChange={(e) => setPassword(e.target.value)} />
      {errors.password && <p className="error">{errors.password}</p>}

      <button type="submit">Зареєструватись</button>
    </form>
  );
}
```

Зверніть увагу, як тут природно зустрічаються дві теми з попередньої лекції одразу: об'єкт `errors` оновлюється незмінно через `setErrors(newErrors)` – цілком новий обʼєкт, а не мутація старого, – а `{errors.email && <p>...</p>}` це вже знайомий з пʼятої лекції умовний рендер через `&&`: повідомлення про помилку зʼявляється в розмітці лише тоді, коли для цього конкретного поля дійсно є помилка.

Окреме практичне рішення – КОЛИ саме запускати перевірку. Найпростіший варіант, показаний вище, – перевіряти лише один раз, при спробі відправки форми (`onSubmit`). Альтернатива – перевіряти кожне поле одразу, щойно користувач вийшов з нього фокусом (`onBlur`), показуючи помилку раніше, ще до спроби відправки. А найагресивніший варіант – перевіряти буквально на кожне натискання клавіші (`onChange`), як у прикладах вище з `email`/`password`. У кожного підходу свій компроміс між швидкістю зворотного звʼязку й тим, наскільки нав'язливо форма «сварить» користувача, який ще навіть не дописав своє введення до кінця, – валідація на кожен символ, показана одразу, часто дратує більше, ніж допомагає.

> [!exam] На іспиті
> Клієнтська валідація – будь-яка, чи то нативні HTML5-атрибути з першої лекції, чи власна JS-логіка, – це ВИКЛЮЧНО питання зручності інтерфейсу (UX), а НЕ безпеки. Будь-який досвідчений користувач може відкрити інструменти розробника в браузері й надіслати запит до сервера напряму, повністю оминувши вашу форму й усю JS-валідацію в ній, – HTTP-запит, як ми зʼясували ще на першій лекції, можна сформувати й надіслати будь-яким способом, не лише через вашу форму. Тому кожне правило, перевірене на клієнті, ОБОВʼЯЗКОВО повинно бути перевірене ЩЕ РАЗ на сервері, перш ніж дані потраплять у базу даних, – про це детально поговоримо в лекціях про Node.js та Express.

## Відправка форми на сервер через fetch

Тепер зʼєднаємо форми з тим, що ми детально вивчали на третій лекції про `fetch`, і з дискримінованими обʼєднаннями типів із четвертої лекції – саме зараз стає видно, чому цей патерн настільки практичний. Стан відправки форми природно описується як один із кількох чітко визначених варіантів: форма ще не відправлена, зараз відправляється, відправилась успішно, чи сталась помилка, – і жодного іншого стану бути не може.

```tsx
type SubmitState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success" }
  | { status: "error"; message: string };

function ContactForm() {
  const [email, setEmail] = useState("");
  const [message, setMessage] = useState("");
  const [submitState, setSubmitState] = useState<SubmitState>({ status: "idle" });

  async function handleSubmit(event: React.FormEvent) {
    event.preventDefault();
    setSubmitState({ status: "loading" });

    try {
      const response = await fetch("/api/contact", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ email, message })
      });

      if (!response.ok) {
        throw new Error(`Сервер повернув помилку: ${response.status}`);
      }

      setSubmitState({ status: "success" });
    } catch (error) {
      setSubmitState({ status: "error", message: (error as Error).message });
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <textarea value={message} onChange={(e) => setMessage(e.target.value)} />

      <button type="submit" disabled={submitState.status === "loading"}>
        {submitState.status === "loading" ? "Надсилання..." : "Надіслати"}
      </button>

      {submitState.status === "success" && <p>Дякуємо, повідомлення надіслано!</p>}
      {submitState.status === "error" && <p className="error">{submitState.message}</p>}
    </form>
  );
}
```

Тут одразу видно, скільки тем із попередніх лекцій зійшлись в одному місці: `event.preventDefault()` із третьої лекції зупиняє типову поведінку форми (перезавантаження сторінки); `try`/`catch` із другої лекції та перевірка `response.ok` із третьої лекції обробляють одразу і мережеву помилку, і HTTP-помилку статус-коду; дискримінований union із четвертої лекції описує стан `submitState`, і React, побачивши конкретне значення `status`, точно знає, що показати – індикатор завантаження, повідомлення про успіх чи текст помилки; а кнопка `disabled={submitState.status === "loading"}` блокує повторну відправку, поки перша ще виконується, – типовий захист від того, щоб нетерплячий користувач не наклацав кілька однакових запитів поспіль.

## Оптимізація рендеру: React.memo

Насамкінець – тема, яка логічно продовжує `useMemo`/`useCallback` із попередньої лекції, лише застосована не до значень чи функцій УСЕРЕДИНІ компонента, а до самого рендеру ЦІЛОГО компонента. За замовчуванням, коли батьківський компонент перерендерюється, React перерендерює й УСІХ його дочірніх компонентів теж – навіть тих, чиї пропси взагалі не змінились. Для маленьких, дешевих компонентів це непомітно, але для великого списку з тисячею карток товарів, де змінилась лише ОДНА картка, а батько перерендерюється часто, це може стати відчутним гальмом.

`React.memo` – це обгортка над компонентом, яка каже React: «перед тим як перерендерити цей компонент, спершу порівняй нові пропси зі старими, і якщо вони НЕ ЗМІНИЛИСЬ – просто пропусти рендер, покажи те, що вже намальовано».

```jsx
const ProductCard = React.memo(function ProductCard({ product, onAdd }) {
  console.log("Рендеримо картку:", product.name); // тепер виводиться лише коли product чи onAdd реально змінились
  return (
    <div className="card">
      <h3>{product.name}</h3>
      <button onClick={() => onAdd(product.id)}>Купити</button>
    </div>
  );
});
```

Тут криється пряма пастка, яка напряму пояснює, чому ми детально розбирали `useCallback` саме на попередній лекції, а не залишили цю тему на потім. `React.memo` порівнює пропси ЗА ПОСИЛАННЯМ для обʼєктів і функцій – той самий принцип із другої лекції про примітиви й посилання. Якщо батьківський компонент передає `onAdd` як інлайн-функцію, оголошену прямо всередині JSX (`onAdd={() => handleAdd(product.id)}`), ця функція створюється ЗАНОВО при КОЖНОМУ рендері батька – нове посилання щоразу, – і для `React.memo` це виглядає так, ніби пропс «змінився», навіть якщо фактична поведінка функції та сама. У результаті `React.memo` марно порівнює пропси щоразу, бачить «відмінність» через нове посилання функції й усе одно перерендерює компонент – уся оптимізація зводиться нанівець.

```jsx
// НЕПРАВИЛЬНО – onAdd отримує нове посилання при кожному рендері ProductList
function ProductList({ products }) {
  function handleAdd(id) { console.log("Додано:", id); }
  return products.map(p => <ProductCard key={p.id} product={p} onAdd={() => handleAdd(p.id)} />);
}

// ПРАВИЛЬНО – useCallback з попередньої лекції зберігає те саме посилання між рендерами
function ProductList({ products }) {
  const handleAdd = useCallback((id) => console.log("Додано:", id), []);
  return products.map(p => <ProductCard key={p.id} product={p} onAdd={handleAdd} />);
}
```

Саме тому `React.memo` й `useCallback` на практиці майже завжди застосовують у парі: `React.memo` пропускає рендер дочірнього компонента, лише якщо пропси дійсно стабільні між рендерами батька, – а стабільність посилання на функцію-пропс гарантує саме `useCallback`.

> [!warning] Типова помилка
> Обгортати в `React.memo` кожен компонент підряд, «про всяк випадок», так само як ми попереджали про надмірне використання `useMemo` на попередній лекції. Сама перевірка пропсів на відмінність теж коштує процесорного часу, і для дешевих, простих компонентів (короткий текст, невелика картка) ця перевірка може обійтись дорожче за сам звичайний рендер, який вона мала б заощадити. `React.memo` виправданий там, де рендер компонента дійсно ВАЖКИЙ (складна розмітка, важкі обчислення всередині) або компонент рендериться дуже часто у великій кількості – наприклад, тисяча рядків таблиці.
