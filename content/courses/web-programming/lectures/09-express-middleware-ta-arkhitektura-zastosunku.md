# Express – middleware та архітектура застосунку

> [!abstract] Коротко
> На попередній лекції ми побіжно згадали `express.json()` як «щось, без чого `req.body` не працює». Тепер розберемо middleware – центральний механізм Express – детально: як писати власне, як обробляти помилки централізовано, як структурувати проєкт із кількома маршрутами, і як безпечно зберігати налаштування й секрети через змінні оточення.

## Навчальні цілі

1. Пояснити механізм middleware в Express: сигнатуру `(req, res, next)`, порядок виконання, різницю між `app.use` глобально й локально для маршруту.
2. Писати власне middleware для логування та перевірки авторизації.
3. Реалізовувати централізовану обробку помилок, включно з помилками в асинхронних обробниках.
4. Структурувати Express-проєкт через `express.Router()` і поділ на маршрути/контролери/сервіси.
5. Використовувати змінні оточення для конфігурації й секретів, не зберігаючи їх у коді.

## План лекції

1. Middleware: механізм і порядок виконання
2. Власне middleware: логування та авторизація
3. Централізована обробка помилок
4. Структура проєкту: Router, контролери, сервіси
5. Змінні оточення

## Middleware: механізм і порядок виконання

Пригадайте `app.use(express.json())` із попередньої лекції – ми тоді сказали лише, що без цього рядка `req.body` залишається порожнім, і пообіцяли розібратись, ЩО це насправді за механізм. Middleware (проміжне програмне забезпечення) – це функція, яка стоїть НА ШЛЯХУ запиту від моменту, коли Express його прийняв, до моменту, коли якийсь конкретний маршрут (`app.get`, `app.post`) нарешті його обробить і надішле відповідь. Уявіть контроль в аеропорту: пасажир не потрапляє одразу до літака – він послідовно проходить через кілька окремих станцій одну за одною: перевірка квитка, огляд багажу, паспортний контроль, – і кожна станція виконує СВОЮ конкретну, вузьку задачу, перш ніж пропустити пасажира далі. Middleware в Express працює за тим самим принципом: кожен запит проходить через ланцюжок функцій-«станцій», і кожна з них щось робить із запитом (логує, перевіряє, розбирає дані) і передає його далі, доки він нарешті не дістанеться свого маршруту.

```js
function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next(); // передати запит далі по ланцюжку
}

app.use(logger); // застосовується до УСІХ маршрутів
```

Три параметри функції middleware – `req`, `res`, `next` – і саме останній, `next`, є ключовим для розуміння всього механізму. Викликаючи `next()`, middleware каже Express: «моя робота тут завершена, передай запит наступній станції в черзі». Якщо middleware ЗАБУДЕ викликати `next()` і НЕ надішле власну відповідь через `res`, запит просто «зависне» – Express чекатиме на подальші дії нескінченно, а клієнт (браузер чи `fetch` на фронтенді) так ніколи й не отримає відповіді.

```js
function requireAuth(req, res, next) {
  const token = req.headers.authorization;

  if (!token) {
    res.status(401).json({ message: "Потрібна авторизація" });
    return; // ЗУПИНЯЄМО ланцюжок тут – next() НЕ викликається
  }

  next(); // токен є, передаємо запит далі
}
```

Тут видно другу сторону цього механізму: middleware може ЗУПИНИТИ ланцюжок, самостійно надіславши відповідь і не викликаючи `next()` взагалі, – так само як пасажира без квитка не пропустять на наступну станцію контролю, а розвернуть просто на місці, ще до паспортного контролю. Саме на цьому принципі побудована перевірка авторизації: якщо токена немає, запит НІКОЛИ не дістанеться самого маршруту з бізнес-логікою – його «розвертають» ще на самому вході.

Middleware для валідації вхідних даних працює за тим самим принципом «розвернути на вході», лише перевіряє не токен, а форму самих даних, – і тут природно згадується перевірка полів форми, яку ми детально розбирали на сьомій лекції, тільки тепер вона відбувається не в браузері, а на сервері (пригадайте застереження з тієї ж лекції: клієнтська валідація – лише зручність, серверна – обовʼязкова):

```js
function validateProduct(req, res, next) {
  const { name, price } = req.body;

  if (!name || typeof name !== "string") {
    res.status(400).json({ message: "Поле name обовʼязкове й має бути рядком" });
    return;
  }
  if (typeof price !== "number" || price <= 0) {
    res.status(400).json({ message: "Поле price має бути додатним числом" });
    return;
  }

  next();
}

app.post("/products", validateProduct, (req, res) => {
  // сюди дійдуть лише дані, що вже пройшли перевірку
});
```

Порядок, у якому middleware підключені через `app.use`, має пряме значення – так само як контроль квитка обовʼязково передує паспортному контролю, а не навпаки. Middleware, підключене РАНІШЕ, виконується РАНІШЕ:

```js
app.use(logger);        // спочатку логуємо ВСІ запити, включно з тими, що провалять авторизацію
app.use(requireAuth);   // потім перевіряємо токен
app.get("/profile", (req, res) => { /* сюди дійдуть лише авторизовані запити */ });
```

Якщо поміняти `logger` і `requireAuth` місцями, неавторизовані запити взагалі не потраплять до логера – цілком коректна, але зовсім інша поведінка, яку варто обирати свідомо, а не випадково.

Express постачається з кількома вбудованими middleware «з коробки», і `express.json()` із попередньої лекції – лише одне з них. Ось кілька інших, які трапляються практично в кожному реальному проєкті:

| Middleware | Призначення |
|---|---|
| `express.json()` | Розбирає тіло запиту у форматі JSON у `req.body` |
| `express.urlencoded({ extended: true })` | Розбирає дані звичайних HTML-форм (`Content-Type: application/x-www-form-urlencoded`) |
| `express.static("public")` | Віддає файли з папки `public` напряму (зображення, CSS) без окремого маршруту на кожен файл |
| `cors()` (окремий пакет) | Додає заголовки, що дозволяють запити з інших доменів |

Останній рядок цієї таблиці варто пояснити окремо: пригадайте CORS із третьої лекції – механізм, через який браузер за замовчуванням блокує запити з фронтенду на іншому домені до вашого API. Пакет `cors`, підключений як middleware, автоматично додає до КОЖНОЇ відповіді заголовок `Access-Control-Allow-Origin`, дозволяючи браузеру фронтенду приймати відповідь від цього сервера, – без нього довелося б виставляти цей заголовок вручну в кожному окремому маршруті.

`app.use` без явно вказаного шляху застосовує middleware до АБСОЛЮТНО всіх маршрутів. Якщо потрібно застосувати middleware лише до конкретного маршруту чи групи маршрутів, його передають окремим аргументом просто перед функцією-обробником:

```js
app.get("/profile", requireAuth, (req, res) => {
  res.json({ message: "Це захищена сторінка" });
});

app.get("/courses", (req, res) => {
  res.json(courses); // публічний маршрут, requireAuth тут не застосовується
});
```

## Власне middleware: логування та авторизація

Розширимо приклад авторизації до реалістичнішого вигляду, що поєднує кілька тем із попередніх лекцій одразу. Пригадайте другу лекцію: `try`/`catch` для обробки помилок, і третю лекцію: `Authorization`-заголовок, який ми вже бачили в таблиці HTTP-заголовків на першій лекції.

```js
function requireAuth(req, res, next) {
  const authHeader = req.headers.authorization; // наприклад, "Bearer eyJhbGci..."

  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    res.status(401).json({ message: "Відсутній або некоректний токен" });
    return;
  }

  const token = authHeader.replace("Bearer ", "");

  try {
    const payload = verifyToken(token); // перевірка підпису токена
    req.user = payload; // прикріплюємо дані користувача до req – наступні middleware й маршрут їх побачать
    next();
  } catch (error) {
    res.status(401).json({ message: "Недійсний токен" });
  }
}
```

Зверніть увагу на рядок `req.user = payload` – middleware може не лише пропускати чи блокувати запит, а й ЗБАГАЧУВАТИ обʼєкт `req` додатковими даними, які потім будуть доступні всім НАСТУПНИМ middleware й самому маршруту в ланцюжку, – так само як контроль паспорта в аеропорту може «прикріпити» до пасажира додатковий статус (наприклад, позначку про додатковий огляд), який побачать усі наступні станції.

## Централізована обробка помилок

Уявіть, що замість дюжини окремих `try`/`catch` у кожному окремому маршруті, які кожен по-своєму форматують повідомлення про помилку, – усі помилки стікаються в ОДНЕ спільне місце, де вирішується, як саме їх показати клієнту. Express підтримує це нативно через спеціальний тип middleware – функцію з ЧОТИРМА параметрами замість трьох (`err, req, res, next`), яку Express розпізнає САМЕ за кількістю параметрів і викликає лише тоді, коли десь раніше в ланцюжку сталася помилка:

```js
function errorHandler(err, req, res, next) {
  console.error(err.stack);

  if (err.name === "ValidationError") { // той самий клас помилки з другої лекції
    res.status(400).json({ message: err.message });
    return;
  }

  res.status(500).json({ message: "Внутрішня помилка сервера" });
}

app.use(errorHandler); // обробник помилок реєструють ОСТАННІМ, після всіх маршрутів
```

Щоб помилка взагалі «дісталась» цього обробника, її потрібно передати через `next(err)` – виклик `next` НЕ без аргументів, а САМЕ З помилкою як аргументом. Це своєрідна «спеціальна смуга» конвеєра: щойно `next` викликають з аргументом, Express одразу перескакує через УСІ звичайні middleware та маршрути, що йшли б далі, і веде запит прямо до найближчого обробника помилок – так само як бракований виріб на заводському конвеєрі одразу спрямовують у спеціальний жолоб для браку, минаючи всі наступні звичайні станції обробки.

```js
app.get("/products/:id", (req, res, next) => {
  try {
    const product = findProductById(req.params.id);
    if (!product) {
      throw new Error("Товар не знайдено");
    }
    res.json(product);
  } catch (error) {
    next(error); // передаємо помилку в централізований обробник, а не обробляємо тут вручну
  }
});
```

Тут криється важлива й неочевидна пастка, повʼязана з асинхронним кодом, – і вона варта окремого, уважного розбору. Express (у версіях до пʼятої) автоматично перехоплює помилки лише в СИНХРОННОМУ коді маршруту. Якщо помилка стається всередині `async`-функції ПІСЛЯ `await` і НЕ обгорнута у власний `try`/`catch`, Express про неї просто не дізнається – запит «зависне» без відповіді, а сервер може навіть аварійно завершитись, залежно від типу помилки:

```js
// НЕБЕЗПЕЧНО в старіших версіях Express – помилка після await "губиться"
app.get("/products/:id", async (req, res) => {
  const product = await fetchProductFromDatabase(req.params.id); // якщо тут станеться помилка...
  res.json(product); // ...цей рядок ніколи не виконається, і Express про помилку НЕ дізнається сам
});

// БЕЗПЕЧНО – явний try/catch з передачею помилки далі, той самий патерн з третьої лекції
app.get("/products/:id", async (req, res, next) => {
  try {
    const product = await fetchProductFromDatabase(req.params.id);
    res.json(product);
  } catch (error) {
    next(error);
  }
});
```

> [!exam] На іспиті
> Питання про те, чому `async`-обробники маршрутів у Express потребують явного `try`/`catch` з `next(error)`, а звичайні синхронні – ні, перевіряють доволі часто. Правильна відповідь має посилатись на те, що ми детально розбирали на третій лекції: Express (як і звичайний `try`/`catch`) не «підписаний» автоматично на відхилені (rejected) `Promise`, що виникають глибоко всередині `async`-функції після `await`, – цю помилку потрібно явно перехопити самостійно й передати далі через `next(error)`.

Пригадайте другу лекцію, де ми створювали власний клас помилки `ValidationError`, успадкований від `Error`, саме для того, щоб розрізняти РІЗНІ типи проблем за назвою класу, а не парсити текст повідомлення. У централізованому обробнику помилок цей прийом розкривається на повну: замість одного загального `if (err.name === "ValidationError")`, можна завести цілу невелику ієрархію власних класів помилок, кожен з яких відповідає своєму HTTP-статус-коду:

```js
class NotFoundError extends Error {
  constructor(message) {
    super(message);
    this.name = "NotFoundError";
    this.statusCode = 404;
  }
}

class ValidationError extends Error {
  constructor(message) {
    super(message);
    this.name = "ValidationError";
    this.statusCode = 400;
  }
}

function errorHandler(err, req, res, next) {
  const statusCode = err.statusCode || 500; // якщо клас помилки невідомий – 500 за замовчуванням
  res.status(statusCode).json({ message: err.message });
}
```

Тепер будь-який маршрут просто кидає ЗМІСТОВНИЙ, конкретний клас помилки (`throw new NotFoundError("Товар не знайдено")`), а обробник помилок сам, автоматично, визначає правильний статус-код за властивістю `statusCode`, яку кожен клас несе із собою, – жодних розкиданих по коду `if`-перевірок на назву помилки більше не потрібно.

> [!warning] Типова помилка
> Забути зареєструвати `errorHandler` останнім, ПІСЛЯ всіх маршрутів. Middleware в Express виконуються строго в порядку реєстрації, і обробник помилок, зареєстрований ДО якогось маршруту, просто не «побачить» помилки, що стались у цьому маршруті, – `next(error)` шукає найближчий ПОДАЛЬШИЙ обробник помилок у ланцюжку, а не будь-який зареєстрований коли завгодно.

## Структура проєкту: Router, контролери, сервіси

Один файл `server.js` із сотнею маршрутів поспіль швидко стає неможливо підтримувати – так само як цех, де різання, збирання й фарбування меблів відбуваються в одному й тому самому переповненому приміщенні без жодного розділення. Express пропонує `express.Router()` – мініатюрну, самостійну версію застосунку, яку можна наповнити власними маршрутами в ОКРЕМОМУ файлі, а потім підключити до головного застосунку одним рядком:

```js
// routes/courses.js
import { Router } from "express";

const router = Router();

router.get("/", (req, res) => { /* GET /courses */ });
router.get("/:id", (req, res) => { /* GET /courses/:id */ });
router.post("/", (req, res) => { /* POST /courses */ });

export default router;
```

```js
// server.js
import coursesRouter from "./routes/courses.js"; // ES-модулі з другої лекції

app.use("/courses", coursesRouter); // усі маршрути router тепер живуть під префіксом /courses
```

Зверніть увагу: усередині `routes/courses.js` маршрути оголошені відносно свого власного «кореня» (`/`, `/:id`), а справжній префікс `/courses` додається лише в момент підключення до головного застосунку через `app.use("/courses", coursesRouter)` – це означає, що той самий router можна за бажання підключити під ІНШИМ префіксом, не змінюючи жодного рядка всередині файлу з маршрутами.

На практиці логіку прийнято розділяти ще далі, на кілька шарів із чіткою відповідальністю кожного: маршрути (routes) визначають лише, ЯКИЙ URL і метод веде до якої функції; контролери (controllers) – самі функції-обробники, що читають `req` і формують `res`; сервіси (services) – «бізнес-логіка», не привʼязана напряму до HTTP узагалі, – наприклад, функції роботи з базою даних, які ми детально розглянемо вже на наступній лекції. Таке розділення робить кожен файл маленьким і зосередженим на одній задачі – той самий принцип «одна станція, одна задача», який ми обговорювали для middleware на початку лекції, застосований тепер до структури всього проєкту.

```
project/
  server.js              – точка входу, підключення middleware й роутерів
  routes/
    courses.js            – лише "який URL веде до якого контролера"
    products.js
  controllers/
    coursesController.js  – читає req, викликає сервіс, формує res
  services/
    coursesService.js     – бізнес-логіка, робота з базою даних
  middleware/
    requireAuth.js
    errorHandler.js
  .env
  .gitignore
  package.json
```

Практична вигода такого розділення відчувається не одразу, а тоді, коли проєкт росте: якщо контролер лише викликає сервіс, не знаючи деталей того, ЯК саме дані дістаються з бази, – саму базу даних (наприклад, PostgreSQL замість MongoDB) можна замінити, переписавши лише файли сервісів, не чіпаючи жодного контролера чи маршруту. Це той самий принцип, з яким ми вже зустрічались у React на пʼятій-шостій лекціях: чим менше конкретний шматок коду знає про сусідні шари, тим легше його змінювати незалежно від решти.

## Змінні оточення

Насамкінець – практичне питання, яке рано чи пізно постає в будь-якому реальному проєкті: де зберігати секретні дані – паролі бази даних, ключі стороннiх сервісів, – які НЕ МОЖНА заносити прямо в код, що потрапляє в git-репозиторій, доступний, можливо, багатьом людям чи навіть публічно на GitHub. Уявіть театральну виставу, той самий текст пʼєси зіграють у десятках різних театрів по всьому світу, – але деякі деталі постановки (декорації, конкретні репліки, що залежать від локального контексту) підставляють ОКРЕМО для кожного конкретного театру, не змінюючи сам оригінальний текст пʼєси. Змінні оточення (environment variables) працюють за тим самим принципом: код застосунку лишається ОДНАКОВИМ незалежно від того, де він запущений, а конкретні значення – адреса бази даних, секретні ключі – підставляють ЗОВНІ, окремо для кожного середовища (розробка на вашому компʼютері, тестовий сервер, реальний продакшн), без жодних змін у самому коді.

```js
const port = process.env.PORT || 3000;
const dbUrl = process.env.DATABASE_URL;
```

`process.env` – глобальний обʼєкт Node.js, що містить усі змінні оточення, з якими запущено процес. Під час розробки їх зазвичай не виставляють вручну в терміналі щоразу, а зберігають у файлі `.env` у корені проєкту й підвантажують через невелику бібліотеку `dotenv`:

```
# .env
PORT=3000
DATABASE_URL=postgresql://user:password@localhost:5432/mydb
JWT_SECRET=якийсь-довгий-секретний-рядок
```

```js
import "dotenv/config"; // завантажує .env у process.env одразу при імпорті

const port = process.env.PORT || 3000;
```

Окрема, дуже поширена змінна оточення – `NODE_ENV`, що позначає, у якому «театрі» зараз виконується вистава: `development` (ваш власний компʼютер під час написання коду), `production` (реальний сервер, яким користуються реальні люди), іноді `test` (автоматичні тести). Код часто читає цю змінну, щоб поводитись по-різному залежно від середовища – наприклад, показувати детальний стек помилки в консолі під час розробки, але приховувати технічні деталі від реальних користувачів у продакшені, щоб випадково не розкрити внутрішню структуру сервера:

```js
function errorHandler(err, req, res, next) {
  const statusCode = err.statusCode || 500;
  const isDev = process.env.NODE_ENV === "development";

  res.status(statusCode).json({
    message: err.message,
    stack: isDev ? err.stack : undefined // деталі помилки лише під час розробки
  });
}
```

> [!warning] Типова помилка
> Закомітити файл `.env` у git разом із рештою коду проєкту. Файл `.env` МАЄ бути прямо перелічений у `.gitignore`, і замість нього в репозиторій додають `.env.example` – той самий список назв змінних, але з порожніми чи фіктивними значеннями замість реальних секретів, – щоб інший розробник знав, ЯКІ змінні потрібно налаштувати самостійно, не бачачи ваших реальних паролів і ключів. Секрет, який хоч раз потрапив у git-історію, вважається скомпрометованим назавжди – навіть якщо видалити файл наступним комітом, він і далі залишається доступним у попередніх комітах історії репозиторію.

## Завдання на занятті (20-25 хв)

1. Напишіть middleware `logger`, що виводить метод, шлях і час обробки кожного запиту (виміряний через різницю часу до й після `next()`), і підключіть його глобально через `app.use`.
2. Напишіть middleware `requireAuth`, що перевіряє наявність заголовка `Authorization`, і застосуйте його лише до одного конкретного маршруту, залишивши решту публічними.
3. Винесіть маршрути товарів в окремий файл через `express.Router()`, підключіть його з префіксом `/products` до головного застосунку, і додайте централізований `errorHandler`, що ловить помилки з `POST /products` через `next(error)` при некоректних вхідних даних.

> [!question] Перевірте себе
> - Що станеться із запитом, якщо middleware не викличе `next()` і не надішле власну відповідь?
> - Чому порядок реєстрації middleware через `app.use` має значення?
> - Як middleware може одночасно і пропустити запит далі, і додати до нього нові дані (наприклад, `req.user`)?
> - За якою ознакою Express розпізнає, що функція – це саме обробник помилок, а не звичайне middleware?
> - Чому `next(error)` «перестрибує» через звичайні маршрути прямо до обробника помилок?
> - Чому `async`-обробник маршруту потребує явного `try`/`catch` з `next(error)`, а звичайний синхронний – ні?
> - Чим `cors()` як middleware розвʼязує проблему, яку ми детально розбирали на третій лекції?
> - Як власна ієрархія класів помилок (`NotFoundError`, `ValidationError`) зі своїм `statusCode` спрощує централізований `errorHandler`?
> - Навіщо `express.Router()` дозволяє оголошувати маршрути відносно власного «кореня», а не повного шляху одразу?
> - Чому розділення на routes/controllers/services полегшує заміну бази даних без переписування контролерів?
> - Для чого потрібна змінна `NODE_ENV`, і чому стек помилки варто показувати лише в `development`, а не в `production`?
> - Чому файл `.env` не можна комітити в git, і що робити, якщо секрет туди все ж потрапив?
