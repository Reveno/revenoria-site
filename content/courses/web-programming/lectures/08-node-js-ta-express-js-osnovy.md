# Node.js та Express.js — основи

> [!abstract] Коротко
> Переходимо з фронтенду на бекенд: Node.js дозволяє виконувати той самий JavaScript, яким ми користувались усі попередні лекції, поза браузером — на сервері. Розглянемо асинхронну модель Node.js, `npm` та `package.json`, різницю між CommonJS і ES-модулями, і напишемо перший HTTP-сервер спочатку на «голому» Node.js, а потім через Express — фреймворк, який робить це набагато зручніше.

## Навчальні цілі

1. Пояснити, чим Node.js відрізняється від JavaScript у браузері, і чому асинхронна, неблокуюча модель особливо важлива саме на сервері.
2. Використовувати `npm` та `package.json` для керування залежностями проєкту.
3. Розрізняти CommonJS (`require`) та ES-модулі (`import`) у Node.js.
4. Створити HTTP-сервер на «голому» Node.js та зрозуміти, яку саме роботу бере на себе Express.
5. Оголошувати маршрути в Express для різних HTTP-методів, читати параметри шляху та query-рядка.

## План лекції

1. Що таке Node.js і навіщо він потрібен
2. Асинхронність на сервері: той самий event loop, нова роль
3. `npm` та `package.json`
4. Модулі: CommonJS проти ES-модулів
5. Перший сервер: від `http` до Express
6. Маршрути в Express

## Що таке Node.js і навіщо він потрібен

Усі сім попередніх лекцій ми писали JavaScript, який виконувався ВСЕРЕДИНІ браузера — маніпулював DOM, реагував на кліки, робив `fetch`-запити до сервера. Але сам JavaScript як мова програмування не привʼязаний до браузера жорстко: рушій, що фактично виконує JS-код у Chrome, — V8 — це окремий, самостійний шматок програмного забезпечення, і розробники Node.js у 2009 році зробили простий, але потужний крок: витягнули цей самий рушій V8 із браузера й дали йому змогу працювати самостійно, поза будь-якою вебсторінкою, з прямим доступом до файлової системи, мережі та інших можливостей операційної системи, яких у браузера з міркувань безпеки якраз немає. Уявіть автомобільний двигун, який вийняли з машини й встановили на човен: це той самий двигун, що працює за тими самими фізичними принципами, але тепер він приводить у рух зовсім інший тип «транспорту», з іншими можливостями та обмеженнями.

> [!definition] Node.js
> Середовище виконання JavaScript поза браузером, побудоване на рушії V8. Дозволяє писати сервери, скрипти командного рядка, інструменти збірки — усе, для чого раніше потрібна була окрема серверна мова (Python, Java, PHP, Ruby) — тим самим JavaScript, яким ви вже пишете фронтенд.

Практична вигода тут не лише концептуальна. Коли фронтенд і бекенд написані однією мовою, одна й та сама людина може вільно переключатись між ними, не перемикаючи в голові синтаксис і звички; типи даних, описані через TypeScript-інтерфейси на четвертій лекції, можна буквально ПОДІЛИТИ між фронтендом і бекендом в одному проєкті; а формат обміну даними — JSON, — з яким ми детально працювали в `fetch` на третій лекції, — це, по суті, рідний формат самого JavaScript (`JSON.stringify`/`JSON.parse` — методи, які ми вже знаємо), тому серверу на Node.js не потрібно нічого «перекладати» між внутрішнім представленням даних і тим, що йде по мережі.

Окрім повноцінних серверів, Node.js активно використовують і для звичайних скриптів командного рядка — саме він виконує команди `npm`, `tsc` (компілятор TypeScript із четвертої лекції) та практично весь сучасний інструментарій фронтенд-розробки: збирачі проєктів, лінтери, тестові фреймворки. Коли ви на попередніх лекціях запускали `tsc` для компіляції TypeScript, під капотом це теж був Node.js-скрипт. Це ще одна причина, чому Node.js став де-факто стандартом: навіть розробники, що взагалі не пишуть бекенд, однаково щодня користуються інструментами, написаними на ньому.

## Асинхронність на сервері: той самий event loop, нова роль

Пригадайте третю лекцію: JavaScript однопотоковий, і саме event loop дозволяє йому не «зависати» на довгих операціях — метафора єдиної каси в супермаркеті, яка передає довгі замовлення «на склад» і тим часом обслуговує наступних клієнтів. На сервері ця сама модель відіграє ще важливішу роль, ніж у браузері, і ось чому. Уявіть сервер, який одночасно обробляє запити від тисячі різних користувачів. Якщо для КОЖНОГО запиту, що потребує звернення до бази даних (а це завжди відносно повільна операція порівняно зі швидкістю самого процесора), «каса» буде фізично СТОЯТИ й чекати на відповідь бази даних, не обслуговуючи нікого іншого, — 999 інших користувачів застрягнуть у черзі, чекаючи, поки завершиться робота з базою даних для першого з них. Саме тому Node.js побудований навколо неблокуючого (non-blocking) підходу до операцій вводу-виводу (I/O) — читання файлів, звернення до бази даних, мережеві запити — за замовчуванням.

```js
const fs = require("fs");

// БЛОКУЮЧИЙ варіант — "каса" фізично зупиняється, доки файл не прочитається повністю
const dataSync = fs.readFileSync("large-file.json");
console.log("Прочитано синхронно");

// НЕБЛОКУЮЧИЙ варіант — "каса" передає читання файлу "на склад" і одразу йде далі
fs.readFile("large-file.json", (err, dataAsync) => {
  console.log("Прочитано асинхронно");
});
console.log("Цей рядок виконається РАНІШЕ, ніж асинхронне читання завершиться");
```

Зверніть увагу на порядок виведення в консоль у неблокуючому варіанті: рядок «Цей рядок виконається РАНІШЕ...» зʼявиться до «Прочитано асинхронно» — це те саме, що ми детально розбирали на третій лекції на прикладі `console.log("1")`, `setTimeout`, `console.log("4")`: колбек `fs.readFile` потрапляє в чергу задач і чекає, доки «каса» звільниться від усього синхронного коду, включно з рядком одразу під ним. Саме завдяки цій моделі один-єдиний процес Node.js може обслуговувати тисячі одночасних зʼєднань, не створюючи для кожного клієнта окремий важкий системний потік, — поки один запит очікує на повільну базу даних, той самий процес уже обробляє наступний.

> [!warning] Типова помилка
> Використовувати СИНХРОННІ («блокуючі») версії функцій (з суфіксом `Sync`, як `fs.readFileSync`) у реальному, робочому коді сервера, що обслуговує кількох користувачів одночасно, — під час читання великого файлу весь сервер буквально «завмирає» для АБСОЛЮТНО ВСІХ інших користувачів, а не лише для того, хто ініціював цю операцію. Синхронні методи прийнятні хіба що в одноразових скриптах командного рядка, де паралельних користувачів немає в принципі.

Уявіть це на конкретних числах. Припустімо, обробка одного запиту без звернення до бази даних триває 1 мілісекунду, а запит, що читає повільний файл синхронно, — 500 мілісекунд. Якщо десять користувачів надішлють прості, швидкі запити одразу ПІСЛЯ того, як одинадцятий користувач надіслав повільний, синхронний запит, усі десять простих запитів ЗМУШЕНІ будуть чекати ті самі 500 мілісекунд, перш ніж «каса» взагалі гляне в їхній бік, — попри те що кожен із них сам по собі виконався б миттєво. З неблокуючою версією `fs.readFile` ці десять простих запитів обробляться практично одразу, паралельно з тим, як повільний файл усе ще читається «на складі», і жоден із них не «застрягне» в черзі позаду чужої повільної операції.

> [!info] Для допитливих — libuv і пул потоків
> Сам JavaScript-код у Node.js виконується в одному потоці, так само як у браузері. Але деякі операції — робота з файловою системою, стиснення даних, DNS-резолвінг (який ми детально розбирали на першій лекції) — фізично делегуються окремій бібліотеці на нижчому рівні, libuv, яка має свій власний невеликий пул РЕАЛЬНИХ системних потоків саме для таких важких операцій. Це і є той «склад», куди «каса» передає довгі замовлення в нашій аналогії з третьої лекції, — сам JavaScript про це навіть не «знає», для нього все виглядає як звичайний асинхронний колбек чи `Promise`.

## `npm` та `package.json`

Жоден реальний Node.js-проєкт не пишеться повністю «з нуля» — практично завжди використовують готові, вже написані кимось бібліотеки (наприклад, той-таки Express, про який поговоримо трохи далі). `npm` (Node Package Manager) — стандартний менеджер пакетів, який встановлюється разом із Node.js і дозволяє завантажувати, оновлювати й керувати такими бібліотеками.

Файл `package.json` у корені проєкту — це своєрідний «рецепт», що точно описує, з яких саме інгредієнтів (бібліотек, і саме яких ВЕРСІЙ) складається проєкт, — щоб будь-хто інший, отримавши цей рецепт, міг зібрати на своєму компʼютері РІВНО ТУ САМУ «страву», не гадаючи, яку версію якої бібліотеки використати.

```json
{
  "name": "my-course-api",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node server.js",
    "dev": "node --watch server.js"
  },
  "dependencies": {
    "express": "^4.18.2"
  },
  "devDependencies": {
    "nodemon": "^3.0.1"
  }
}
```

`dependencies` — бібліотеки, потрібні програмі під час РЕАЛЬНОЇ роботи (наприклад, сам Express); `devDependencies` — інструменти, потрібні лише під час РОЗРОБКИ (лінтери, тестові фреймворки), які не встановлюють на робочому сервері в продакшені. Значок `^` перед номером версії (наприклад, `^4.18.2`) означає «можна оновлювати до будь-якої новішої версії в межах `4.x.x`, але не до `5.0.0`» — це називають семантичним версіонуванням (semver): перше число позначає «ламаючі» зміни, несумісні з попередньою версією, друге — нову функціональність без поломок, третє — виправлення дрібних помилок.

Команда `npm install` читає `package.json` і завантажує всі перелічені бібліотеки в папку `node_modules` (яку ніколи не зберігають у git — вона регенерується з `package.json` за потреби), а `npm run dev` запускає скрипт, названий `dev`, зі списку `scripts` — зручний спосіб не памʼятати напамʼять довгі команди запуску.

> [!info] Для допитливих — `package-lock.json`
> Поряд із `package.json` npm автоматично створює `package-lock.json`, який фіксує ТОЧНІ версії — не «приблизно 4.18.x», а буквально `4.18.2` — усіх бібліотек, включно з бібліотеками, від яких ЗАЛЕЖАТЬ ваші бібліотеки (залежності залежностей). Це гарантує, що збірка на вашому компʼютері й на компʼютері колеги (чи на реальному сервері) використовує РІВНО той самий набір версій, а не «приблизно той самий», що потенційно міг би поводитись інакше через дрібну відмінність версій десь глибоко в ланцюжку залежностей.

## Модулі: CommonJS проти ES-модулів

Пригадайте четверту й другу лекції: ES-модулі із синтаксисом `import`/`export` — стандартний спосіб розділити код на файли в сучасному JavaScript. Але Node.js існує з 2009 року, а ES-модулі стали офіційним стандартом мови лише в 2015-му (ES6) і повноцінно запрацювали в самому Node.js ще пізніше. Тому в Node.js історично прижилась ІНША система модулів — CommonJS, із синтаксисом `require`/`module.exports`, — і величезна кількість наявного коду й бібліотек досі написана саме так:

```js
// utils.js — CommonJS
function formatPrice(value) {
  return `${value} грн`;
}
module.exports = { formatPrice };

// server.js — CommonJS
const { formatPrice } = require("./utils.js");
```

```js
// utils.js — ES-модулі (той самий синтаксис, що ми вивчали на другій лекції)
export function formatPrice(value) {
  return `${value} грн`;
}

// server.js — ES-модулі
import { formatPrice } from "./utils.js";
```

Синтаксично різниця невелика, але це дві РІЗНІ системи, які не змішуються довільно в одному файлі. Щоб Node.js трактував `.js`-файли проєкту як ES-модулі (а не CommonJS, який досі є типовим за замовчуванням), у `package.json` додають рядок `"type": "module"` — саме це ми й бачили в прикладі `package.json` вище. У цьому курсі ми послідовно використовуватимемо ES-модулі — той самий синтаксис `import`/`export`, яким уже користувались на фронтенді, — щоб не тримати в голові дві різні системи одночасно.

> [!warning] Типова помилка
> Копіювати приклад коду з інтернету, написаний у CommonJS (`require`), у проєкт, де `package.json` уже має `"type": "module"` (отже, очікує `import`) — Node.js одразу викине помилку `require is not defined`, тому що в режимі ES-модулів `require` просто не існує як глобальна функція. Якщо в проєкті `import`/`export` — увесь код, включно зі скопійованими прикладами, має послідовно використовувати саме цей синтаксис.

Ще одна дрібниця, яка регулярно спантеличує при переході з CommonJS на ES-модулі: у старому CommonJS-коді часто зустрічаються глобальні змінні `__dirname` і `__filename` — шлях до поточної папки й файлу відповідно, потрібні, наприклад, щоб коректно побудувати шлях до статичних файлів незалежно від того, звідки саме запущено сервер. У режимі ES-модулів цих змінних не існує взагалі — їхній еквівалент отримують через `import.meta.url`:

```js
import { fileURLToPath } from "url";
import { dirname } from "path";

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
```

Це виглядає громіздкіше за просте звернення до готової змінної `__dirname` у CommonJS, і саме тому в наявному, старому коді ви ще довго зустрічатимете CommonJS навіть у нових на перший погляд прикладах, — але для послідовності з рештою курсу ми й надалі використовуємо ES-модулі.

## Перший сервер: від `http` до Express

У Node.js уже вбудований низькорівневий модуль `http`, здатний самостійно приймати HTTP-запити й повертати HTTP-відповіді — той самий протокол, який ми детально розбирали на найпершій лекції курсу, лише тепер ми опиняємось по ІНШИЙ бік цієї взаємодії, у ролі «кухні», а не «клієнта за столиком».

```js
import { createServer } from "http";

const server = createServer((req, res) => {
  if (req.url === "/" && req.method === "GET") {
    res.writeHead(200, { "Content-Type": "text/plain" });
    res.end("Головна сторінка");
  } else if (req.url === "/courses" && req.method === "GET") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify([{ id: 1, title: "Веб-програмування" }]));
  } else {
    res.writeHead(404, { "Content-Type": "text/plain" });
    res.end("Сторінку не знайдено");
  }
});

server.listen(3000, () => console.log("Сервер запущено на порту 3000"));
```

Тут одразу впізнаються поняття з першої лекції — метод (`req.method`), шлях (`req.url`), статус-код (`res.writeHead(200, ...)` чи `404`), заголовок `Content-Type`. Але зверніть увагу, наскільки багато ручної, повторюваної роботи вже в цьому маленькому прикладі з усього двома маршрутами: доводиться вручну порівнювати `req.url` та `req.method` через ланцюжок `if`/`else if`, вручну виставляти заголовки, вручну перетворювати дані на JSON-рядок. Для реального застосунку з десятками маршрутів, параметрами шляху, розбором тіла запиту такий підхід швидко стає громіздким і крихким — це схоже на те, щоб будувати меблі, самостійно розпилюючи кожну дошку з необробленого стовбура дерева, замість того щоб скористатись уже готовим, продуманим набором деталей конструктора.

Express — саме такий «готовий конструктор» поверх низькорівневого модуля `http`: він бере на себе всю повторювану, рутинну роботу з розбору запитів і маршрутизації, залишаючи вам змогу зосередитись на самій логіці застосунку.

```js
import express from "express";

const app = express();

app.get("/", (req, res) => {
  res.send("Головна сторінка");
});

app.get("/courses", (req, res) => {
  res.json([{ id: 1, title: "Веб-програмування" }]);
});

app.listen(3000, () => console.log("Сервер запущено на порту 3000"));
```

Той самий сервер, та сама функціональність — але замість ручного `if (req.url === "/courses" && req.method === "GET")` тепер просто `app.get("/courses", ...)`, і замість ручного `JSON.stringify` та виставляння заголовка `Content-Type` — просто `res.json(...)`, який робить обидві ці речі сам, автоматично.

## Маршрути в Express

Express пропонує по одному методу на кожен HTTP-метод із таблиці, яку ми детально розбирали на першій лекції, — і назви цих методів Express буквально повторюють HTTP-методи:

```js
app.get("/products", (req, res) => { /* отримати список товарів */ });
app.post("/products", (req, res) => { /* створити новий товар */ });
app.put("/products/:id", (req, res) => { /* замінити товар повністю */ });
app.patch("/products/:id", (req, res) => { /* частково оновити товар */ });
app.delete("/products/:id", (req, res) => { /* видалити товар */ });
```

`:id` тут — це параметр шляху, той самий принцип, що й `:courseId` у React Router на сьомій лекції, лише тепер із протилежного, серверного боку: замість того щоб ЧИТАТИ параметр через `useParams`, сервер його ОГОЛОШУЄ в шляху маршруту, а читає — через `req.params`:

```js
app.get("/products/:id", (req, res) => {
  const { id } = req.params; // { id: "42" } для GET /products/42
  const product = findProductById(id);

  if (!product) {
    res.status(404).json({ message: "Товар не знайдено" });
    return;
  }

  res.json(product);
});
```

Зверніть увагу на `res.status(404).json(...)` — це той самий принцип «ланцюжка викликів», побудований так, щоб рядок коду читався природно: спершу встановити статус-код відповіді (пригадайте категорії статус-кодів із першої лекції — `4xx` означає помилку саме на боці клієнта, тут конкретно — запитаний ресурс не існує), а потім одразу відправити тіло відповіді у форматі JSON.

Окрім параметрів ШЛЯХУ (`:id`), URL часто містить і параметри рядка запиту (query string) — усе, що йде після знаку `?` в адресі, наприклад `/products?category=laptops&sort=price`. Express автоматично розбирає їх у зручний обʼєкт `req.query`:

```js
app.get("/products", (req, res) => {
  const { category, sort } = req.query; // { category: "laptops", sort: "price" }
  const filtered = filterProducts(category, sort);
  res.json(filtered);
});
```

Практична різниця між ними варта окремого наголосу: параметр шляху (`:id`) використовують для ідентифікації КОНКРЕТНОГО ресурсу — «цей самий товар, і жоден інший», тоді як параметри рядка запиту — для НЕОБОВʼЯЗКОВИХ уточнень запиту до ЦІЛОГО списку — фільтрів, сортування, пагінації, — без яких маршрут усе одно спрацює, просто поверне неотфільтрований результат.

Насамкінець — маршрут `POST`, що приймає дані ВІД клієнта, той самий сценарій, який ми детально розглядали на третій і сьомій лекціях із боку `fetch`. Тепер подивімось на нього з протилежного, серверного боку:

```js
app.post("/products", (req, res) => {
  const { name, price } = req.body; // дані з тіла POST-запиту
  const newProduct = { id: generateId(), name, price };
  products.push(newProduct);
  res.status(201).json(newProduct);
});
```

Щоб `req.body` взагалі був заповнений, а не залишався `undefined`, Express потрібно ЯВНО сказати розібрати тіло запиту як JSON — сам собою він цього не робить із міркувань продуктивності: не кожен маршрут очікує JSON у тілі, тож розбирати його «про всяк випадок» на кожному запиті було б зайвою роботою.

```js
app.use(express.json()); // без цього рядка req.body буде undefined для JSON-запитів
```

Цей рядок — наш перший погляд на middleware (проміжне програмне забезпечення) в Express: функцію, що обробляє запит ще ДО того, як він дістанеться конкретного маршруту. Детально middleware — його механізм, порядок виконання, написання власного — розберемо вже на наступній лекції; поки що досить запамʼятати, що без `express.json()` тіло POST/PUT/PATCH-запитів у форматі JSON просто не буде розібране в зручний обʼєкт `req.body`.

Зверніть увагу й на статус-код `201 Created` замість звичного `200 OK` — пригадайте таблицю категорій статус-кодів із першої лекції: `201` — це більш точна, конкретна відповідь саме для успішного СТВОРЕННЯ нового ресурсу, на відміну від загального «усе добре» в `200`.
