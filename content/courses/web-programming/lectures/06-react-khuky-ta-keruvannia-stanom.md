# React-хуки та керування станом

> [!abstract] Коротко
> Хуки – спосіб дати функціональному компоненту «памʼять» і доступ до можливостей React, які раніше вимагали класів. Розглянемо `useState` глибше, побічні ефекти через `useEffect`, прямий доступ до DOM через `useRef`, оптимізацію через `useMemo`/`useCallback`, побудову власних хуків і розвʼязання проблеми prop drilling через Context.

## Навчальні цілі

1. Пояснити, чому хуки можна викликати лише на верхньому рівні компонента, і як це повʼязано із замиканнями з другої лекції.
2. Оновлювати стан-обʼєкти й стан-масиви незмінно (immutably), через spread.
3. Використовувати `useEffect` для побічних ефектів із правильним масивом залежностей і функцією очищення.
4. Застосовувати `useRef` для доступу до DOM і збереження значень між рендерами без перерендеру.
5. Оптимізувати компоненти через `useMemo`/`useCallback` і виносити повторювану логіку у власні хуки.
6. Розвʼязувати проблему prop drilling через Context.

## План лекції

1. Хуки та правила їх виклику
2. `useState` глибше: обʼєкти, масиви, лінива ініціалізація
3. `useEffect`: побічні ефекти та очищення
4. `useRef`: доступ до DOM і значення без перерендеру
5. `useMemo` та `useCallback`: memoization
6. Власні хуки
7. Context: розвʼязання prop drilling

## Хуки та правила їх виклику

На попередній лекції ми залишили відкритим одне питання: як саме `useState` умудряється «памʼятати» значення лічильника між викликами функції-компонента, якщо компонент – це звичайна функція, а звичайні функції, як ми знаємо з другої лекції, забувають усі свої локальні змінні одразу після завершення виконання? Відповідь – замикання (closures), той самий механізм, який ми детально розбирали на другій лекції на прикладі функції `createCounter`, що «носила з собою рюкзак» зі змінною `count`. React, за лаштунками, підтримує окремий масив «комірок памʼяті» для кожного екземпляра компонента, і кожен виклик хука – це, по суті, звернення до чергової комірки в цьому масиві: перший виклик `useState` у компоненті звертається до комірки номер один, другий виклик `useState` (чи `useRef`, чи будь-якого іншого хука) – до комірки номер два, і так по черзі.

Саме звідси випливає найважливіше й найсуворіше правило хуків, яке варто запамʼятати міцно: хуки МОЖНА викликати лише на верхньому рівні тіла компонента, і НІКОЛИ – всередині `if`, циклів чи вкладених функцій. Уявіть гардероб із пронумерованими гачками, де кожен відвідувач отримує свій одяг за НОМЕРОМ гачка, а не за імʼям, – і гардеробник видає речі строго в тому порядку, в якому люди підходили. Якщо цього разу відвідувач підійшов до гардероба не в тому порядку, що минулого разу (наприклад, тому що якийсь `if` вирішив «цього разу пропустимо третій гачок»), гардеробник видасть речі переплутано – не той одяг не тому власнику. React рахує «комірки пам�ʼяті» для хуків так само – за порядком виклику, а не за іменем змінної чи якимось іншим ідентифікатором, – і якщо порядок викликів хуків зміниться між двома рендерами того самого компонента (а це неминуче станеться, якщо хук викликати всередині умови), React переплутає, яке значення якому хуку належить.

```jsx
// НЕПРАВИЛЬНО
function Counter({ showCounter }) {
  if (showCounter) {
    const [count, setCount] = useState(0); // хук усередині if – заборонено
  }
  // ...
}

// ПРАВИЛЬНО
function Counter({ showCounter }) {
  const [count, setCount] = useState(0); // завжди на верхньому рівні, у тому самому порядку
  if (!showCounter) return null;
  // ...
}
```

> [!exam] На іспиті
> Питання «чому хуки не можна викликати умовно» перевіряють майже завжди, і правильна відповідь обовʼязково має пояснювати механізм: React ідентифікує кожен хук за ПОРЯДКОМ виклику всередині компонента, а не за іменем, тому порядок викликів має бути ІДЕНТИЧНИМ на кожному рендері одного й того самого компонента.

Простежимо покроково, ЩО САМЕ піде не так у «неправильному» прикладі вище, якщо React дійсно дозволив би такий код (насправді він або кине помилку, або поведінка стане непередбачуваною – розберемо чому саме). Уявіть, що на першому рендері `showCounter` дорівнює `true`: гардеробник видає перший гачок під `useState(0)` (лічильник), і якщо в компоненті нижче є ще один хук, наприклад `useRef`, він отримує другий гачок. На наступному рендері, якщо `showCounter` раптом стає `false`, виклик `useState(0)` усередині `if` просто НЕ відбувається – компонент одразу перескакує до хука, що йшов раніше «другим». Але гардеробник (React) не знає, що трапилось, – він просто видає ПЕРШИЙ доступний гачок наступному хуку в черзі викликів, тобто тому самому `useRef`, який минулого разу отримав другий гачок. Тепер `useRef` отримує дані, які насправді належали лічильнику `count`, – типи даних переплутані, і компонент або впаде з помилкою, або, що ще гірше, почне тихо працювати з чужими, неправильними даними.

## `useState` глибше: обʼєкти, масиви, лінива ініціалізація

На попередній лекції стан у нас завжди був простим примітивом – числом чи булевим значенням. На практиці стан часто є обʼєктом чи масивом, і тут прямо застосовується все, що ми детально розбирали на другій лекції про примітиви й посилання в памʼяті. Пригадайте: React визначає, чи потрібно перерендерити компонент після виклику `setState`, порівнюючи НОВЕ значення зі СТАРИМ саме ЗА ПОСИЛАННЯМ – так само, як `const user = { ... }` і мутація `user.name = "..."` не створюють нового посилання. Якщо ви спробуєте оновити обʼєкт стану прямою мутацією, React просто не помітить зміни, адже посилання лишилось тим самим:

```jsx
const [user, setUser] = useState({ name: "Ірина", age: 25 });

// НЕПРАВИЛЬНО – мутація напряму, React не побачить різниці
user.age = 26;
setUser(user); // те саме посилання, що й було – рендеру не станеться

// ПРАВИЛЬНО – новий обʼєкт через spread, знайомий з другої лекції
setUser({ ...user, age: 26 });
```

Той самий принцип працює й для масивів у стані – додавання, видалення чи зміна елемента робиться через створення НОВОГО масиву, а не мутацію наявного методами на кшталт `push` чи `splice`, які змінюють масив «на місці», не створюючи нового посилання:

```jsx
const [items, setItems] = useState([]);

setItems([...items, newItem]);                      // додати
setItems(items.filter(item => item.id !== idToRemove)); // видалити
setItems(items.map(item => item.id === id ? { ...item, done: true } : item)); // оновити один
```

У кожному з цих трьох рядків ми буквально повторюємо той самий шаблон spread + `filter`/`map`, який детально вивчали на другій лекції, – тепер він виявляється фундаментом усього керування станом у React: замість мутації даних щоразу будують НОВУ версію структури, залишаючи стару недоторканою.

Ситуація ускладнюється, коли обʼєкт стану має ВКЛАДЕНУ структуру – обʼєкт усередині обʼєкта. Spread-оператор, як ми зауважували на другій лекції, копіює лише ОДИН рівень углиб (це називають неглибоким, shallow копіюванням): якщо просто написати `{ ...user, address: user.address }`, вкладений обʼєкт `address` не копіюється, а лишається тим самим посиланням, що й був. Щоб дійсно незмінно оновити вкладене поле, spread доводиться застосовувати на КОЖНОМУ рівні вкладеності, який реально змінюється:

```jsx
const [user, setUser] = useState({ name: "Ірина", address: { city: "Київ", zip: "01001" } });

// оновлюємо лише місто, залишаючи решту адреси й імʼя недоторканими
setUser({
  ...user,
  address: { ...user.address, city: "Львів" }
});
```

Саме через цю зростаючу «драбину» вкладених spread-операторів на глибоко вкладених структурах даних складні форми чи глобальний стан застосунку часто виносять в окремі бібліотеки керування станом (Redux, Zustand та подібні), які автоматизують цю незмінну оновлюваність, – але сам ПРИНЦИП незмінності лишається той самий, який ми щойно розібрали вручну.

Насамкінець – лінива ініціалізація. Якщо початкове значення стану обчислюється через щось відносно затратне (наприклад, читання й розбір великого обʼєкта з `localStorage`), варте уваги: `useState(computeInitialValue())` викликає `computeInitialValue()` ПРИ КОЖНОМУ рендері компонента, навіть попри те, що результат реально використовується лише один-єдиний раз – при найпершому створенні компонента. Щоб уникнути цих зайвих обчислень на кожному повторному рендері, `useState` можна передати ФУНКЦІЮ замість готового значення – і React викличе її рівно один раз:

```jsx
const [settings, setSettings] = useState(() => computeInitialValue()); // викликається лише один раз
```

## `useEffect`: побічні ефекти та очищення

Дотепер усе, що робив компонент, – це ОПИСУВАВ інтерфейс на основі даних: чисту, декларативну функцію «дані на вході → JSX на виході», без жодних побічних дій назовні. Але реальні застосунки постійно потребують чогось, що виходить за межі самого рендеру: завантажити дані з сервера через `fetch` (третя лекція), підписатись на подію (теж третя лекція), запустити таймер. React навмисно відокремлює ці «побічні ефекти» від самого рендеру в окремий хук – `useEffect` – і причина цього розділення варта пояснення. Уявіть фотографа, який робить знімок кімнати (це і є рендер – опис того, як зараз виглядає інтерфейс): сам процес фотографування має бути чистим і передбачуваним, без стороннього втручання, – а от ПІСЛЯ того, як знімок зроблено, фотограф цілком може, наприклад, надіслати цей знімок клієнту поштою. Надсилання поштою – це «побічний ефект», який відбувається ПІСЛЯ основної дії (фотографування) і не повинен впливати на сам процес зйомки.

```jsx
import { useState, useEffect } from "react";

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then(response => response.json())
      .then(data => setUser(data));
  }, [userId]); // масив залежностей

  if (!user) return <p>Завантаження...</p>;
  return <h2>{user.name}</h2>;
}
```

Другий аргумент `useEffect` – масив залежностей – визначає, ПІСЛЯ ЯКИХ САМЕ змін ефект потрібно повторно запустити. React порівнює значення в цьому масиві з тим, якими вони були на попередньому рендері (тим самим порівнянням за значенням для примітивів і за посиланням для обʼєктів, яке ми детально розбирали на другій лекції), і якщо хоч одне з них справді змінилось – запускає ефект знову. Порожній масив `[]` означає «запустити ефект рівно один раз, одразу після першого рендеру, і більше ніколи» – типовий патерн для одноразового завантаження даних при появі компонента. Відсутність масиву взагалі (просто `useEffect(() => {...})` без другого аргументу) означає «запускати ефект ПІСЛЯ КОЖНОГО рендеру без винятку» – на практиці так роблять рідко, здебільшого ненавмисно, і це часто джерело продуктивних проблем.

Розберемо ще одну класичну пастку – цього разу з протилежного боку, коли масив залежностей ЗАБУВАЮТЬ узагалі, а не пропускають конкретну залежність усередині нього. Уявіть компонент, що всередині ефекту оновлює власний стан, спираючись на дані, отримані з сервера:

```jsx
function BadCounter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    setCount(count + 1); // немає масиву залежностей узагалі!
  });

  return <p>{count}</p>;
}
```

Простежимо, чому це призводить до нескінченного циклу. Компонент рендериться вперше, `count` дорівнює `0`. Оскільки другого аргументу `useEffect` немає взагалі, React запускає ефект ПІСЛЯ КОЖНОГО рендеру без винятку. Ефект викликає `setCount(count + 1)`, що змінює стан на `1` – а зміна стану, як ми знаємо, викликає повторний рендер. Цей повторний рендер знову запускає той самий ефект (бо масиву залежностей немає, і React не має підстав його ПРОПУСТИТИ), той знову викликає `setCount`, знову змінюючи стан, – і так до нескінченності, поки браузер фізично не «зависне», намагаючись встигнути за шаленою швидкістю перерендерів. Виправлення тут – або додати порожній масив `[]`, щоб ефект спрацював рівно один раз, або, якщо `count` дійсно має оновлюватись у відповідь на щось зовнішнє, прибрати цю логіку з `useEffect` узагалі й покласти в звичайний обробник події.

> [!warning] Типова помилка
> Забути вказати `userId` у масиві залежностей ефекту, що використовує `userId` усередині. Компонент завантажить дані для першого користувача, а потім, якщо `userId` зміниться (наприклад, користувач перейшов на профіль іншої людини), НЕ перезавантажить їх заново – ефект просто не спрацює повторно, і на екрані застрягнуть старі дані попереднього користувача. React навіть попереджає про це в консолі під час розробки, якщо ESLint-плагін для хуків налаштований правильно.

Іноді побічний ефект потребує «прибирання» за собою при завершенні – наприклад, якщо ви підписались на подію через `addEventListener`, детально розглянутий на третій лекції, і компонент зникає зі сторінки, слухач події лишиться «висіти» назавжди, якщо його не зняти явно, – витік памʼяті, коли компонента вже немає на екрані, а браузер усе одно продовжує викликати для нього код. Для цього функція, передана в `useEffect`, може повернути ІНШУ функцію – функцію очищення (cleanup), яку React викликає перед тим, як запустити ефект заново (через зміну залежностей) або коли компонент остаточно зникає зі сторінки:

```jsx
useEffect(() => {
  function handleResize() {
    console.log("Розмір вікна змінився");
  }

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize); // прибираємо за собою
  };
}, []);
```

> [!info] Для допитливих – навіщо функція очищення саме ТАКА
> Функція очищення викликається React АВТОМАТИЧНО перед КОЖНИМ повторним запуском ефекту (коли залежності змінюються) і при видаленні компонента – тобто «підписка» й «відписка» завжди йдуть парою, симетрично, і про це не потрібно памʼятати вручну в кожному місці, де компонент може зникнути зі сторінки. Це прямий аналог до `try`/`finally` з другої лекції: `finally` виконується завжди, незалежно від результату; функція очищення `useEffect` теж виконується завжди, незалежно від того, ЧОМУ саме ефект перезапускається.

## `useRef`: доступ до DOM і значення без перерендеру

Іноді потрібно зберегти якесь значення МІЖ рендерами компонента, але так, щоб ЗМІНА цього значення НЕ викликала перерендер, – на відміну від `useState`, де кожен виклик `setState` саме й запускає перерендер. `useRef` створює обʼєкт із єдиною властивістю `.current`, значення якої можна вільно читати й змінювати напряму, і ця зміна ніяк не «повідомляє» React про потребу оновити інтерфейс:

```jsx
function Timer() {
  const secondsRef = useRef(0);

  useEffect(() => {
    const intervalId = setInterval(() => {
      secondsRef.current = secondsRef.current + 1; // не викликає перерендер
    }, 1000);

    return () => clearInterval(intervalId);
  }, []);

  return <p>Компонент запущено (перевірте secondsRef.current у консолі)</p>;
}
```

Друге, ще практичніше застосування `useRef` – прямий доступ до реального DOM-вузла, коли декларативного підходу React недостатньо й потрібно, наприклад, програмно поставити фокус на поле вводу. Пригадайте третю лекцію: там ми знаходили DOM-елементи вручну через `document.querySelector`. У React так робити не заведено – замість пошуку елемента постфактум, React дозволяє «попросити» посилання на конкретний DOM-вузол ще на етапі опису розмітки, через спеціальний атрибут `ref`:

```jsx
function SearchInput() {
  const inputRef = useRef(null);

  useEffect(() => {
    inputRef.current.focus(); // прямий виклик DOM-методу, як на третій лекції
  }, []);

  return <input ref={inputRef} type="text" />;
}
```

Після першого рендеру React сам заповнює `inputRef.current` реальним DOM-вузлом цього конкретного `<input>`, і далі з ним можна працювати напряму тими самими методами DOM API, які ми вивчали на третій лекції, – `.focus()`, `.scrollIntoView()`, читання `.value` для некерованих полів форми. `useRef` – це, по суті, свідомий «аварійний люк» із декларативного світу React назад в імперативний світ прямої роботи з DOM, і використовують його саме тоді, коли для конкретної задачі декларативного способу справді не існує.

## `useMemo` та `useCallback`: memoization

Пригадайте HTTP-кешування з першої лекції: замість того щоб щоразу заново «готувати те саме блюдо», сервер (чи браузер) повторно використовує вже готовий результат, якщо нічого не змінилось. `useMemo` й `useCallback` застосовують ту саму ідею кешування, лише не до мережевих запитів, а до обчислень і функцій усередині компонента React.

`useMemo` запамʼятовує РЕЗУЛЬТАТ обчислення й перераховує його заново лише тоді, коли справді змінились залежності, перелічені в масиві, – так само, як другий аргумент `useEffect`:

```jsx
function ProductList({ products, filterText }) {
  const filteredProducts = useMemo(() => {
    console.log("Фільтруємо заново..."); // виведеться лише коли products чи filterText реально зміняться
    return products.filter(p => p.name.includes(filterText));
  }, [products, filterText]);

  return <ul>{filteredProducts.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}
```

Без `useMemo` вираз `products.filter(...)` виконувався б ПРИ КОЖНОМУ рендері компонента `ProductList`, навіть якщо цей рендер стався через зміну чогось геть іншого, ніяк не повʼязаного зі списком товарів чи текстом фільтра, – марна повторна робота. `useMemo` «кешує» результат фільтрації, немов той самий `ETag` з першої лекції: якщо «інгредієнти» (залежності) не змінились, повторно віддається вже готовий результат замість того, щоб «готувати страву» заново.

`useCallback` – по суті той самий принцип, але для ФУНКЦІЙ, а не для значень: він кешує саме посилання на функцію між рендерами, доки залежності не зміняться. Навіщо кешувати посилання на функцію, а не просто «пережити» те, що функція створюється заново? Пригадайте знову другу лекцію: кожне оголошення функції – навіть з абсолютно однаковим тілом коду – створює НОВЕ посилання в памʼяті. Якщо ця функція передається дочірньому компоненту пропсом, і дочірній компонент оптимізований через `React.memo` (пропускає повторний рендер, якщо пропси не змінились ЗА ПОСИЛАННЯМ), нова функція при кожному рендері батька означатиме, що пропс «змінився» щоразу, навіть якщо фактична поведінка функції та сама, – і оптимізація дочірнього компонента виявиться марною.

```jsx
function ProductList({ products }) {
  const handleAddToCart = useCallback((productId) => {
    console.log("Додано в кошик:", productId);
  }, []); // те саме посилання на функцію між рендерами, доки масив залежностей порожній

  return products.map(p => <ProductCard key={p.id} product={p} onAdd={handleAddToCart} />);
}
```

> [!warning] Типова помилка
> Обгортати геть УСІ обчислення й функції в `useMemo`/`useCallback` «про всяк випадок», сподіваючись, що це саме по собі пришвидшить компонент. Сама memoization теж коштує ресурсів – React мусить зберігати попередні залежності й порівнювати їх на кожному рендері, – тому для дешевих обчислень (простий арифметичний вираз, коротка функція без важких дочірніх оптимізацій) накладні витрати на саму перевірку можуть перевищити виграш від пропущеного повторного обчислення. `useMemo`/`useCallback` виправдані там, де обчислення дійсно ВАЖКЕ (сортування чи фільтрація великого масиву) або де посилання на функцію реально впливає на оптимізацію дочірнього компонента через `React.memo` – не скрізь підряд.

## Власні хуки

Коли та сама комбінація `useState` + `useEffect` повторюється в кількох різних компонентах – наприклад, логіка «завантажити дані з `fetch`, показати стан завантаження, обробити помилку» знадобиться і для списку товарів, і для профілю користувача, і для коментарів, – цю логіку можна винести в окрему, повторно використовувану функцію. Таку функцію називають власним хуком (custom hook), і єдина формальна вимога до неї – назва має починатися саме зі слова `use`, щоб React (і лінтер) розпізнавали її як хук і застосовували до неї ті самі правила порядку виклику, які ми обговорювали на початку лекції.

```jsx
function useFetch(url) {
  const [data, setData] = useState(null);
  const [error, setError] = useState(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    setIsLoading(true);
    fetch(url)
      .then(response => response.json())
      .then(setData)
      .catch(setError)
      .finally(() => setIsLoading(false));
  }, [url]);

  return { data, error, isLoading };
}

// використання в будь-якому компоненті
function UserProfile({ userId }) {
  const { data: user, error, isLoading } = useFetch(`/api/users/${userId}`);

  if (isLoading) return <p>Завантаження...</p>;
  if (error) return <p>Помилка завантаження</p>;
  return <h2>{user.name}</h2>;
}
```

Власний хук `useFetch` тут – це просто звичайна JavaScript-функція, що всередині використовує інші хуки (`useState`, `useEffect`), і саме тому вона сама теж підпорядковується правилу виклику лише на верхньому рівні. Практична вигода очевидна: замість того щоб копіювати ту саму логіку завантаження, обробки помилок і стану завантаження в КОЖНОМУ компоненті окремо, її пишуть один раз і повторно використовують – так само, як формочка для печива з попередньої лекції: один шаблон, багато готових результатів.

Ще один дуже поширений власний хук – `useLocalStorage`, який синхронізує стан компонента зі сховищем браузера `localStorage`, щоб дані переживали перезавантаження сторінки, – наприклад, збережена тема оформлення чи вміст незавершеної форми:

```jsx
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initialValue; // лінива ініціалізація, розглянута раніше
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// використання виглядає так само зручно, як звичайний useState
function ThemeToggle() {
  const [theme, setTheme] = useLocalStorage("theme", "light");
  return <button onClick={() => setTheme(theme === "light" ? "dark" : "light")}>{theme}</button>;
}
```

Зверніть увагу, наскільки природно тут зустрічаються практично всі теми, розглянуті на цій лекції: лінива ініціалізація стану через функцію, `useEffect` із залежностями, що синхронізує зовнішній світ (localStorage) зі станом компонента, – і все це обгорнуте в один хук, яким компонент `ThemeToggle` користується так само просто, як звичайним `useState`, зовсім не переймаючись деталями реалізації синхронізації зі сховищем.

## Context: розвʼязання prop drilling

Пригадайте проблему з попередньої лекції – «пробурювання пропсів» (prop drilling), коли дані доводиться протягувати через кілька проміжних компонентів, яким самі ці дані не потрібні, лише щоб вони дісталися глибоко вкладеного нащадка. Уявіть різницю між тим, щоб передавати записку з рук у руки через кожен кабінет офісу по черзі, і тим, щоб оголосити щось через гучномовець, який чують одразу у ВСІХ кабінетах будівлі, незалежно від того, на якому поверсі й наскільки далеко від джерела оголошення вони перебувають. Context у React – це саме такий «гучномовець»: спосіб зробити дані доступними будь-якому компоненту в піддереві, незалежно від того, скільки проміжних рівнів компонентів між постачальником даних і тим, хто їх реально використовує.

```jsx
import { createContext, useContext, useState } from "react";

const UserContext = createContext(null);

function App() {
  const [user, setUser] = useState({ name: "Ірина" });

  return (
    <UserContext.Provider value={user}>
      <Layout />
    </UserContext.Provider>
  );
}

function Layout() {
  return <Header />; // Layout навіть не знає про існування user
}

function Header() {
  return <Avatar />; // Header теж не знає
}

function Avatar() {
  const user = useContext(UserContext); // а тут дані «почуті» напряму з Context
  return <img src={user.avatarUrl} alt={user.name} />;
}
```

Побудова складається з трьох частин: `createContext` створює сам «канал звʼязку», `<UserContext.Provider value={user}>` – це «гучномовець», що транслює конкретне значення всім нащадкам усередині себе, а `useContext(UserContext)` у будь-якому вкладеному компоненті – це «приймач», який «слухає» цей канал і отримує поточне значення напряму, без жодної участі проміжних компонентів `Layout` і `Header`, які в цьому прикладі взагалі не підозрюють про існування `user`.

> [!info] Для допитливих – Context не панацея від усього
> Context чудово розвʼязує prop drilling, але не варто одразу обгортати НАЙМЕНШУ дрібницю в Context «про всяк випадок»: кожна зміна значення в `Provider` викликає перерендер УСІХ компонентів-нащадків, що використовують цей Context через `useContext`, навіть якщо конкретному компоненту потрібна лише крихітна частина цих даних. Для локальних, невеликих дерев компонентів звичайні пропси часто лишаються простішим і продуктивнішим рішенням; Context найбільш виправданий саме для дійсно ГЛОБАЛЬНИХ даних – теми оформлення, залогіненого користувача, мови інтерфейсу – потрібних у багатьох, розкиданих по різних гілках дерева місцях одночасно.
