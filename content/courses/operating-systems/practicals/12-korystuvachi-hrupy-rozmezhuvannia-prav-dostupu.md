# Користувачі, групи та розмежування прав доступу

> [!abstract] Пов'язана лекція
> [[courses/operating-systems/lectures/10-bezpeka-ta-keruvannia-dostupom|Лекція 10. Безпека та керування доступом]]. Робота присвячена користувачам, групам і розширеним правам доступу в Linux.

## Навіщо ця робота

Базових дев'яти бітів прав достатньо для простих випадків, але реальні системи вимагають тонкішого контролю: спільні каталоги для команди, привілеї окремих команд без пароля root, окремі права для аудиторів. Помилка тут це або «дірка» в безпеці, або «нічого не працює».

Ви створите користувачів і групу проєкту, налаштуєте спільний каталог із бітом setgid, подивитеся на програми з setuid і дозвольте окремому користувачеві єдину команду через sudo.

## Мета

Навчитися керувати користувачами й групами, налаштовувати спільні каталоги (setgid), розуміти setuid, налаштовувати sudo й ACL.

Після заняття ви повинні вміти:

- створювати користувачів і групи;
- налаштовувати каталог з правами 2770;
- знаходити програми setuid;
- обмежувати sudo однією командою;
- використовувати ACL;

## Обладнання та програмне забезпечення

- Віртуальна машина з Linux і правами адміністратора, утиліти useradd, usermod, groupadd, chmod, chown, sudo, getfacl.

Усі приклади розраховано на Ubuntu 22.04 або новішу у віртуальній машині (VirtualBox або WSL2). Працюйте від звичайного користувача; `sudo` потрібен лише там, де це вказано. Не виконуйте експериментів на робочій системі, де є важливі дані: усе, що змінює розділи, права чи ядро, робіть у віртуальній машині, зробивши знімок стану перед початком.

## Теоретична частина

Ядро оперує числовими ідентифікаторами користувачів і груп. Права визначаються дев'ятьма бітами для власника, групи та інших; додаткові біти setuid, setgid і sticky розв'язують окремі задачі. Біт setgid на каталозі змушує нові файли успадковувати групу каталогу, що є типовим способом організації спільної теки відділу. Правило найменших привілеїв вимагає надавати рівно ті права, які потрібні для роботи, і не більше. Легальне підвищення привілеїв виконується через sudo з журналюванням кожної дії.

**setgid на каталозі (2xxx)**: нові об'єкти успадковують групу каталогу, а не основну групу творця. **setuid на програмі (4xxx)**: програма виконується з правами власника файлу (наприклад, `passwd` змінює `/etc/shadow` від імені root). **sudo** дозволяє виконувати окремі команди з підвищеними правами за правилами `/etc/sudoers` (редагувати лише `visudo`). **ACL** додають права конкретним користувачам і групам понад класичні дев'ять бітів.

## Хід роботи

Нижче кожен крок із методички доповнено поясненням: що саме робити, як і навіщо. Не пропускайте пояснень: вони вказують, на що звертати увагу й чого очікувати.

### Крок 1. Створіть двох користувачів і групу проєкту, додайте обох до групи

Виконайте: `sudo groupadd proj; sudo useradd -m -G proj anna; sudo useradd -m -G proj petro; sudo passwd anna` (пароль задайте самостійно, не використовуйте реальні). Перевірте `id anna`.

### Крок 2. Створіть спільний каталог, призначте йому власника, групу та права 2770

Створіть каталог: `sudo mkdir /srv/proj; sudo chown root:proj /srv/proj; sudo chmod 2770 /srv/proj`. Перевірте `ls -ld /srv/proj`: побачите `drwxrws---`.

### Крок 3. Поясніть, що саме дає кожна цифра, зокрема двійка попереду

Розбір: перша цифра 2 це setgid, 7 для власника (rwx), 7 для групи (rwx), 0 для решти. Літера `s` у групі замінює `x`.

### Крок 4. Від імені кожного користувача створіть файли й перевірте, яку групу вони отримали

Від імені Анни створіть файл: `sudo -u anna touch /srv/proj/a.txt`; `ls -l /srv/proj`: група файлу `proj`, а не `anna`. Це наслідок setgid.

### Крок 5. Перевірте, що сторонній користувач не має доступу до каталогу

Створіть третього користувача `sudo useradd -m ivan` і спробуйте `sudo -u ivan ls /srv/proj`: «Permission denied».

### Крок 6. Знайдіть у системі програми з бітом setuid і поясніть призначення двох із них

Знайдіть setuid: `find /usr/bin /bin -perm -4000 -ls 2>/dev/null`. Опишіть дві програми (`passwd`, `sudo`) і чому їм потрібні права root.

### Крок 7. Налаштуйте дозвіл одному користувачеві виконувати одну конкретну команду через sudo

Дайте Петру право виконувати лише `systemctl restart nginx`: через `sudo visudo -f /etc/sudoers.d/petro` додайте рядок `petro ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx`. Перевірте `sudo -l -U petro`.

## Приклад виконання

ACL для задачі з самостійної частини:

```bash
sudo groupadd dev; sudo groupadd audit
sudo mkdir /srv/data; sudo chown root:dev /srv/data; sudo chmod 770 /srv/data
sudo setfacl -m g:audit:rx /srv/data
getfacl /srv/data
```

## Завдання для самостійного виконання

Розв'яжіть задачу: до каталогу потрібен повний доступ групі розробників, доступ лише для читання групі аудиторів і жодного доступу решті. Поясніть, чому дев'яти бітів недостатньо, і реалізуйте розв'язок списком контролю доступу.

Класична схема дає лише одну групу й одного власника. Щоб надати різні права двом групам, потрібні ACL (`setfacl`/`getfacl`); альтернатива це складна ієрархія вкладених груп.

## Типові помилки

- Редагувати sudoers не через `visudo`.
- Видавати `ALL=(ALL) NOPASSWD: ALL` будь-кому.
- Залишати тестових користувачів із простими паролями.
- Забувати, що членство в групі діє лише після нового входу.

## Контрольні питання

1. Чим реальний ідентифікатор користувача відрізняється від ефективного?
2. Що дає біт setgid на каталозі?
3. Навіщо потрібен біт sticky і де він застосовується?
4. Чому програми з setuid є потенційно небезпечними?
5. Коли класичної моделі прав недостатньо?

## Вимоги до звіту

Звіт подається без титульного листа й містить:

1. Тему та мету роботи.
2. Умову завдання (номер варіанта).
3. Хід виконання роботи зі скриншотами ключових кроків.
4. Результати виконання завдань (вихідний код, схеми, конфігурації або протоколи вимірювань, залежно від роботи).
5. Відповіді на контрольні питання.
6. Висновки.

Скриншоти мають показувати термінал із запрошенням (ім'я користувача, ім'я машини, поточний каталог) і виведення команд повністю, а не обрізаним. Текстові результати (таблиці, виведення програм) краще вставляти текстом у блоках коду: це дозволяє перевірити їх пошуком. Код програм додавайте у звіт повністю, з коментарями.
