# Обмеження ресурсів процесів: cgroups v2 і ulimit

> [!abstract] Пов'язана лекція
> [[courses/operating-systems/lectures/03-planuvannia-protsesiv|Лекція 3. Планування процесів]], [[courses/operating-systems/lectures/11-virtualizatsiia-ta-konteinery|Лекція 11. Віртуалізація та контейнери]]. Ви навчитеся обмежувати пам'ять, процесор і кількість процесів для групи програм та побачите, як це лежить в основі контейнерів.

## Навіщо ця робота

Одна програма з помилкою може «з'їсти» всю пам'ять і покласти сервер, а нескінченний цикл може забрати всі ядра. Тому ОС дозволяє встановлювати для процесів ліміти. Найпростіші (`ulimit`) діють на окремий процес. Потужніші (контрольні групи, cgroups) обмежують цілу групу процесів і є основою контейнерів: коли ви вказуєте `docker run --memory=200m`, насправді змінюється файл у cgroup.

У роботі ви на практиці перевірите, що відбувається, коли програма перевищує ліміт, і зрозумієте, звідки береться ізоляція ресурсів у сучасних системах.

## Мета

Навчитися встановлювати обмеження ресурсів за допомогою ulimit та cgroups v2, спостерігати спрацювання обмежень і розуміти зв'язок cgroups із контейнеризацією.

Після заняття ви повинні вміти:

- переглядати й змінювати ліміти ulimit;
- створювати групу cgroup v2 і задавати ліміти пам'яті та процесора;
- запускати процеси у групі;
- спостерігати завершення процесу через перевищення ліміту (OOM);
- користуватися systemd-run для тимчасових обмежень;

## Обладнання та програмне забезпечення

Комп'ютер або віртуальна машина з Ubuntu 22.04 і новішою (VirtualBox, WSL2). Для роботи потрібні права `sudo`. Перед початком зробіть знімок віртуальної машини: усе, що змінює диски й сервіси, можна буде швидко відкотити.

## Теоретична частина

**ulimit** задає граничні значення для процесу оболонки та її нащадків (відкриті файли, розмір стека, кількість процесів). **cgroups v2** це ієрархія груп у файловій системі `/sys/fs/cgroup`, де кожен контролер (memory, cpu, pids, io) налаштовується файлами. `memory.max` обмежує пам'ять; при перевищенні ядро завершує процес групи (OOM killer). `cpu.max` має формат `квота період`: `20000 100000` означає 20 мс процесорного часу кожні 100 мс, тобто 20 % одного ядра. `pids.max` обмежує кількість процесів у групі і захищає від fork-бомби.

## Хід роботи

### Крок 1. Перегляньте ліміти оболонки

Виведіть усі ліміти `ulimit -a` і зверніть увагу на `open files` та `max user processes`. Зменшіть кількість відкритих файлів у підоболонці й переконайтеся, що вона не може відкрити більше.

```bash
ulimit -a | head
( ulimit -n 20; for i in $(seq 1 30); do exec {fd}<>/dev/null; done ) 2>&1 | tail -2
```

> [!tip] Круглі дужки створюють підоболонку: зміна ліміту не вплине на ваш основний термінал.

### Крок 2. Створіть cgroup

Переконайтеся, що система використовує cgroups v2 (`stat -fc %T /sys/fs/cgroup` має вивести `cgroup2fs`). Створіть групу та увімкніть у батьківській контролери memory, cpu, pids.

```bash
stat -fc %T /sys/fs/cgroup
echo "+memory +cpu +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
sudo mkdir /sys/fs/cgroup/lab
```

### Крок 3. Задайте ліміти

Запишіть значення в керувальні файли групи: пам'ять 100 МБ, процесор 20 %, не більше 50 процесів.

```bash
cd /sys/fs/cgroup/lab
echo 100M | sudo tee memory.max
echo "20000 100000" | sudo tee cpu.max
echo 50 | sudo tee pids.max
cat memory.max cpu.max pids.max
```

### Крок 4. Перевірте ліміт пам'яті

Запустіть у групі Python-програму, що намагається виділити 300 МБ. Щоб перенести процес у групу, запишіть його PID у файл `cgroup.procs`. Для зручності скористайтеся оболонкою: `sudo sh -c 'echo $$ > /sys/fs/cgroup/lab/cgroup.procs; exec python3 -c "a=bytearray(300*1024*1024); print(len(a))"'`.

![[attachments/os-lab07-step4.svg|820]]
*Крок 4. Процес завершено ядром: у memory.events лічильник oom_kill дорівнює 1. Вигляд терміналу Linux (приклад очікуваного виводу; ваші значення можуть відрізнятися). Джерело: власна ілюстрація автора курсу, для цього конспекту.*

### Крок 5. Перевірте ліміт процесора

Запустіть у групі нескінченний цикл і порівняйте у `top` використання CPU з лімітом. Без ліміту процес займав би 100 % ядра, з лімітом близько 20 %.

```bash
sudo sh -c 'echo $$ > /sys/fs/cgroup/lab/cgroup.procs; exec yes > /dev/null' &
top -b -n 1 | grep yes
cat /sys/fs/cgroup/lab/cpu.stat | head -5
```

### Крок 6. Скористайтеся systemd-run

Те саме можна зробити однією командою, не торкаючись файлів: systemd створить тимчасову групу й застосує ліміти.

```bash
sudo systemd-run --scope -p MemoryMax=50M -p CPUQuota=10% python3 -c "a=bytearray(200*1024*1024)"
# прибирання
sudo pkill yes; sudo rmdir /sys/fs/cgroup/lab
```

> [!tip] Саме так Docker і Kubernetes реалізують параметри `--memory` та `--cpus` для контейнерів.

## Завдання для самостійного виконання

Налаштуйте `pids.max=20` і запустіть у групі «безпечну» імітацію fork-бомби: `sh -c 'for i in $(seq 1 100); do sleep 60 & done'`. Перегляньте `pids.events` і кількість процесів у групі. Поясніть, чому без ліміту подібна програма небезпечна.

## Індивідуальні завдання (варіанти)

Варіант обирається за порядковим номером у списку групи (якщо номер більший за 5, від нього віднімають 5 до отримання числа від 1 до 5).

| № | Зміни до базового завдання |
|---|---|
| 1 | пам'ять 100 МБ, CPU 20 %, процеси 50 |
| 2 | пам'ять 64 МБ, CPU 50 %, процеси 20 |
| 3 | ліміт швидкості запису диска (`io.max`) |
| 4 | порівняти ліміт `memory.high` (м'який) та `memory.max` (жорсткий) |
| 5 | ліміт пам'яті лише через systemd-run для служби з роботи 5 |

## Типові помилки

- Не ввімкнути контролери у `cgroup.subtree_control`.
- Помилитися з форматом `cpu.max`.
- Очікувати, що ulimit діє на інші процеси.
- Видалити групу, у якій ще є процеси.
