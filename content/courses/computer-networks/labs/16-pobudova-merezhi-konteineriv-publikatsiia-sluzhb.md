# Побудова мережі контейнерів та публікація служб

> [!abstract] Пов'язана лекція
> [[courses/computer-networks/lectures/23-merezhi-konteineriv-i-kubernetes|Лекція 23. Мережі контейнерів і Kubernetes]]. Ви створюєте користувацьку мережу Docker, запускаєте в ній два контейнери, перевіряєте зв'язність за іменами й публікуєте порт служби назовні.

## Навіщо ця робота

Контейнер це не віртуальна машина, але мережа в нього справжня: кожен контейнер отримує власний мережевий інтерфейс, адресу й таблицю маршрутизації. Docker створює віртуальні мережі, з'єднує контейнери між собою й вирішує, чи доступні вони ззовні. Усе це працює на тих самих принципах, що ви вже знаєте: підмережі, шлюзи, NAT, перенаправлення портів.

Розуміння мережі контейнерів основа для роботи з Kubernetes і сучасними застосунками, що складаються з десятків мікросервісів. У цій роботі ви створите мережу, запустите два контейнери, переконаєтеся, що вони знаходять одне одного за іменем, і відкриєте порт одного з них на зовнішню адресу.

## Мета

Навчитися створювати користувацьку мережу Docker із заданою підмережею, запускати контейнери в цій мережі, перевіряти зв'язність за іменами, публікувати порти й аналізувати мережеві налаштування контейнерів.

Після заняття ви повинні вміти:

- створювати користувацьку мережу (docker network create --subnet);
- запускати контейнери в заданій мережі й з публікацією порту;
- перевіряти зв'язність за іменем контейнера;
- аналізувати налаштування мережі (docker network inspect, ip a);
- пояснювати вплив поділу контейнерів на різні мережі;

## Обладнання та програмне забезпечення

- Персональний комп'ютер з доступом до мережі Інтернет.
- Аналізатор мережевого трафіку Wireshark, термінальний клієнт.

Потрібен **Docker**: Docker Desktop (Windows, macOS; docker.com) або Docker Engine в Linux (`sudo apt install docker.io`). Для Windows потрібне ввімкнення WSL2 чи Hyper-V. Перевірте встановлення: `docker version`. ## Теоретична частина

У контейнерному середовищі кожен контейнер отримує мережевий інтерфейс у віртуальній мережі. Служби публікують порти назовні, а вбудована служба імен дозволяє звертатися до контейнерів за назвою, а не за адресою.

### Типи мереж Docker

**bridge** мережа за замовчуванням: віртуальний міст на хості; контейнери отримують адреси з підмережі, а вихід назовні відбувається через NAT. У **користувацьких** bridge-мереж працює **вбудований DNS**: контейнери знаходять один одного за іменами. **host** контейнер користується мережею хоста. **none** без мережі.

### Публікація портів

Опція `-p 8080:80` створює правило: «пакети на порт 8080 хоста перенаправити на порт 80 контейнера». Без неї служба в контейнері доступна лише всередині Docker-мережі.

## Хід роботи

Нижче кожен крок із методички доповнено поясненням: що саме робити, як і навіщо. Не пропускайте пояснень: вони вказують, на що звертати увагу й чого очікувати.

### Крок 1. Створіть віртуальну мережу для контейнерів

**Що робити.** Створіть мережу: `docker network create --subnet 172.20.0.0/24 labnet`. Перегляньте `docker network ls` та `docker network inspect labnet`.

**Навіщо.** Явна підмережа дозволяє передбачувано планувати адреси. Мережа за замовчуванням не має вбудованого DNS для імен контейнерів.

**Очікуваний результат.** Мережа labnet зі шлюзом 172.20.0.1.

### Крок 2. Запустіть два контейнери в цій мережі

**Що робити.** Запустіть контейнери: `docker run -d --name web --network labnet -p 8080:80 nginx:alpine` та допоміжний `docker run -it --rm --name tools --network labnet alpine sh`.

**Навіщо.** Імена контейнерів стають іменами в мережі. Допоміжний контейнер потрібен для перевірок зсередини.

**Очікуваний результат.** Контейнер web працює (`docker ps`), у `tools` відкрито оболонку.

### Крок 3. Перевірте зв'язність між ними за іменами

**Що робити.** У контейнері `tools` виконайте `ping web` та `wget -qO- http://web`. Запишіть адресу, яку отримало ім'я `web`.

**Навіщо.** Вбудований DNS перетворює ім'я контейнера на адресу в мережі: не потрібно знати адресу наперед.

**Очікуваний результат.** Пінг успішний, `wget` повертає HTML-сторінку nginx.

### Крок 4. Опублікуйте порт однієї служби назовні та перевірте доступ

**Що робити.** З хоста відкрийте `http://localhost:8080` (браузер чи `curl`). Виведіть `docker port web`.

**Навіщо.** Це перевірка публікації порту: запит на хост перенаправляється в контейнер.

**Очікуваний результат.** Сторінка «Welcome to nginx!».

### Крок 5. Перегляньте налаштування мережі та перелік інтерфейсів

**Що робити.** Огляньте мережеві налаштування: `docker network inspect labnet` (контейнери й адреси), у контейнері `ip a`, `ip route`. Запустіть третій контейнер в **іншій** мережі й перевірте, чи бачить він `web`.

**Навіщо.** Різні мережі ізольовані за замовчуванням: це основа сегментації мікросервісів.

**Очікуваний результат.** Опис адрес і висновок про ізоляцію.

## Приклад виконання

**Варіант «nginx:alpine, порт 80»** (мережа 172.20.0.0/24, публікація на 8080).

```
$ docker network create --subnet 172.20.0.0/24 labnet
$ docker run -d --name web --network labnet -p 8080:80 nginx:alpine
$ docker run -it --rm --name tools --network labnet alpine sh

/ # ping -c 2 web
PING web (172.20.0.2): 56 data bytes
64 bytes from 172.20.0.2: seq=0 ttl=64 time=0.2 ms
/ # wget -qO- http://web | head -5
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
```

**Перевірка ззовні:**

```
$ curl -I http://localhost:8080
HTTP/1.1 200 OK
Server: nginx/...
$ docker port web
80/tcp -> 0.0.0.0:8080
```

**Аналіз налаштувань** (фрагмент `docker network inspect labnet`):

| Параметр | Значення |
|---|---|
| Підмережа | 172.20.0.0/24 |
| Шлюз | 172.20.0.1 (міст хоста) |
| web | 172.20.0.2 |
| tools | 172.20.0.3 |

У контейнері `ip route` показує маршрут за замовчуванням через 172.20.0.1: весь зовнішній трафік іде через міст хоста, де виконується NAT (маскарад).

**Ім'я проти адреси.** Ім'я `web` перетворюється на 172.20.0.2 вбудованим DNS Docker (адреса 127.0.0.11 у контейнері). Якщо контейнер перезапустити й він отримає іншу адресу, ім'я залишиться тим самим: тому в застосунках використовують **імена**, а не адреси.

**Різні мережі.** Якщо запустити контейнер у мережі за замовчуванням (`docker run -it --rm alpine sh`), то `ping web` дасть `bad address 'web'`, а `ping 172.20.0.2` не пройде: мережі ізольовані. Щоб контейнер бачив обидві мережі, його під'єднують командою `docker network connect labnet <ім'я>`. Така ізоляція корисна: база даних доступна лише застосунку, а не всьому хосту.

## Завдання для самостійного виконання

Поясніть, що станеться зі зв'язністю, якщо контейнери запустити в різних віртуальних мережах.

Підкресліть, що ізоляція є **типовою** поведінкою: контейнери, які не мають спільної мережі, не бачать одне одного ні за іменем, ні за адресою. Це безпечний фундамент: спільну мережу створюють лише для тих сервісів, що мають взаємодіяти. У Kubernetes аналогічну роль виконують мережеві політики.

## Типові помилки

- Запускати контейнери в мережі за замовчуванням і розраховувати на DNS за іменами.
- Забути `-p` і дивуватися, що служба недоступна з хоста.
- Опублікувати порт бази даних на всі інтерфейси (0.0.0.0) замість localhost.
- Використовувати адреси контейнерів у конфігурації замість імен.
- Не видалити тестові контейнери й мережі після роботи (`docker rm`, `docker network rm`).

## Контрольні питання

1. Як контейнери звертаються один до одного?
2. Що означає публікація порту?
3. Навіщо контейнерам окрема віртуальна мережа?
4. Чим мережа контейнерів відрізняється від мережі віртуальних машин?

## Вимоги до звіту

Звіт подається без титульного листа й містить:

1. Тему та мету роботи.
2. Умову завдання (номер варіанта).
3. Хід виконання роботи зі скриншотами ключових кроків.
4. Результати виконання завдань (вихідний код, схеми, конфігурації або протоколи вимірювань, залежно від роботи).
5. Відповіді на контрольні питання.
6. Висновки.

Звіт містить команди створення мережі й запуску контейнерів, результати перевірки зв'язності за іменем, перевірки публікації порту, вивід docker network inspect із поясненням адрес, експеримент із різними мережами та відповідь на самостійне завдання.
