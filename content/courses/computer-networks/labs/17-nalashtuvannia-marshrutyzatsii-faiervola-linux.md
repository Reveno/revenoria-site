# Налаштування маршрутизації та фаєрвола в Linux

> [!abstract] Пов'язана лекція
> [[courses/computer-networks/lectures/26-linux-merezhi-ta-nftables|Лекція 26. Linux-мережі та nftables]]. Ви перетворюєте Linux-вузол на маршрутизатор із фаєрволом nftables: вмикаєте пересилання пакетів, пишете правила з політикою за замовчуванням і перевіряєте їх лічильниками.

## Навіщо ця робота

Linux це не лише серверна ОС, а й повноцінний маршрутизатор і фаєрвол: на ньому побудовано значну частину домашніх роутерів, мережевого обладнання й хмарної інфраструктури. Усе потрібне вже в ядрі: пересилання пакетів між інтерфейсами вмикається одним параметром, а фільтрування виконує підсистема **nftables** із таблицями, ланцюгами й правилами.

Ключ до фаєрвола політика за замовчуванням і порядок правил. Принцип «усе заборонено, дозволено лише потрібне» безпечніший за «усе дозволено, заборонено лише погане». У цій роботі ви реалізуєте саме так: політика forward = drop, явні дозволи для потрібних служб, перевірка лічильників і (за самостійним завданням) трансляція адрес.

## Мета

Навчитися переглядати таблицю маршрутизації й інтерфейси Linux, вмикати пересилання пакетів, створювати таблицю й ланцюги nftables, додавати правила дозволу потрібних служб із політикою за замовчуванням drop, перевіряти дію за лічильниками та налаштовувати NAT.

Після заняття ви повинні вміти:

- вмикати пересилання (net.ipv4.ip_forward) тимчасово й постійно;
- створювати таблиці й ланцюги nftables;
- писати правила з політикою drop і станом з'єднань;
- перевіряти лічильники й журнали;
- налаштовувати маскарад (NAT) для внутрішніх вузлів;

## Обладнання та програмне забезпечення

- Персональний комп'ютер з доступом до мережі Інтернет.
- Аналізатор мережевого трафіку Wireshark, термінальний клієнт.

Потрібна Linux-система з правами `sudo`: віртуальна машина (Ubuntu Server) у VirtualBox із трьома мережевими адаптерами або **мережеві простори імен** (network namespaces), які дозволяють змоделювати «маршрутизатор і дві мережі» на одному комп'ютері без віртуальних машин (див. приклад). Пакет `nftables` входить до сучасних дистрибутивів (`sudo apt install nftables`).

## Теоретична частина

У Linux маршрутизація вмикається окремим параметром ядра, а фільтрування виконує підсистема nftables з таблицями, ланцюгами та правилами. Правила перевіряються послідовно, тому порядок і політика за замовчуванням визначають поведінку системи.

### Шлях пакета

Пакети проходять через **hooks**: `prerouting` (вхід, до маршрутизації), `input` (призначено самому хосту), `forward` (транзит, через маршрутизатор), `output` (від хоста), `postrouting` (вихід, після маршрутизації). Правила в ланцюжку перевіряються послідовно; **політика** ланцюга (`accept`/`drop`) діє, якщо жодне правило не збіглося.

![[attachments/ksm-lr17-nft.svg|900]]
*Шлях пакета через nftables: транзитний трафік між мережами проходить ланцюг forward. NAT виконується в prerouting (DNAT) і postrouting (SNAT/masquerade). Джерело: власна ілюстрація автора курсу, для цього конспекту.*

### Стан з'єднань

Правило `ct state established,related accept` пропускає **відповіді** на дозволені з'єднання, тож не треба окремо дозволяти зворотний трафік. Нові з'єднання (`ct state new`) перевіряються за правилами.

## Хід роботи

Нижче кожен крок із методички доповнено поясненням: що саме робити, як і навіщо. Не пропускайте пояснень: вони вказують, на що звертати увагу й чого очікувати.

### Крок 1. Перегляньте таблицю маршрутизації та мережеві інтерфейси

**Що робити.** Перегляньте інтерфейси й таблицю маршрутизації: `ip a`, `ip route`. Налаштуйте топологію (три інтерфейси або простори імен) і перевірте, що кожен вузол бачить шлюз.

**Навіщо.** Перш ніж налаштовувати фаєрвол, переконайтеся, що мережа працює без нього.

**Очікуваний результат.** Вузли в обох мережах пінгують свої шлюзи.

### Крок 2. Увімкніть пересилання пакетів між інтерфейсами

**Що робити.** Увімкніть пересилання: `sudo sysctl -w net.ipv4.ip_forward=1`, а для постійності додайте рядок у `/etc/sysctl.d/99-forward.conf`.

**Навіщо.** За замовчуванням Linux не пересилає пакети між інтерфейсами (він «хост»); пересилання перетворює його на маршрутизатор.

**Очікуваний результат.** `sysctl net.ipv4.ip_forward` повертає 1; ping між мережами проходить (до фільтрування).

### Крок 3. Створіть таблицю й ланцюги фільтрування

**Що робити.** Створіть таблицю й ланцюг forward із політикою drop та правилами: дозволити встановлені з'єднання й потрібну службу згідно з варіантом.

**Навіщо.** Усе, що явно не дозволено, відкидається: безпечне налаштування за замовчуванням.

**Очікуваний результат.** Завантажений набір правил (`sudo nft list ruleset`).

### Крок 4. Додайте правила дозволу потрібних служб і заборони решти

**Що робити.** Перевірте: дозволена служба працює, а заборонені обміни ні. Подивіться лічильники (`counter` у правилах, `sudo nft list ruleset`).

**Навіщо.** Лічильники показують, які правила спрацювали, і дозволяють знайти помилку без здогадок.

**Очікуваний результат.** Лічильники ростуть біля потрібних правил.

### Крок 5. Перевірте дію правил і перегляньте лічильники

**Що робити.** Налаштуйте трансляцію адрес для вузлів внутрішньої мережі (маскарад на зовнішньому інтерфейсі) і перевірте їхній вихід назовні.

**Навіщо.** Маскарад замінює адреси внутрішніх вузлів адресою зовнішнього інтерфейсу: те саме, що ми робили на Cisco командою NAT overload.

**Очікуваний результат.** Внутрішні вузли досягають зовнішньої мережі.

## Приклад виконання

**Варіант:** маршрутизатор із трьома інтерфейсами: eth0 (інтернет), eth1 192.168.10.1/24, eth2 192.168.110.1/24. Дозволити TCP 22 із 192.168.10.0/24 до 192.168.110.0/24; решта транзитного трафіку заборонена.

**Моделювання на одному комп'ютері (простори імен):**

```
sudo ip netns add r; sudo ip netns add a; sudo ip netns add b
sudo ip link add va type veth peer name ra
sudo ip link add vb type veth peer name rb
sudo ip link set va netns a; sudo ip link set ra netns r
sudo ip link set vb netns b; sudo ip link set rb netns r
sudo ip netns exec a ip addr add 192.168.10.10/24 dev va
sudo ip netns exec b ip addr add 192.168.110.10/24 dev vb
sudo ip netns exec r ip addr add 192.168.10.1/24 dev ra
sudo ip netns exec r ip addr add 192.168.110.1/24 dev rb
for n in a b r; do sudo ip netns exec $n ip link set lo up; done
sudo ip netns exec a ip link set va up; sudo ip netns exec b ip link set vb up
sudo ip netns exec r ip link set ra up; sudo ip netns exec r ip link set rb up
sudo ip netns exec a ip route add default via 192.168.10.1
sudo ip netns exec b ip route add default via 192.168.110.1
sudo ip netns exec r sysctl -w net.ipv4.ip_forward=1
```

**Правила nftables** (файл `fw.nft`, у просторі імен `r`):

```
table inet filter {
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state established,related counter accept
    iifname "ra" oifname "rb" ip saddr 192.168.10.0/24 ip daddr 192.168.110.0/24 tcp dport 22 counter accept
    counter drop comment "решта транзиту"
  }
}
```

Завантаження: `sudo ip netns exec r nft -f fw.nft`.

**Перевірка:**

```
sudo ip netns exec b nc -l 22 &            # «служба» на порту 22 у мережі b
sudo ip netns exec a nc -zv 192.168.110.10 22   # дозволено: Connection succeeded
sudo ip netns exec a ping -c 2 192.168.110.10   # заборонено: 100% packet loss
sudo ip netns exec r nft list ruleset
```

У виводі лічильники показують, наприклад, `counter packets 1 bytes 60` у правилі дозволу (одне нове з'єднання) та `counter packets 2` у заключному drop (два ICMP-пакети).

**Постійне пересилання:** `echo "net.ipv4.ip_forward=1" | sudo tee /etc/sysctl.d/99-forward.conf` і `sudo sysctl --system`.

**NAT (самостійне завдання)** на маршрутизаторі з eth0 до інтернету:

```
table ip nat {
  chain postrouting {
    type nat hook postrouting priority 100;
    oifname "eth0" ip saddr 192.168.0.0/16 masquerade
  }
}
```

Тепер вузли з 192.168.10.0/24 та 192.168.110.0/24 виходять в інтернет під адресою eth0. Не забудьте дозволити таке пересилання в ланцюзі forward (правила `iifname "eth1" oifname "eth0" accept`).

## Завдання для самостійного виконання

Налаштуйте трансляцію адрес для вузлів внутрішньої мережі та перевірте їх вихід назовні.

Перевірте результат так: з внутрішнього вузла `curl ifconfig.me` повертає публічну адресу маршрутизатора, а не адресу вузла; у таблиці `sudo conntrack -L` видно трансльовані з'єднання. Не забувайте, що без дозвільного правила у forward (політика drop) трафік назовні відкидатиметься, навіть якщо маскарад налаштовано.

## Типові помилки

- Не ввімкнути ip_forward: маршрутизації немає взагалі.
- Поставити політику drop без правила для established,related: відповіді відкидаються й з'єднання не встановлюються.
- Застосувати правила на віддаленому сервері й заблокувати собі SSH: спершу перевірте в безпечному середовищі.
- Забути зробити пересилання й правила постійними: після перезавантаження все зникає.
- Плутати ланцюги input (до самого хоста) й forward (транзит).

## Вимоги до звіту

Звіт подається без титульного листа й містить:

1. Тему та мету роботи.
2. Умову завдання (номер варіанта).
3. Хід виконання роботи зі скриншотами ключових кроків.
4. Результати виконання завдань (вихідний код, схеми, конфігурації або протоколи вимірювань, залежно від роботи).
5. Відповіді на контрольні питання.
6. Висновки.

Звіт містить топологію, команди, текст правил nftables, результати перевірки (дозволений і заборонений обміни), лічильники, налаштування постійного пересилання та NAT і відповідь на самостійне завдання.
