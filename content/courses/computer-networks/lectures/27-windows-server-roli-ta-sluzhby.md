# Windows Server: ролі та служби

> [!abstract]
> У попередній лекції ви налаштовували мережу Linux-сервера командою `ip` і nftables. Сьогодні розберемо симетричну сторону — практичне керування Windows Server: як організована система ролей і функцій, як PowerShell перетворює адміністрування на послідовність передбачуваних, структурованих команд, і чим принципово відрізняється сама модель збереження конфігурації порівняно з тим, що ви щойно бачили і в Cisco IOS, і в Linux.

## Ролі та функції: дві категорії того, чим може бути сервер

Windows Server організовує все, що сервер потенційно вміє робити, у дві категорії, і розрізняти їх варто чітко. **Роль (role)** визначає **основне призначення** сервера — велику, самодостатню функцію, заради якої цей конкретний сервер, по суті, і існує в мережі: **Active Directory Domain Services (AD DS)**, **DNS Server**, **DHCP Server**, **File and Storage Services**, **Web Server (IIS)**, **Print and Document Services**, **Remote Desktop Services**. **Функція (feature)**, натомість, — менший, допоміжний компонент, що підтримує чи розширює можливості сервера, але сам собою не визначає його основне призначення — наприклад, .NET Framework, засоби відмовостійкої кластеризації (Failover Clustering), BitLocker для шифрування диска.

> [!definition] Визначення
> **Роль (server role)** — основна функція, заради якої сервер розгорнутий у мережі (наприклад, контролер домену чи DNS-сервер). **Функція (feature)** — допоміжний компонент, що розширює можливості сервера, але не визначає його основного призначення.

Одному фізичному чи віртуальному серверу можна (хоча в production-середовищах це не завжди рекомендована практика з міркувань безпеки й ізоляції відмов) призначити одразу кілька ролей — наприклад, невеликий офіс цілком може обійтись одним сервером, що одночасно виконує роль контролера домену *і* DNS-сервера *і* DHCP-сервера, тоді як велике підприємство типово розносить кожну роль на окремий, спеціалізований сервер (чи навіть кілька — заради резервування, той самий принцип відмовостійкості, який ми вже бачили як зони доступності в лекції 22).

## Server Manager і зсув у бік PowerShell

Традиційний спосіб керування ролями й функціями — графічний інструмент **Server Manager**: майстер, що дозволяє вибрати потрібні ролі й функції з переліку прапорців, переглянути короткий опис кожної, і встановити обрані одним послідовним майстром. Це зручний, доступний старт для того, хто ще не володіє командним рядком, — саме тим самим шляхом, яким студенти з мінімальним досвідом традиційно й починають знайомство з Windows Server.

Але, як ми зазначили в лекції 25, сучасна практика адміністрування Windows Server дедалі більше зміщується до **PowerShell** — і причина та сама, що спонукала до появи Server Core: графічний майстер незручно повторити ідентично на десятках серверів одночасно, а PowerShell-скрипт — тривіально. Розглянемо базові команди управління ролями, паралельні до того, що ви вже бачили в лекції 26 для Linux.

```text
PS C:\> Get-WindowsFeature

Display Name                                            Name                       Install State
------------                                            ----                       -------------
[ ] Active Directory Domain Services                    AD-Domain-Services         Available
[ ] DNS Server                                           DNS                        Available
[ ] DHCP Server                                          DHCP                       Available
[X] File and Storage Services                            FileAndStorage-Services    Installed
```

Команда `Get-WindowsFeature` — функціональний аналог `Get-Service` чи, якщо провести паралель через увесь курс, аналог `dnf list` в екосистемі Linux (лекція 25) чи `show ip interface brief` в Cisco IOS (лекція 13): швидкий, структурований огляд поточного стану системи. Зверніть увагу на саму назву команди — вона одразу демонструє конвенцію "Дієслово-Іменник" (`Get-WindowsFeature`), про яку ми говорили в лекції 25: дієслово `Get` однозначно повідомляє, що команда лише *читає* стан, нічого не змінюючи, — на відміну від команд з дієсловом `Install`, `Set` чи `New`, з якими побачимо нижче.

Встановлення нової ролі — команда `Install-WindowsFeature`:

```text
PS C:\> Install-WindowsFeature -Name DNS -IncludeManagementTools
```

Параметр `-IncludeManagementTools` одразу встановлює й графічні, і командні інструменти керування щойно доданою роллю (у випадку DNS — консоль керування зонами й записами, детально розглянуту в наступній лекції), а не лише саму фонову службу, — практична деталь, яку варто одразу запам'ятати, бо забутий цей параметр залишає адміністратора без зручного способу далі керувати щойно встановленою роллю.

## Мережеве налаштування через PowerShell: та сама задача, інший синтаксис

Порівняємо безпосередньо ті самі мережеві задачі, які ви вже виконували на Linux у лекції 26, тепер у PowerShell, — щоб побачити, наскільки послідовно та сама логічна задача виражається різним синтаксисом у різних системах.

| Задача | Cisco IOS (лекція 13) | Linux `ip` (лекція 26) | PowerShell |
|---|---|---|---|
| Переглянути інтерфейси | `show ip interface brief` | `ip addr show` | `Get-NetIPAddress` |
| Призначити адресу | `ip address 192.168.1.10 255.255.255.0` | `ip addr add 192.168.1.10/24 dev eth0` | `New-NetIPAddress -IPAddress 192.168.1.10 -PrefixLength 24 -InterfaceAlias Ethernet` |
| Переглянути маршрути | `show ip route` | `ip route show` | `Get-NetRoute` |
| Додати статичний маршрут | `ip route 10.0.0.0 255.255.255.0 192.168.1.254` | `ip route add 10.0.0.0/24 via 192.168.1.254` | `New-NetRoute -DestinationPrefix 10.0.0.0/24 -NextHop 192.168.1.254` |
| Задати DNS-сервер клієнта | `ip name-server 8.8.8.8` | редагування `/etc/resolv.conf` чи NetworkManager | `Set-DnsClientServerAddress -InterfaceAlias Ethernet -ServerAddresses 8.8.8.8` |

Три колонки цієї таблиці розв'язують ту саму задачу трьома різними, послідовними всередині себе синтаксисами — і саме вміння впізнавати той самий концептуальний крок під різним синтаксичним "одягом" і є практичною метою, яку переслідує весь цей модуль курсу.

## Постійність конфігурації: тут Windows поводиться інакше

У лекціях 13 і 26 ми двічі детально наголошували на одному й тому самому практичному застереженні: команди, введені прямо в термінал (чи то Cisco IOS, чи то `ip` в Linux), діють негайно, але зникають після перезавантаження, доки їх явно не збережено в окремій, постійній конфігурації. Windows Server у цьому конкретному сенсі поводиться **інакше**, і ця відмінність варта явного, окремого наголошення, а не замовчування.

Переважна більшість налаштувань, зроблених через Server Manager чи командою PowerShell на кшталт `New-NetIPAddress` чи `Install-WindowsFeature`, **записуються одразу й постійно** — в реєстр Windows чи інше постійне сховище конфігурації, — без окремого, явного кроку "збережи це назавжди", аналогічного `copy running-config startup-config` з лекції 13 чи редагуванню окремого файлу мережі з лекції 26. Немає ситуації, у якій щойно призначена статична IP-адреса просто зникне після наступного перезавантаження сервера, — вона там і залишиться, доки хтось свідомо її не змінить чи не видалить.

> [!warning] Типова помилка
> Ця відмінність — не привід для студента розслабитись і вважати "у Windows можна не думати про збереження взагалі". По-перше, встановлення нової ролі часто *вимагає* перезавантаження сервера для завершення процесу (хоча стан самого встановлення й обраної ролі при цьому зберігається коректно, а не втрачається). По-друге, і найважливіше практично: **звичка** — свідомо перевіряти, чи справді конфігурація застосувалась і чи вона витримає перезапуск конкретного сервісу чи всієї системи, — має залишатись з вами незалежно від того, яку саме операційну систему ви адмініструєте прямо зараз. Відмінність між системами тут суто механічна (де саме й коли саме зберігається стан), а не привід забути про саму дисципліну перевірки результату своєї роботи.

## Віддалене керування: RSAT і PowerShell Remoting

У лекції 25 ми згадали RDP (Remote Desktop Protocol) як типовий спосіб віддаленого доступу до Windows-сервера — повноцінний графічний робочий стіл через мережу. Але для серверів у режимі Server Core (без графічного інтерфейсу взагалі, лекція 25) чи просто для ефективнішого масового керування десятками серверів одночасно існують два практичніші підходи.

**RSAT (Remote Server Administration Tools)** — набір графічних консолей керування, що встановлюється не на самому сервері, а на робочій станції адміністратора, і дозволяє керувати ролями віддаленого сервера (включно з Server Core) через звичний графічний інтерфейс, попри те що сам сервер узагалі не має локального графічного середовища, — подібно до того, як адміністратор Linux керує віддаленим headless-сервером через SSH-клієнт зі свого власного комп'ютера, тільки тут замість текстового термінала — графічна консоль, що спілкується із сервером мережею.

**PowerShell Remoting**, побудований на протоколі **WinRM (Windows Remote Management)**, дозволяє виконувати команди PowerShell на віддаленому сервері так, ніби ви ввели їх локально (`Enter-PSSession -ComputerName SRV01`), — функціонально дуже близький аналог SSH (лекція 20, детальніше в лекції 40) з погляду мети (безпечний, командний віддалений доступ), хоча технічно побудований на іншому транспортному протоколі (типово HTTP/HTTPS, порти 5985/5986, а не окремий протокол SSH на порту 22).

## Огляд ключових мережевих ролей

Коротко зафіксуємо, чим саме займається кожна з провідних мережевих ролей Windows Server, — детальне, практичне розгортання кожної з них іде вже в наступних лекціях і лабораторних роботах курсу.

**AD DS (Active Directory Domain Services)** — служба каталогів, центральний реєстр користувачів, комп'ютерів і політик безпеки цілого домену підприємства; детально розглянемо в модулі 5 цього курсу (лекції 30-37), який повністю присвячений темі служби каталогів.

**DNS Server** — реалізація служби доменних імен (детальна теорія — лекція 17) безпосередньо на Windows Server; часто розгортається *разом* із AD DS, оскільки сама Active Directory внутрішньо активно покладається на DNS для власної роботи. Практичне розгортання — наступна лекція.

**DHCP Server** — реалізація автоматичної видачі мережевих параметрів (теорія DORA — лекція 14) на Windows Server, альтернатива тому, що ми конфігурували на Cisco-маршрутизаторі командами `ip dhcp pool`. Практичне розгортання — так само наступна лекція.

**File and Storage Services** — файловий сервер, що надає спільні мережеві папки протоколом **SMB (Server Message Block)**, з керуванням квотами, дозволами доступу й, за потреби, реплікацією між кількома серверами для відмовостійкості.

**Web Server (IIS, Internet Information Services)** — вбудований вебсервер Windows, реалізація HTTP/HTTPS (лекція 17) для розміщення вебзастосунків; детальніше розглянемо в лекції 29 поряд із файловими службами та Docker.

**Print and Document Services** і **Remote Desktop Services** — централізоване керування принтерами мережі й надання віддалених робочих столів чи опублікованих застосунків користувачам відповідно; менш центральні для цього курсу, але типові ролі реального корпоративного середовища.

> [!example] Приклад
> Невеликий офіс на 30 співробітників цілком реалістично обходиться *одним* сервером Windows Server, що одночасно виконує ролі AD DS, DNS Server, DHCP Server і File and Storage Services, — саме такий сценарій ви й розгорнете в лабораторній роботі цього модуля. Велике підприємство з тисячами співробітників, навпаки, типово розносить кожну роль на окремий, а часто й резервований (кілька серверів на одну роль для відмовостійкості) фізичний чи віртуальний сервер, — той самий принцип масштабування "від малого до великого", який ми вже неодноразово бачили протягом курсу, тепер застосований до розподілу ролей серверів, а не лише мережевого обладнання.

## Windows Server у контексті курсу

Ця лекція завершує пряме зіставлення двох операційних систем, розпочате в лекціях 25-26: тепер ви бачили ту саму послідовність практичних задач — перегляд стану, налаштування мережі, встановлення функціональності, віддалене керування — виконаною і на Cisco IOS, і на Linux, і на Windows Server, кожного разу іншим синтаксисом, але тією самою логікою. Наступна лекція візьме дві конкретні ролі, вже згадані сьогодні побіжно, — DNS та DHCP, — і покаже їхнє практичне розгортання одразу на обох платформах, Windows Server і Linux, безпосередньо застосувавши теорію з лекцій 14 і 17 на практиці.

> [!exam] На іспиті
> Типові питання: а) розрізнити роль і функцію Windows Server за визначенням і навести приклад кожної; б) назвати команду PowerShell для перегляду встановлених ролей і для встановлення нової ролі; в) пояснити конвенцію іменування cmdlets "Дієслово-Іменник"; г) пояснити, чим модель збереження конфігурації Windows Server відрізняється від моделі Cisco IOS (running/startup-config) і Linux (`ip`-команди проти постійних файлів); д) розрізнити RSAT і PowerShell Remoting за призначенням і провести паралель із засобами віддаленого доступу до Linux.

## Завдання на занятті (20 хв)

1. Використовуючи таблицю відповідностей команд вище, самостійно (без підглядання в таблицю) запишіть, якою командою PowerShell ви призначите інтерфейсу `Ethernet0` адресу 10.20.30.5/24, і порівняйте з відповідними командами Cisco IOS та Linux `ip`.
2. У парі поясніть одне одному, чому команда `Install-WindowsFeature -Name DNS -IncludeManagementTools` містить саме такий параметр, і що конкретно станеться з можливостями адміністратора, якщо цей параметр забути.
3. Обговоріть: невеликий коледж планує один сервер із ролями AD DS, DNS і DHCP одночасно. Які ризики такого об'єднання ролей варто врахувати, і за яких умов має сенс розділити їх на окремі сервери?
4. Порівняйте усно PowerShell Remoting і SSH (лекція 20) за метою, яку вони обидва переслідують, і за тим, чим вони технічно відрізняються (транспортний протокол, типовий порт).

> 2. Яка команда PowerShell покаже список усіх доступних і встановлених ролей та функцій сервера?
> 3. Що означає конвенція "Дієслово-Іменник" у назвах cmdlets, і яке дієслово вказує, що команда лише читає стан, нічого не змінюючи?
> 4. Чим модель збереження мережевої конфігурації Windows Server принципово відрізняється від моделі Cisco IOS і Linux?
> 5. Що таке RSAT і для якого сценарію (порівняно з локальним Server Manager) він призначений?
