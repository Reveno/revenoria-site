# Мережеві операційні системи: Windows Server і Linux

> [!abstract]
> Двадцять чотири лекції ми дивились на мережу з погляду обладнання, що лише пересилає трафік, — комутаторів і маршрутизаторів під керуванням вузькоспеціалізованої Cisco IOS. Тепер настав час зазирнути на інший кінець кабелю — до серверів, що фактично *надають* сервіси, заради яких уся ця інфраструктура існує: файлові сховища, вебсайти, служби каталогів. Розберемо дві операційні системи, що ділять між собою переважну більшість серверного ринку, — Windows Server і Linux, — не як "хто краще", а як два різні набори компромісів, кожен доречний для власного класу задач, часто обидва одночасно в тій самій мережі підприємства.

## Що таке мережева операційна система сьогодні

Термін "мережева операційна система" (Network Operating System, NOS) історично означав дещо вужче й конкретніше — наприклад, Novell NetWare 1980-90-х років, спеціалізовану систему, розроблену буквально для однієї мети: обслуговувати файлові та принтерні служби мережі. Сьогодні цей термін розмився й здебільшого позначає просто **серверну операційну систему загального призначення**, яка, попри свою універсальність, найчастіше в реальній практиці розгортається саме заради мережевих служб: файлових сховищ, вебсерверів, баз даних, служб каталогів (модуль 5), DNS- і DHCP-серверів (лекція 28), — на відміну від Cisco IOS (лекція 13), яка вузько й виключно спеціалізована під пересилання пакетів і кадрів.

Практично весь цей ринок сьогодні поділений між двома родинами: **Windows Server** — серверна лінійка Microsoft, і **Linux** — сімейство операційних систем на основі відкритого ядра, випущених у вигляді десятків незалежних **дистрибутивів**. Жодна з двох не "перемогла" іншу — обидві домінують у своїх власних, часто взаємодоповнювальних нішах, і переважна більшість реальних корпоративних мереж, які ви зустрінете в роботі, використовують обидві одночасно, кожну для того класу задач, де вона доречніша.

## Windows Server: екосистема навколо Active Directory

**Windows Server** побудований на тому самому ядрі, що й звичний десктопний Windows, але оптимізований і ліцензований під серверні навантаження. Головна практична сила Windows Server — не сама по собі операційна система, а **екосистема служб**, тісно інтегрованих одна з одною й (що особливо важливо для підприємств) із десктопними комп'ютерами співробітників, що теж переважно працюють під Windows.

Центральний елемент цієї екосистеми — **Active Directory (AD)**, служба каталогів, детально розглянута в модулі 5 цього курсу (лекції 30-33): централізований реєстр усіх користувачів, комп'ютерів і ресурсів мережі підприємства, з єдиним входом (single sign-on) і централізованим керуванням політиками безпеки через групові політики (лекція 33). Саме глибока інтеграція з AD — головна практична причина, чому переважна більшість підприємств із великим парком робочих станцій Windows (типовий офіс зі стандартними робочими місцями співробітників) обирає саме Windows Server для інфраструктурних ролей: файлового сервера, сервера друку, контролера домену.

Управління Windows Server історично асоціюється з графічним інтерфейсом — знайомими вікнами й майстрами налаштування, що знижують поріг входу для адміністратора, який ще не володіє командним рядком. Але сучасний Windows Server дедалі активніше зміщується в бік командного керування через **PowerShell** — оболонку з принципово іншою філософією, ніж класичні Unix-подібні командні рядки: команди PowerShell (**cmdlets**, вимовляється "командлети") побудовані за строгою конвенцією "Дієслово-Іменник" (`Get-Service`, `Set-NetIPAddress`, `New-ADUser`) і, що особливо важливо структурно, передають між собою в конвеєрі не голий текст, а повноцінні **об'єкти** зі своїми властивостями й методами, — до цієї відмінності ми детальніше повернемось у лекції 36, коли розглядатимемо автоматизацію мережі.

## Linux: відкрите ядро, безліч дистрибутивів

**Linux** — не одна операційна система, а **ядро**, навколо якого різні незалежні команди й компанії будують повноцінні дистрибутиви, комплектуючи ядро власним набором системних утиліт, менеджером пакетів і філософією підтримки. Для серверних задач найпоширеніші дистрибутиви поділяються на дві практичні категорії: **комерційні, орієнтовані на підприємства** (Red Hat Enterprise Linux, часто скорочують RHEL, і SUSE Linux Enterprise) з платною технічною підтримкою й гарантованим довгостроковим циклом оновлень, і **спільнотні** (Debian, і особливо Ubuntu Server, що побудований на основі Debian) — безкоштовні, з підтримкою від спільноти розробників, хоча Ubuntu теж пропонує платну комерційну підтримку як опцію для підприємств, яким вона потрібна.

Головна практична сила Linux — саме той командний, текстовий, глибоко скриптовий підхід до керування, який ми вже частково відчули на прикладі Cisco IOS у лекції 13: **shell** (найпоширеніший — **Bash**) керує системою через послідовність текстових команд, кожна з яких, за класичною філософією Unix, "робить одну річ і робить її добре", а результат однієї команди легко передається (**pipe**, `|`) на вхід наступній, утворюючи довільно складні ланцюжки обробки прямо в командному рядку. Саме ця скриптовність — головна причина, чому Linux настільки домінує там, де потрібна масова, автоматизована, відтворювана конфігурація сотень чи тисяч однакових серверів одразу, — і саме тому, як ми вже неодноразово бачили в модулі про глобальні мережі (лекції 21-23), **переважна більшість хмарної й контейнерної інфраструктури сучасного інтернету — Linux**: віртуальні машини хмарних провайдерів (лекція 22), контейнери Docker (лекція 23), вузли кластерів Kubernetes — усе це майже завжди Linux під капотом, а не Windows Server.

> [!info] Для допитливих
> Варто зробити ще одне спостереження, що прямо стосується самого предмета цього курсу: значна частина мережевого обладнання, включно з деякими платформами самої Cisco, під капотом фактично працює на модифікованому ядрі Linux — вузькоспеціалізована IOS чи подібні системи часто виявляються не написаними геть "з нуля", а побудованими поверх Linux-ядра з власним, спеціалізованим шаром керування зверху. Знання Linux, яке ви отримаєте в наступній лекції, — не окрема, паралельна навичка стосовно решти курсу, а фундамент, що часто ховається буквально під тим самим обладнанням Cisco, з яким ви вже практикувались.

## Управління пакетами: як в обидві системи потрапляє нове програмне забезпечення

Практична відмінність, з якою ви одразу зіткнетесь на практиці, — спосіб встановлення й оновлення програмного забезпечення. Дистрибутиви на основі Debian (включно з Ubuntu) використовують менеджер пакетів **APT** (команда `apt install`), тоді як дистрибутиви родини Red Hat використовують **DNF** (сучасний наступник старішого YUM, команда `dnf install`). В обох випадках ідея та сама: центральний **репозиторій** пакетів, з якого система автоматично завантажує потрібну програму разом з усіма її залежностями (іншими пакетами, від яких вона сама залежить), перевіряючи цілісність і сумісність версій, — принципово інший підхід порівняно з тим, до чого звик типовий користувач Windows, де встановлення програми традиційно означає завантаження окремого інсталятора з сайту виробника. Windows Server, утім, теж отримав власний, концептуально подібний менеджер пакетів — **winget** — хоча повсюдність і зрілість цього підходу в екосистемі Windows поки що суттєво поступається десятиліттям усталеної практики Linux.

## Ліцензування: не суто технічна, а практична економічна відмінність

Ще одна відмінність, яку варто явно проговорити, бо вона напряму впливає на реальні рішення підприємств, — модель ліцензування. **Windows Server** — комерційний продукт: ліцензія купується за моделлю, що враховує кількість фізичних ядер процесора сервера, і додатково для багатьох сценаріїв потрібні **клієнтські ліцензії доступу (CAL, Client Access License)** — окрема плата за кожного користувача чи пристрій, що звертається до сервера. **Linux** сам собою безкоштовний і відкритий (ядро й переважна більшість системного програмного забезпечення поширюються за відкритими ліцензіями), хоча підприємства, яким потрібна гарантована технічна підтримка й довгостроковий цикл оновлень безпеки (типова вимога для критичної інфраструктури), усе одно зазвичай платять — не за саму операційну систему, а за **підписку на підтримку** (класична модель Red Hat). До економічного виміру цього вибору — сукупної вартості володіння (TCO), яка включно з витратами на адміністрування, а не лише саму ліцензію, — ми детально повернемось у лекції 44 про економіку мережі.

| | Windows Server | Linux |
|---|---|---|
| Модель ліцензування | комерційна, за ядрами + CAL | безкоштовне ядро й ПЗ, платна підтримка (опційно) |
| Основне управління | GUI традиційно, PowerShell дедалі більше | командний рядок (Bash), GUI переважно опційний |
| Ключова сильна сторона | глибока інтеграція з Active Directory | скриптовність, масштаб, домінування в хмарі/контейнерах |
| Типова роль у мережі | контролер домену, файловий сервер, застосунки .NET | вебсервери, бази даних, контейнери, мережеві служби |
| Віддалене керування | RDP (графічний), WinRM/PowerShell Remoting | SSH (лекція 40) |

## Server Core: точка зближення двох філософій

Варто окремо згадати практичну тенденцію, яка зближує обидві системи ближче одна до одної, ніж могло б здатися з таблиці вище. **Windows Server Core** — режим встановлення Windows Server без графічного інтерфейсу взагалі, керований виключно через командний рядок (переважно PowerShell) чи віддалено. Причина появи цього режиму пряма і по суті запозичена з традиційної практики Linux: менша поверхня атаки (менше встановлених компонентів — менше потенційних вразливостей, той самий принцип, що пояснював компактність WireGuard у лекції 20), менше споживання ресурсів сервера, і швидша, передбачуваніша процедура встановлення оновлень безпеки (менше компонентів, які взагалі потрібно оновлювати). Server Core сьогодні — рекомендована Microsoft конфігурація за замовчуванням для більшості production-розгортань Windows Server, попри те що GUI-варіант залишається доступним і зручним для навчання чи менш критичних сценаріїв, — саме тому в лабораторних роботах цього курсу ви побачите й спробуєте обидва підходи керування, а не лише звичний графічний.

> [!warning] Типова помилка
> Не варто робити висновок, що вибір між Windows Server і Linux — це вибір "або-або" для всієї мережі підприємства одразу. Реальна корпоративна мережа, яку ви зустрінете в роботі, майже завжди **гібридна**: контролер домену й файловий сервер на Windows Server, поруч із вебсерверами й базами даних на Linux, і все це одночасно в тій самій мережі, з'єднане тими самими комутаторами й маршрутизаторами Cisco, які ми вивчали протягом усього курсу. Питання, яке реально постає перед мережевим інженером на практиці, — не "яка операційна система краща", а "яка операційна система доречніша для *цієї конкретної* ролі", і відповідь майже завжди залежить від того, наскільки тісно ця роль пов'язана з екосистемою Active Directory чи, навпаки, з хмарною й контейнерною інфраструктурою.

## Куди веде ця лекція далі

Ця лекція навмисно залишилась на рівні порівняння й загальних принципів — практичне, командне занурення в кожну з двох систем окремо йде вже в наступних двох лекціях модуля. У **лекції 26** ми детально розглянемо налаштування мережевих інтерфейсів і фільтрацію трафіку в Linux через **nftables** — сучасний, ідейний наступник `iptables`, який ми вже побіжно згадували в лекції 23 стосовно того, як Docker реалізує NAT на хості. У **лекції 27** ми так само детально розглянемо основні мережеві ролі Windows Server — файлові служби, друк, базові служби застосунків, — перш ніж у лекціях 28-29 перейти до конкретних мережевих служб (DNS, DHCP, вебсерверів), які може розгортати кожна з двох систем.

> [!exam] На іспиті
> Типові питання: а) пояснити, чому сучасний термін "мережева операційна система" ширший за історичне значення Novell NetWare; б) назвати головну практичну причину, чому підприємства з великим парком робочих станцій Windows обирають Windows Server для інфраструктурних ролей; в) пояснити, чому Linux домінує саме в хмарній і контейнерній інфраструктурі; г) порівняти моделі ліцензування Windows Server і Linux; д) пояснити, що таке Windows Server Core і чому ця конфігурація концептуально зближується з традиційною філософією Linux.

## Завдання на занятті (20 хв)

1. У парі складіть список із п'яти типових серверних ролей підприємства (файловий сервер, вебсервер, контролер домену, база даних, DNS-сервер) і для кожної обґрунтуйте, яку операційну систему ви обрали б за замовчуванням і чому.
2. Обговоріть: чому саме скриптовність і текстовий командний рядок Linux (а не, наприклад, нижча ціна) вважають головною причиною домінування Linux у хмарній інфраструктурі, спираючись на те, що ви вже знаєте про масштаб автоматизації з лекцій 21-23.
3. Порівняйте усно принцип менеджера пакетів (APT/DNF) з принципом класичного встановлення програм у Windows через окремий інсталятор — які практичні переваги дає централізований репозиторій із залежностями?
4. Компанія планує розгорнути новий кластер вебсерверів у хмарній VPC (лекція 22) і одночасно оновити файловий сервер офісу, тісно інтегрований з Active Directory. Обґрунтуйте вибір операційної системи для кожного з двох сценаріїв.

> [!question] Перевірте себе
> 1. Чим сучасне, широке розуміння терміна "мережева операційна система" відрізняється від вузькоспеціалізованої Cisco IOS (лекція 13)?
> 2. Яка служба Windows Server є головним практичним фактором, що визначає вибір цієї системи для підприємства з великим парком робочих станцій Windows?
> 3. Назвіть по одному менеджеру пакетів для дистрибутивів родини Debian і родини Red Hat.
> 4. Чим модель ліцензування Windows Server відрізняється від типової моделі Linux?
> 5. Що таке Windows Server Core і яку саму ідею з традиційної практики Linux він запозичує?
