# Веб- і файлові служби, контейнеризація служб (Docker)

> [!abstract]
> Завершуємо модуль про мережеві операційні системи двома практичними темами й одним поглядом на майбутнє. Розберемо, як розгортаються вебсервери на обох платформах курсу і як Nginx на практиці виконує роль, теоретично розглянуту ще в лекції 24, — реверс-проксі й балансувальника навантаження; розберемо файлові служби SMB і NFS; і повернемось до Docker, тепер уже не з погляду мережевої теорії лекції 23, а практично — розгорнувши реальний мережевий сервіс у контейнері.

## Вебсервери: IIS, Apache, Nginx

У лекції 27 ми згадали **IIS (Internet Information Services)** як вбудований вебсервер Windows Server — тісно інтегрований з рештою екосистеми Windows (автентифікація через Active Directory, керування через ту саму PowerShell-конвенцію). У світі Linux домінують два незалежні проєкти з різною внутрішньою архітектурою, і різниця між ними — не просто історична випадковість, а практично значуща.

**Apache HTTP Server** — старший, надзвичайно модульний вебсервер: під кожен запит традиційно виділяється окремий процес чи потік, а величезна екосистема модулів (включно з файлами `.htaccess`, що дозволяють змінювати поведінку сервера для конкретної папки без перезапуску всього сервера) робить Apache надзвичайно гнучким для складних, різнорідних сценаріїв розміщення.

**Nginx** побудований на принципово іншій, **подієво-орієнтованій (event-driven)** архітектурі: замість окремого процесу чи потоку на кожне з'єднання один невеликий набір робочих процесів здатен обслуговувати тисячі одночасних з'єднань, ефективно перемикаючись між ними в міру готовності кожного, — та сама ідея ефективного мультиплексування, яку ми вже бачили концептуально в лекції 17 стосовно того, як HTTP/2 мультиплексує кілька потоків в одному з'єднанні. Саме ця архітектурна перевага в обробці великої кількості одночасних з'єднань і зробила Nginx одним із найпоширеніших виборів саме для ролі, яку ми детально розглядали теоретично в лекції 24, — **реверс-проксі й балансувальника навантаження рівня L7**.

## Nginx як реверс-проксі: теорія лекції 24 стає конфігурацією

Розглянемо мінімальний, практичний приклад того, як саме виглядає конфігурація, що реалізує принципи з лекції 24, — L7-балансування із завершенням TLS (TLS termination):

```text
server {
    listen 443 ssl;
    server_name college.local;

    ssl_certificate     /etc/nginx/ssl/college.crt;
    ssl_certificate_key /etc/nginx/ssl/college.key;

    location / {
        proxy_pass http://backend_pool;
    }
}

upstream backend_pool {
    server 192.168.10.21:8080;
    server 192.168.10.22:8080;
    server 192.168.10.23:8080;
}
```

Директиви `ssl_certificate` й `ssl_certificate_key` — це буквально та сама пара, яку ми обговорювали в лекції 17 (сертифікат і закритий ключ) і знову в лекції 24 стосовно TLS termination: Nginx приймає на себе роль сервера в TLS-рукостисканні, розшифровує трафік клієнта, і вже незашифрованим HTTP пересилає його (`proxy_pass`) до одного із серверів у блоці `upstream` — того самого пулу бекенд-серверів, між якими розподіляється навантаження, концептуально ідентичного пулу подів за Service у лекції 23 чи бекенд-серверам L7-балансувальника з лекції 24. За замовчуванням Nginx розподіляє запити між серверами `upstream`-пулу за алгоритмом round robin (лекція 24), хоча директивами на кшталт `least_conn` чи явних вагових коефіцієнтів можна обрати інший алгоритм — точнісінько ті самі алгоритми, які ми розбирали теоретично.

## Файлові служби: SMB і NFS

У лекції 27 ми згадали **SMB (Server Message Block)** як протокол файлових служб Windows. Світ Linux/Unix історично використовує власний, окремий протокол — **NFS (Network File System)**: концептуально розв'язує ту саму задачу (мережевий доступ до віддаленої файлової системи так, ніби вона підключена локально), але з іншою внутрішньою механікою автентифікації й дозволів, історично тісніше пов'язаною із самою моделлю користувачів і прав Unix, ніж з обліковими записами Active Directory.

Практична проблема мішаних мереж (типовий сценарій, з яким ви зустрінетесь у реальній роботі, — Linux-сервер, що повинен обслуговувати файлами Windows-клієнтів, чи навпаки) розв'язується проєктом **Samba** — реалізацією протоколу SMB безпосередньо на Linux, що дозволяє Linux-серверу виглядати для Windows-клієнтів так, ніби він звичайний файловий сервер Windows, включно (за додаткового налаштування) з можливістю самому Samba-серверу виконувати роль контролера домену, сумісного з Active Directory, — практична межа, де дві операційні системи цього модуля не просто співіснують поруч (як ми зазначали в лекції 25), а безпосередньо взаємодіють одна з одною тим самим протоколом.

| | SMB | NFS |
|---|---|---|
| Походження | Windows / Microsoft | Unix / Linux |
| Модель дозволів | тісно пов'язана з Active Directory | традиційна модель Unix (користувач/група/інші) |
| Linux-реалізація | Samba | нативна |
| Windows-реалізація | нативна | потребує додаткового компонента |

## Docker на практиці: від теорії мережі до реального сервісу

У лекції 23 ми детально розібрали, *як* Docker будує мережу — міст `docker0`, veth-пари, PAT, проброс портів. Сьогодні застосуємо це практично, розгорнувши реальний вебсервіс.

```text
$ docker run -d --name web1 -p 8080:80 nginx
```

Ця одна команда завантажує образ Nginx (якщо його ще немає локально), запускає контейнер у фоновому режимі (`-d`), і прокидає порт 80 контейнера (де Nginx слухає за замовчуванням) на порт 8080 хоста, — саме той **проброс портів**, детально розглянутий у лекції 23, тепер застосований до конкретного, реального сервісу, а не абстрактного прикладу.

Реальний застосунок рідко складається з одного-єдиного контейнера — типовий сценарій: вебсервер, застосунок і база даних, кожен у власному контейнері, що мають взаємодіяти між собою. **Docker Compose** дозволяє описати весь такий набір контейнерів одним декларативним файлом:

```text
services:
  web:
    image: nginx
    ports:
      - "8080:80"
    depends_on:
      - db
  db:
    image: postgres
    environment:
      POSTGRES_PASSWORD: examplepass
```

Запуск `docker compose up` піднімає обидва контейнери одночасно, автоматично створює для них спільну, ізольовану мережу (той самий міст `docker0`-подібний механізм із лекції 23, тільки тепер окремий для цього конкретного набору сервісів), у якій контейнер `web` може звертатись до контейнера `db` просто за іменем сервіса `db` (Docker Compose автоматично додає внутрішній DNS-запис для кожного сервіса — маленький, локальний приклад того самого принципу, який Kubernetes реалізує в набагато більшому масштабі через Service з лекції 23). Це і є практичне втілення **"інфраструктури як код"**, про яку ми вперше згадали ще в лекції 1 й повторно — стосовно SDN у лекції 21: увесь опис розгортання — один текстовий файл, який можна зберігати в системі контролю версій, відтворювати ідентично на будь-якому іншому сервері й переглядати як історію змін, а не як разову, ручну послідовність команд, слід якої губиться одразу після виконання.

## Три способи розгорнути ту саму мережеву службу — підсумок модуля

Варто явно звести докупи те, що весь цей модуль насправді показав вам на прикладі одних і тих самих мережевих служб (DNS, DHCP, вебсервер), розгорнутих трьома принципово різними способами.

**Класична установка на виділений сервер** (лекції 27-28: `Install-WindowsFeature`, `apt install bind9`) — служба працює безпосередньо на операційній системі хоста, повністю під вашим контролем, але прив'язана до конкретної, живої машини: оновлення, відмова обладнання й масштабування — усе це ваша особиста відповідальність адміністратора.

**Контейнеризація** (сьогоднішня лекція, спираючись на мережеву теорію лекції 23) — служба ізольована й портативна: той самий образ Docker запускається ідентично на ноутбуці розробника, тестовому сервері й у production, а масштабування (запустити ще один контейнер) — секундна, а не годинна операція.

**Повністю керована хмарна служба** (лекція 22: NAT Gateway, керований DNS хмарного провайдера) — ви взагалі не бачите й не адмініструєте жодного сервера, лише споживаєте готовий, повністю обслуговуваний провайдером сервіс.

Жоден із трьох підходів не "кращий" абсолютно — кожен наступний крок цієї градації обмінює частину прямого контролю над деталями на менше операційне навантаження й швидшу масштабованість, і саме розуміння всіх трьох одночасно (а не лише найновішого чи найзвичнішого) — те, що робить мережевого інженера здатним усвідомлено обирати правильний підхід для конкретної задачі, а не автоматично тягнутись до того, що вже знайоме.

## Модуль про мережеві операційні системи завершено

П'ять лекцій цього модуля пройшли шлях від концептуального порівняння двох філософій (лекція 25) через практичне командне керування кожною окремо (лекції 26-27) до конкретних, наскрізних служб, розгорнутих на обох одразу (лекції 28-29). Наступний модуль курсу звертається до теми, яку ми вже кілька разів згадували побіжно, — **служби каталогів**: Active Directory та протокол LDAP, на якому вона побудована, — центральний реєстр користувачів і ресурсів, що зв'язує докупи майже все, розглянуте в цьому модулі (DNS, файлові служби, автентифікація) в єдину, узгоджену систему керування підприємством.

> [!exam] На іспиті
> Типові питання: а) пояснити архітектурну відмінність Apache (процес/потік на з'єднання) від Nginx (подієво-орієнтована) і чому це впливає на придатність кожного для ролі реверс-проксі; б) описати, як конфігурація Nginx `upstream` реалізує принципи L7-балансування й TLS termination з лекції 24; в) порівняти SMB та NFS і пояснити роль проєкту Samba; г) пояснити, чим Docker Compose відрізняється від одиночної команди `docker run` і чому це приклад "інфраструктури як код"; д) порівняти три способи розгортання мережевої служби (класична установка, контейнер, керована хмарна служба) за критерієм контролю й операційного навантаження.

## Завдання на занятті (20 хв)

1. Допишіть конфігурацію Nginx з прикладу вище так, щоб пул `backend_pool` використовував алгоритм least connections (лекція 24) замість типового round robin (підказка: пошукайте усно, яка директива Nginx це реалізує, спираючись на логіку, вже знайому з лекції 24).
2. У парі поясніть одне одному, чому Linux-серверу, що повинен обслуговувати файлами і Linux-, і Windows-клієнтів одночасно, зазвичай потрібен саме Samba, а не лише нативний NFS.
3. Розширте наведений `docker-compose.yml`, додавши третій сервіс `cache` на основі образу `redis`, що має бути доступний контейнеру `web` за іменем сервіса.
4. Обговоріть: для якого сценарію (невеликий, стабільний внутрішній файловий сервер офісу vs популярний публічний вебзастосунок із непередбачуваним піковим навантаженням) кожен із трьох підходів розгортання, підсумованих вище, підходить найкраще, і чому.

> [!question] Перевірте себе
> 1. Чим архітектура Nginx принципово відрізняється від архітектури Apache?
> 2. Які дві директиви Nginx реалізують TLS termination, розглянуте теоретично в лекції 24?
> 3. Чим SMB відрізняється від NFS за походженням і моделлю дозволів, і яку роль виконує Samba?
> 4. Що саме дозволяє контейнеру `web` у Docker Compose звертатись до контейнера `db` просто за іменем сервіса?
> 5. Назвіть три способи розгортання мережевої служби, розглянуті в підсумку лекції, і коротко охарактеризуйте компроміс контролю й операційного навантаження для кожного.
